# AGENTS.md

Rules for coding agents working in this repository. The product plan is in `RFC.md`, and commands and milestone status are in `README.md`.

## Stage boundaries

  SEE-87 makes the Node sidecar's MCP interface one **optional adapter** over the request core, and changes nothing about the existing private agent workflow. `MCP_ENABLED` is the switch and defaults to on, so an existing deployment keeps every setting and behaviour it has. With it off, `/mcp` answers 404 — not served rather than locked, because a challenge would suggest a credential would open one — both OAuth metadata paths answer 404, and no MCP setting is required: a leftover `MCP_TOKEN`, `MCP_ALLOWED_HOSTS` or `MCP_DEMO_TOOLS` is ignored and named in the startup log, while `MCP_OAUTH_*` is a configuration error because the profile would advertise authorization for an endpoint the deployment does not serve. A broken switch value leaves the adapter on, so a typo cannot silently remove the endpoint. Adapters reach the core only through `requests/agent-api.ts`, which forwards and decides nothing: idempotency, parameter validation, the lifecycle's transitions, the pending limit and result handling stay in `RequestStore`, `requests/lifecycle.ts` and `requests/action.ts`, and the failure an adapter sees is the one the core raised, so agent-facing tool names, contracts, error codes and result delivery are unchanged. The boundary authenticates nobody — a credential belongs to the adapter that accepts it — and holds no connection, cache or store of its own. Pairing, the phone credential and what it may reach, stored request identity, `PrepareRequest`/`SubmitResult`, production updates, FCM registration and invalidations, `/healthz`, startup and shutdown are identical in both modes. Nothing is loaded at runtime and no adapter is accepted at runtime. Deployment extends Stage 7 rather than forking it: `gateway/compose.yaml` gained `MCP_ENABLED` and no new file. `sidecar/src/stage-boundary.test.ts` holds it: the adapter files may not name `RequestStore`, `TransactionPreparer` or `ConfirmationTracker`, nothing but `server.ts` may import the endpoint, the boundary may not open a listener or run SQL or read an `Authorization` header, and `createMcpEndpoint` is called in exactly one place. See `docs/wiki/mcp-adapter.md`.
- **Stage 7.1, client plugins and the broadcast gateway (in progress).** SEE-86 adds one boundary to the existing app and lifts no limit: a `plugins/` package of data and pure functions where a bundled client plugin can be registered, so SEE-93 (`jupiter.swap`) and SEE-94 (`jupiter.prediction`) can be written without changing a transport, a policy, the wallet, or storage. A plugin declares a stable ID, the contract version it was written against, the operations it serves and the environments it serves them in, and supplies exactly three behaviors: parameter collection, preparation, and inspection. What it is handed is exhaustive — the connection ID, the operation, the environment, the structured request, and the wallet the owner selected as a public address and network. It receives no credential, no wallet authorization token, no transport handle, and nothing that can approve or send; the owner's manual approval, the one-at-a-time wallet interaction, the policy evaluation and the local execution record all stay in core. Operations are named at the protocol's own level (`swap`), so no provider's name appears in `connections/`, `sync/`, `live/`, `push/`, `policy/`, `transactions/` or `activity/`. A plugin reports what it read as typed facts, coverage is derived from the instruction counts rather than stated, and the chain is core's — the network the owner's wallet is selected for, never the plugin's claim. An operation no plugin serves, one with nothing prepared, and one whose bytes couldn't be read all establish nothing and can never be `ALLOWED`: a missing plugin is a gap in the review, not a byte that turned out to be fine. The bundled list is empty at SEE-86, so a swap behaves exactly as it did; nothing is downloaded, and there is no dynamic load path. No storage format, proto, or screen changed. Two `StageBoundaryTest` checks hold it: the plugin package's imports against an exact list with no wallet interaction, store, HTTP client or approval in its code, and no provider name or plugin import in core transport. See `docs/wiki/client-plugins.md`.
- **Stage 7.1, server manifests, per-connection modes, and plugin compatibility (SEE-88).** A connection's kind is now part of its record, and it comes from the server's own validated statement rather than from how it was added. `seekervault.server.v1.ServerManifest` carries the server's lasting ID, the phone–server contract version it speaks, a settings revision, the mode (`direct` or `gateway_feed`), one reference — a URL, or a gateway origin and a channel — the client plugins its operations need with the contract range each needs, the environments it serves, and a bounded name it is never believed about. `PairingService.GetServerManifest` serves the sidecar's own, authenticated with the phone credential and scoped to the caller's connection; a sidecar from before this stage answers UNIMPLEMENTED, which is the documented legacy-direct path and not a failure. The sidecar's revision is stored (migration 6 on the `server` singleton) and moves by one exactly when the content the manifest is built from changes, never down. The phone validates before it stores: the identity, the origin and the mode must be the ones the connection already has, a publisher may name only its own channel, and the revision must be orderable and never backwards — so a manifest confirms where the phone is talking and can never redirect a credential, switch a transport, or claim another publisher's audience, and a mode is never guessed. Content that changed while the revision stood still is a contradiction the phone keeps neither half of. Support is derived from the plugins compiled into the build on every read and **never stored**, because a verdict on disk would outlive the build that reached it; missing plugin, incompatible plugin version, unsupported protocol, unsupported environment and refused manifest are separate states, and only supported, legacy and not-yet-asked are executable. A server this build doesn't support is readable and rejectable: nothing is prepared, no wallet is opened, and nothing falls back to signing a raw message or an unaccounted-for transaction. `Connection.mode` is stored, `ConnectionStore` is at version 2 and still reads a version 1 file as a direct connection whose server has not been asked, and `Connection.usable` carries the mode so every sidecar path — refresh, synchronization, push registration, wallet publication, every approval — excludes a feed at once. A feed holds no credential and never did. This build resolves no feed: `FeedGateway` is the seam, the gateway is SEE-90, and `addFeed` says so rather than pretending. No screen was redesigned. See `docs/wiki/server-manifests.md`.
- **Stage 7.1, shared proposals with device-local parameters, decisions and results (SEE-89).** A publisher broadcasts one document and everyone subscribed receives the same bytes, so `seekervault.proposal.v1.Proposal` is its own contract and the personal `ActionRequest` was **not** made shared to get there: a private request is still addressed to one phone and still returns its result to the server that asked. A proposal carries the publisher's identity and its own channel (`server/<its ID>`), a stable proposal ID, a revision that never goes backwards, the operation at the protocol's own level with the plugin it was written for, created/updated times, an absolute required expiry, an explicit open-or-cancelled status, the publisher's unverified note, and at most 32 bounded named terms — and nothing about any subscriber, because the publisher has none to describe. There is no per-proposal protocol version: what contract a publisher speaks is stated once in its manifest, and a feed cannot exist without that manifest having been validated. Delivery is not trustworthy about repetition, so one idempotent apply path takes every snapshot read, stream event and duplicate push: the same revision with the same terms writes nothing at all, a lower revision is refused, a higher one replaces the publisher's half and leaves this device's decisions exactly where they were, and the same revision with *different* terms is a contradiction the phone stops executing from until a higher revision says something new. A dismissal is final for the proposal's identity, not its revision, so a republication cannot put it back in front of someone who said no. What is executed is never "the proposal": the terms as they stood, the parameters this owner chose, the wallet they had selected, the plugin this build resolved and its contract version, and one set of prepared bytes are pinned together in one `ExecutionBinding` before any wallet opens, and `bindingProblem` is the whole gate — it asks for the standing rather than deciding again, so what the owner sees and what the gate allows cannot drift apart. A publisher's `plugin_id` is checked against what the build resolves and never used to select code. There is **one execution per proposal identity, ever**: the record is written before the wallet is opened so a second tap finds it, and it is not relaxed for a failure, a decline, or a new revision; an execution the app closed on is settled as unresolved and never as a failure, and nothing retries signing or submission automatically. Nothing on this side is published: for a feed there is no `PublishWallet`, `PrepareRequest`, `SubmitResult` or sync upload, because all of them already require `Connection.usable`, which requires the direct mode. Availability and standing are derived on every read, never stored. Activity gained `ActivityKind.Operation` with a `ReviewedOperation` — codes and public values, kept on the phone — and a feed's proposals go when the feed does while those records outlive it. This build receives no proposal and executes none: `ProposalFeed` is the seam, the gateway is SEE-90 and the stream SEE-91, the Jupiter plugins are SEE-93 and SEE-94, and `refresh` answers `NoFeed` rather than pretending. See `docs/wiki/shared-proposals.md`.
- **Stage 7.1, the Go broadcast gateway (SEE-90).** The shared service the stage's two seams pointed at now exists, in `broadcast/`, and it is **not** `gateway/`: that directory is one owner's reverse proxy in front of their own sidecar, and this is the service a developer's publisher publishes to and every subscribed phone reads from. It has two APIs in one package, `seekervault.gateway.v1`, and they are separate on purpose and separately deployed: `FeedService` reads and takes no credential, because a feed is a broadcast whose reference can be printed in a README; `PublisherService` takes a bearer credential scoped to one server, and listens on its own socket, so a read port serves no handler that could change anything and `publish.proto` is generated for Go alone — the phone is not a publisher, so no publisher client is compiled for it. The credential is the whole of the grant: it says which server the caller publishes as, and every document is checked against that rather than against what the document claims, so a publisher can name only its own channel (`server/<server_id>`) and a withdrawal names no channel at all. Three rules are the gateway's own: a published manifest must be a `gateway_feed` naming this gateway's configured origin, because a `direct` manifest carries a URL and relaying one would let a publisher point every subscribed phone at an address of its choosing; a revision must be positive and orderable (at most 2^63-1, which is what the phone can compare); and every document is **rebuilt from the fields that were validated**, so an unknown protobuf field is dropped rather than relayed, while over JSON a field the contract does not have is refused outright by a strict codec. The revision is the idempotency key, because it is already the publisher's promise about content: the same revision with the same content answers `unchanged` and writes nothing, the same revision with different content is a conflict that says which revision is held, a lower one is stale, a moved creation time is refused, and a withdrawal is final — nothing is published over one, because a phone keeps its record of a proposal it acted on for ever (SEE-89). A publication commits its outbox notice **in the same transaction as the document**, so a crash between persisting and fanning out leaves work to redo rather than a document nobody hears about; delivery is at-least-once and says so, two notices for one document collapse into the later one, and a notice is cleared only at the revision it was sent at. Reads are version-aware in the contract rather than in a header (`known_settings_revision`, `known_snapshot_sequence`, `Cache-Control: no-store`), a page is ordered by proposal ID and every page of one walk reports the sequence the walk began at — a documented boundary and not a transaction, which converges because each document carries its own revision — and retention serves a proposal until its own expiry plus the window, withdrawn ones included, so a phone that was switched off learns it was taken back rather than failing to find it. The store is SQLite, one file, six tables, and **no column anywhere for a subscriber**: no address, no chosen quantity, no decision, no result, and reading a feed writes nothing down. Registering a publisher is a local act with no network surface (`broadcastctl`), a credential is kept only as its SHA-256 and shown once, rotation is two steps so it needs no outage, and revoking every credential leaves the documents phones already read. Nothing is fanned out to yet: Centrifugo and Redis are SEE-91, `dispatch.Dispatcher` is the seam, and no phone calls the gateway in this build either — the Android client is SEE-91's, and what closes the loop here is the cross-runtime fixtures, written from the running service and read back by the phone's own validators. See `docs/wiki/broadcast-gateway.md`.
- **Stage 7.1, streaming delivery and reconnection recovery (SEE-91).** The gateway fans out now, and the phone listens: Centrifugo v6.9.6 with Redis 8 behind it, both pinned where the deployment names them. The transport is Centrifugo's **unidirectional gRPC**, and its shape decided the design, because a listener on it can send nothing after it connects — so it cannot subscribe itself, cannot ask for history and cannot refresh its credential. Every one of those was established by running the pinned release, not assumed: a connect request naming channels in `subs` is answered with a connection and **no subscriptions at all** (that map is a recovery position), a token-granted channel bypasses the anonymous-subscribe permission (so every such permission stays off and the ticket is the only way in), `channel_regex` does not constrain a token-granted channel, there are no application-level pings whatever `ping_interval` says (so liveness is HTTP/2's), and a graceful shutdown arrives as `3001` with `reconnect: false` — which is why the client reads the documented code range and not that field. The channels therefore come from a **ticket the gateway mints** (`FeedService.GetStreamTicket`): it says which channels and nothing about who — an empty subject, an expiry, no device identifier, no address, no record kept of minting it — and it names **no host**, because SEE-90 refused to relay a redirection and a ticket carrying an address would have reintroduced one. The stream is one fixed gRPC path on the gateway's own origin, which is the only address a phone ever learns. A publication carries `seekervault.gateway.v1.FeedEvent`: our envelope, not the broker's, so a phone parses one type and runs the document inside through the same validators a read goes through — **the stream is a faster way to learn something, never a more trusted one** — and an event of a kind it does not know is a reason to read the snapshot rather than an empty document. Recovery happens once, at connect, with `(epoch, offset)` per channel; `recovered: true` is the only proof of continuity, and every other answer — nothing held, a changed epoch, further behind than the broker keeps or will replay, a channel that is not recoverable — sends the phone to the **authoritative snapshot**, because the broker's history is a bounded cache and the documents are the gateway's. There is no buffer between the snapshot and the stream and none is needed: both apply through SEE-89's revision-ordered idempotent path, so a page from the middle of a walk and an event during it converge whichever order they land in. The broker's `offset`/`epoch` and the gateway's `sequence` are two counters with two jobs and are never compared; the revision decides. On the phone the listener is **foreground-only** and shares no state with the direct path's — one stream per gateway, opened on `onStart`, closed on `onStop`, reopened (debounced) when the feed set changes because the transport cannot add a subscription to an open stream — and there is no new background work, because a shared feed has nothing to deliver to a phone nobody is holding. The broker is configured so a listener can only listen: one transport, every publish/history/presence permission off, presence and join/leave off, no other transport, its own usage statistics off, its API and Redis on an internal network. Its Redis is deliberately not persisted — losing it costs each listener one snapshot. The vendored client schema lives in `third_party/centrifugo` with its digest, generates Kotlin through a third buf template into its own directory, and **one file in the app may import it**; a boundary test pins that, and another pins the field numbers the adapter reads. What is documented rather than hidden: the JSON history API cannot render these binary payloads (`limit: 0` still answers a position), and the broker's queue bound protects the broker rather than a slow phone — our client keeps reading, so what bounds a phone that falls behind is the gateway's publish rate limit. See `docs/wiki/broadcast-gateway.md#the-stream` and `docs/testing/stage-7-1.md`.
- **Stage 7.1, a push relay and per-feed topics (SEE-92).** SEE-73's push pipeline now covers the other kind of server, and nothing about the first one changed. The notifying is ours rather than a publisher's: after a publication commits, `broadcast/internal/relay` sends **one content-free message** to that feed's public Firebase topic — `kind=feed_invalidation`, `version=1`, and nothing else, so no proposal, revision, sequence or publisher is in it and nothing could be about one subscriber. Which feed changed is the **topic it arrived on**, which is a routing field rather than payload, the same line SAW-056 drew for a device target. It is a second `dispatch.Dispatcher` beside the broker and `dispatch.Fan` feeds both, with one asymmetry stated out loud: the broker carries the document and may defer a notice, the relay carries a hint and **never** does — a hint that could defer the outbox would make a Firebase outage into the broker re-publishing everything it had already delivered. The topic is `feed.<environment>.<server_id>`, derived from the channel in a notice the gateway wrote itself, and the phone is **told** it rather than deriving it (`FeedService.GetFeedTopics`, with `GATEWAY_PROBLEM_NO_PUSH` when a deployment relays nothing): a name worked out on both sides would drift into silence rather than into an error. A publisher is given no credential and has no field anywhere to put a topic in; the service account is the deployment's, mounted read-only into the gateway alone by `broadcast/compose.push.yaml`, and the image now carries a CA bundle for that one connection — a visible line in the Dockerfile. On the phone each half stays in the package that owns it: `push/FeedTopicManager.kt` subscribes and unsubscribes on SAW-055's serialized channel, `push/FeedTopicClient.kt` is the third and last file allowed to import Firebase, `sync/FeedSynchronization.kt` is the bounded read in the one package permitted a WorkManager, and `notifications/FeedNotifications.kt` is one type-aware native alert with a validated read-only route that opens the feed. Membership is Firebase's and **nobody keeps a list**: the gateway is never told who joined, and the phone derives its subscriptions from the owner's connections every time — a topic nothing wants is unsubscribed from when a hint arrives on it. The work input is empty, so a coalesced, dropped or delayed hint costs nothing: the read covers every feed the phone holds.
- **Stage 7.1, the Jupiter Swap plugin and the path to a wallet (SEE-93).** `jupiter.swap` is the first real client plugin, and the boundary SEE-86 landed held: the plugin reaches **one host of its own** and takes everything else from what it is handed — no credential, no wallet token, no store, no approval, neither of the app's transports, and no decoder of its own. Its whole shape is decided by one fact: the phone reaches no chain, so it can only approve bytes it can read offline. A versioned Solana message loads its accounts from lookup tables that cannot be resolved without the chain, and Jupiter's own statement of what its tables hold is a builder's account of its own bytes — exactly what this app has never accepted. So the request says `asLegacyTransaction` and `onlyDirectRoutes`, an answer needing a table is refused, and the single hop is **verified in the bytes** rather than merely asked for; if that parameter ever goes away the plugin stops preparing rather than starts signing what it cannot read, which is written down as the standing risk. A signal names **mints, never tickers** — there is deliberately no way to propose "buy Bitcoin", only a specific wrapped mint — with decimals, a slippage ceiling, optional amount bounds and optional unverified symbols; the amount and the slippage are the owner's, in base units and whole basis points, and never leave the phone. The review establishes, out of the instructions: nothing signed yet, the owner's wallet paying and nothing else signing, one routing instruction the owner authorizes, the input leaving the owner's own token account for the publisher's mint in exactly the entered amount, the output arriving in the owner's own account for the other mint, the floor the instruction enforces equal to the offer's stated threshold to the base unit, no platform fee in either form, and every other instruction one of the five a swap has a reason for. It does **not** read the route plan, and that is stated rather than hidden: the plan cannot change any of those things, because the program checks them and fails the whole transaction if the output falls under the floor — the phone verifies the bound, the chain enforces it. `operations/` is the path a person walks and **names no provider**, so SEE-94's plugin is shown by the same screens: a feed's **Signals** where a direct connection shows pending requests, then the publisher's words as theirs, the facts read out of the bytes, and the owner's rules under them. Approve appears only for bytes accounted for whole, which is input validation and not a rule to overrule. Approving re-reads the rules, compares the verdict with the one shown, **then** takes the wallet lock and only inside it binds and records — where expiry, revision, choice, plugin and wallet are checked at once. A preparation stands one minute, because a quote is a price from a moment ago and a legacy blockhash lasts about that long; changing a parameter throws away what was prepared for the old one. A wallet on any network but mainnet is refused before anything is asked. (SEE-97 later settled what sandbox does: the plugin no longer reads the environment at all, and core is what stops before the wallet.) `PLUGIN_CONTRACT` stays 1 and what it means was settled here rather than changed — a subject may carry a proposal's terms instead of a request, `inspect` is given core's copy of the owner's choice, `prepare` may fail, and a form may say why there is nothing to collect — because nothing had ever been written against it; the next change after a publisher exists raises it. The build's plugin list moved to the composition root, since a real plugin needs an HTTP client and `plugins/` holds none. A direct-mode swap request is **still not executable**: core prepares no swap, so its facts stay unread and Stage 6's server-side path was not resurrected. Four real transactions from the live keyless API are committed as fixtures and read by two independent readers; the privacy claim is captured traffic rather than an argument. See `docs/wiki/jupiter-swap.md` and `docs/integrations/jupiter.md`.
- **Stage 7.1, the Jupiter Prediction plugin (SEE-94).** `jupiter.prediction` reads which market a publisher pointed at, asks the provider what that market currently *is*, asks the owner which side and how much, prepares a real order through the same keyless API, and then the phone **resolves the transaction's accounts and reads the order out of the bytes** before the wallet is asked once. A publisher names a market and is believed about nothing else: open or closed, the two prices, the rules, the settlement time and whether it has already resolved all come from the provider at the moment the owner looks, and the market is read *before* an order is requested so a stale signal becomes "this market is no longer open" rather than an order that fails. The side and the stake are the owner's, are in no document, and reach neither the publisher nor the gateway. Its one real addition to the app was the owner's decision rather than mine: a prediction order arrives **only** as a versioned transaction whose accounts come from address lookup tables — six spellings of a legacy-transaction parameter were tried against the live API and all are ignored — so signing it without resolving them would mean signing something the phone cannot see. Rather than a parameter-only review or a plugin that never prepares, the phone now reads the chain: `solana/` is a shared, **provider-neutral** component with one read method (`getMultipleAccounts`), it discovers the tables from each transaction rather than hardcoding any, and it validates ownership, format, indices and the rebuilt account list in the runtime's own order — static, then every table's writable indexes, then every table's readonly ones, because any other order resolves each instruction to the wrong addresses silently. What that costs is documented rather than hidden: the review is only as accurate as the configured endpoint, which is **not** offline verification and **not** trustless; the endpoint is the application's or its host's and never a publisher's, because an endpoint chosen by the thing being reviewed is not a second opinion; it is **empty by default**, so a checkout reaches no cluster and a build that wants orders configures one deliberately; and a table that cannot be fetched or validated **blocks signing with its own reason** — there is no parameter-only fallback and no blind signature in that path. Resolving proves which accounts the runtime will use and nothing about whether they are the right ones, so every check that makes a swap approvable still runs: the owner pays and the order is theirs, it buys rather than sells, it buys **the side the owner picked** read from the instruction's own byte, the contracts and ceiling and cost and slippage are the ones quoted, the stake leaves the owner's own account for the provider's own token and the contracts land in the order's own account, and the funding swap is read by SEE-93's reader unchanged. The provider **co-signs**, so the rule is not "nothing else signs" but "exactly one signature is missing, it is the owner's, and the owner is the fee payer". It **stops at submission plus links**: no fill monitoring, no positions screen, no settlement, no payout claim, no profit or loss — afterwards the owner gets the transaction on the explorer and the market on the provider's platform, and deliberately **no position link**, because the platform has no per-position address and inventing one would be the only dishonest thing on offer. No URL is ever stored; every link is built where it is shown. `inspect` is still not suspending, on purpose: the chain read happens in `prepare`, so the boundary keeps its plainest promise that an inspection reads bytes and never a network. `PolicyAction.Prediction` gives the owner's rules a word for it, because a stake on an outcome is not a swap. See `docs/wiki/jupiter-prediction.md`.
- **Stage 7.1, the Go CopyTrading publisher template (SEE-95).** The thing every earlier ticket in this stage pointed at now exists: `publisher/`, a **second Go module** rather than a command inside `broadcast/`, because the gateway's operator and a publisher are different people and a template that compiled against the gateway's store would be a template nobody could copy out. It shares the protocol and nothing else, and where that could drift a test reads the gateway's own source (`internal/signals/contract_test.go`). One module, two templates: what is not about swaps — configuration, the store, the outbox, the API, the CLI — is the core, and the swap signal is one `signals.Kind` that `cmd/copytrading` registers, so SEE-96 is a second kind and neither can be turned into the other by configuration. **No feed client is generated for the module at all** (`buf.gen.publisher.yaml` takes the publisher API, its problem detail and the two documents), which is the same argument that keeps `publish.proto` out of the phone's generation: a publisher publishes and stops. The **API is the one path in** — the CLI is a client of it with no privileged access — so validation, the identity, the revision and the publication happen in one place; it is plain JSON over HTTP because what a strategy engine sends is this server's own affair, and the decoder refuses a field the contract does not have rather than dropping it, so `wallet`, `amount`, `decision`, `signature` and `result` are each answered "there is no field" and a term by that name is refused too. **The document is its own outbox**: every row carries the revision it is at and the revision the gateway has confirmed, so there is no second table to keep in step, a crash between storing and publishing leaves work to redo, and a retry sends identical bytes that the gateway answers `UNCHANGED`. A revision moves only when the content does, so an update that changes nothing publishes nothing and a restart republishes the same manifest revision — neither wakes a phone. `Idempotency-Key` is **required** on a create (the same key with the same statement is the same signal; with a different one it is a 409), and nothing else needs one. A gateway that is down answers **202 pending** with the next attempt's time and the drainer keeps trying; a refusal that retrying cannot fix answers **502 refused** with the gateway's own problem code and is retried only when somebody asks. Sandbox and production are separate deployments and the **database is stamped** with which, so a copied compose file pointed at an existing volume is refused at startup. Four tables and no column for a subscriber — a test reads the live schema — no Firebase, no broker, no MCP, no compiled-in service address, and neither credential in a log line. `PUBLISHER_PUBLISH_URL` exists because the manifest names where phones *read* and a publication *goes* somewhere that may be private; it was found by running the thing, not by reading it. See `docs/wiki/copytrading-template.md`, `docs/integrations/signal-api.md` and `docs/development/publisher.md`.
- **Stage 7.1, the Go Prediction publisher template (SEE-96).** The second template, in the same module and with the same core: `cmd/prediction` **discovers** Jupiter Prediction markets through its operator's filters and publishes one proposal per market that matches. The seam held — it registers `signals.Prediction` and nothing else about the configuration, the store, the outbox, the drainer, the manifest or the API changed shape — and the one thing that did is who writes the signals: `api.Authorship` is `ByDiscovery` here, so `POST /v1/signals`, `PUT /v1/signals/{id}` and `POST /v1/signals/{id}/cancel` answer **403 `written_by_discovery`** with the filters named, because a caller's signal would be undone by the next cycle; the front door does not forward them either, and `GET /v1/discovery` and `POST /v1/discovery/poll` are added. Two filters are the provider's own parameters (the venue and the bucket, plus its named filter) because they decide which events the listing returns at all; **tags, keywords, the state and the close-time window are applied to the records that came back**, over fields those records carry, and every market skipped is counted by reason so that "my filters match nothing" has an answer. **Absence is not closure**: a tracked market missing from a filtered listing is asked about directly, and only the provider's own answer — closed, cancelled, settled, or no such market — withdraws a proposal, while a provider that is unreachable, rate limiting or refusing a key withdraws **nothing** and the cycle is recorded as partial. A filter is discovery rather than withdrawal, so a market that stops matching keeps its proposal until the source ends it. Nothing is announced twice: the expiry is the market's **own close time** rather than anything derived from the clock (an expiry that moved would move the revision and wake every phone on every cycle), the idempotency key is **derived** — `market:<venue>:<id>:<generation>` — and a market row's proposal is `UNIQUE`, so one market cannot become two proposals however a cycle is interrupted; a market that closes and re-opens gets a *new* proposal, because a withdrawal is final for every phone that saw it. The provider's identifiers are published and **its links are not** — a URL a publisher chose, arriving on a phone, is what the manifest rules exist to prevent — and the provider's key lives in one `x-api-key` header with a test that searches every answer and the whole log for it. `internal/jupiter` is **the only file in the module that names a provider's host**, which is the rule the phone applies to the same constant; the API is in beta by its own documentation, so a market this template cannot read is skipped with a line naming it, and seven real captured answers plus an opt-in live test are what keep the shapes honest. There is **no model in it**: no recommendation, no probability of its own, no ranking but by close time, and no term a side could be published in. The store is six tables now and is brought forward a version at a time rather than refused, so a CopyTrading deployment's database opens with its signals intact. See `docs/wiki/prediction-template.md`, `docs/integrations/jupiter.md#prediction-discovery-see-96` and `docs/development/publisher.md`.

- **Stage 7.1, explicit Sandbox and Production modes (SEE-97).** One environment contract across the manifest, both templates, the gateway, both client plugins and this phone's own records, and the shape of it is that **a manifest says which environments a server *serves* while a connection records which one it *keeps***. Those are different facts in different places, which is what makes a promotion to production something a person did: a feed starts in **sandbox** whenever its publisher serves one, `ConnectionRepository.setEnvironment` is the owner's only way to move it and refuses an environment the server does not serve, and a manifest that stops naming the one a connection keeps makes that server *unsupported* — readable, executing nothing — rather than moving the connection to the other one. The shared gateway refuses such a document upstream anyway: the environments a server ID published **may not move at any revision** (`other_environment`), because a promise a higher revision can raise is not a promise, and every subscribed phone caches a manifest by revision. A second environment is a second deployment, which is the rule the publisher's own database stamp already kept at its end. **Sandbox is the real thing minus the signature**: the same live provider read, the same transaction bytes, the same inspection, the same rules — and then no wallet, nothing sent, and **no signature or explorer link invented for something that did not happen**. Neither plugin reads the environment, and `PLUGIN_CONTRACT` is still **1**: nothing about the boundary changed, only what core does with a preparation made in one of them, exactly as which cluster bytes are for has always been core's. The promise is pinned in the `ExecutionBinding` and compared with the connection's inside the wallet's single lock, beside the preparation's expiry and the wallet selection, so a mode switch that lands while an approval is in flight is refused rather than slipping through; and the sandbox branch of an approval is **lexically outside `withWallet`**, so there is no session in scope to sign with. A rehearsal is recorded as `Simulated` with the promise it was bound under beside the cluster, it **spends the proposal** exactly as a decline in the wallet does, and it counts nothing against a daily threshold the owner set on real money. An environment is **not a Solana cluster** and does not choose one — there is no Jupiter devnet or testnet to point sandbox at, the wallet's own network is still checked in both, and the app's existing devnet transfer and message checks are about a different thing. A **direct** connection is always production, by an invariant stated where a connection is built: a rehearsal is possible only where nobody is waiting for the answer, and an agent that asked for a signature can be told no but cannot be handed a simulation. Both templates' `.env` examples ship as sandbox so that copying one demonstrates the whole path without anybody's money, while the code itself still has no default. See `docs/wiki/environments.md`.

- **Stage 5, policies.** SAW-025 opened it, and it opened the model and nothing else (`docs/policy.md`): a policy is a per-connection document held only on the phone — allowlists of actions, assets (each on one network), recipients, and programs, plus per-operation and daily thresholds in the asset's own base units — and an assessment is one conjunction of the checks the owner configured. An absent list is not an empty one: the first configures no check at all, and the second allows nothing. Neither a connection with no policy nor one whose rules this build can't read is ever `ALLOWED`. There is no `BLOCKED` and no automatic approval, and a policy never softens input validation: a preparation whose bytes disagree with its request is refused before any policy is consulted, and is never relabelled as an advisory warning. The rules never reach the sidecar, and no agent can read or change them. SAW-026 made the phone apply that model: a request is assessed against facts the phone read for itself — the action kind from the structured request, and the asset, amount, recipient and programs out of the transaction's own bytes — never against an agent's prose; a transaction it couldn't account for whole is never `ALLOWED` however well the rest matched; and the day's spending is counted from the owner's own Activity records, per connection, wallet, asset and chain, over a local day, with confirmed amounts kept apart from ones the wallet was handed and never accounted for. SAW-027 gave the owner the editor (`docs/guides/policies.md`): a Rules screen under each connection, stock Material 3 only, with a switch per list because an absent list is not an empty one, thresholds hanging off the asset rows so a limit for an unlisted asset can't be written, SOL typed in SOL and a token in that mint's own base units — the phone can't establish a mint's decimal count without a transaction that carries it and won't guess one — and the exact base-unit number shown under every field as it is typed. Saving with nothing configured removes the connection's rules; a connection's rules go when the connection does; and rules this build can't read are never replaced by a blank form opening over them. SAW-028 put the assessment on the request-review screen (`docs/security.md#verification-versus-advisory-rules`): under everything the phone established for itself and never in place of it, with the verdict in words, every check and what it read, the checks nothing covered, and the line that never changes — both verdicts still need the owner's hand on the wallet. An affirmative answer to a request it warns about takes a deliberate step, and what the owner ticks is the assessment rather than the request, so a new preparation or an edited rule clears it; a connection with no rules warns about nothing, because warning on every request would teach them to tick without reading. The rules and the records are read again at the moment they answer, and an answer whose assessment changed under it stops rather than going ahead on what they read. Input validation still comes first and is never relabelled: no rule puts back an Approve button it took away, and there is no tick that would. The assessment they read is kept with the Activity record as codes — never the rules — and nothing about either reaches the sidecar. SAW-029 ran the whole thing end to end and wrote down what it does and does not do (`docs/guides/policies.md#worked-examples`): six scenarios from bytes the sidecar really built, through rules read off a real store on disk and the owner's own records, each asserting the classification *and* the exact reason codes *and* the checks it doesn't cover — across two connections and a restart. Two of them are the pair that matters: a request the rules warn about is exactly as approvable as it was, and one that matches every rule the owner wrote — the program list included — has no Approve button at all. The agent's own words are never an input: a note saying a tenth of what the instruction carries reaches the same decision, byte for byte, as the same transaction with no note. A day's counter is a floor and never a ceiling, and it does not pretend to see what a wallet did outside this app. And no policy string calls a verdict safe, secure, automatic, blocked, or guaranteed — a test holds it there. **The owner's own run on the Seeker is done**: device checks 56–78 are PASS, 2026-09-13, all 23 on their own device (`docs/testing/stage-5.md`), including the editor and the assessment at the largest system text size and under TalkBack, an ALLOWED verdict approved by hand in a real wallet, and an UNDER_RESTRICTIONS one rejected. Review of the stage PR then turned up three defects in code SAW-026 to SAW-028 had landed, each now fixed with a test that fails without the fix: a history nobody had read counted as a day with nothing spent, consent to a warning survived a transaction prepared again, and edits typed while a save was in flight were marked as saved.

  - the broadcast gateway is called and calls nobody it serves (SEE-90, SEE-91, SEE-92). `broadcast/internal/gateway/boundary_test.go` fails if shipped Go code outside `internal/stream` and `internal/relay` acquires an HTTP client or dials anything — one publishes to the broker and the other sends a hint through Firebase, and the same check fails if either carries an address of its own, so the two things that open a connection take where to open them from their operator (one string is allowed by its exact spelling, the OAuth scope, which is a name rather than a host) — if SQL appears outside `internal/store`, if `internal/rules` reaches for anything but the two documents and the shapes they are held to, if a provider's name appears anywhere in the service, if the schema's tables or columns change or grow a word about a person, if the field set of either gateway proto changes or a forbidden word appears in it, or if either listener answers anything but 404 for the other's procedures. The gateway's image carries a CA bundle since SEE-92, and only because of it: the broker beside it is plain HTTP on an internal network with nothing for a trust store to verify, while the push endpoint is somebody else's service over TLS. It is a visible line in `broadcast/Dockerfile` with the reason written beside it, which is the shape the earlier comment asked for.
  - the broker behind a feed is behind one file (SEE-91). `FeedBoundaryTest` reads every Kotlin source under `android/app/src/main` and fails if any file but `feeds/CentrifugoFeedStream.kt` imports the vendored schema, if anything else in `feeds/` so much as names a broker (comments included), or if the vendored proto's field numbers move under the adapter — and `pnpm generate` refuses to run at all if `third_party/centrifugo` is not the copy its `SHA256SUMS` records. `StageBoundaryTest`'s HTTP allow-list gained the two files that talk to a broadcast gateway, so a third one is a new host to read as one. The listener adds no background component: WorkManager stays inside `sync/`, and a feed's stream lives and dies with the foreground.
  - a proposal is bounded data too, and the package that reads one decides nothing (SEE-89). `StageBoundaryTest` reads `proposals/`'s imports against an exact list — the ID and channel rules, the plugin registry and the names a proposal may use for it, what this build supports, the owner's selected wallet, and the protocol message — and fails if the code (comments removed) names a feed, a wallet, a transport, a store, an approval, or `suspend`. It also reads `proto/seekervault/proposal/v1/proposal.proto` and fails if the field set changes or if a forbidden word appears in it, so a field that could carry a subscriber's address, their chosen quantity or anything prepared for them to sign has to be added to the check first.
  - a server manifest is bounded data, and the package that reads one acts on nothing (SEE-88). `StageBoundaryTest` reads `servers/`'s imports against an exact list — the pairing code's URL and ID rules, the plugin registry and the names a manifest may use for it, and the protocol message — and fails if the code (comments removed) names a wallet, a transport, an HTTP client, a store, an approval, or so much as `suspend`. It also reads `proto/seekervault/server/v1/manifest.proto` and fails if the field set changes, so a field that could carry a permission, a policy, or a wallet endpoint has to be added to the check first.
  - the client plugin boundary can't reach a wallet or a sidecar (SEE-86). `StageBoundaryTest` reads `plugins/`'s imports against an exact list — the typed facts a policy is applied to, the asset and the action they name, the protocol's requests and networks, the app's three-state verdict, and the owner's selected wallet — and fails if the code (comments removed) names a wallet interaction, a wallet token, a transport, an HTTP client, a store, or an approval. A second check fails if a provider's name appears in `connections/`, `sync/`, `live/`, `push/`, `policy/`, `transactions/`, `activity/` or `operations/`, or if the package is imported outside `plugins/`, `servers/`, `proposals/` and `jupiter/` by any file other than `SeekerVaultApplication.kt`, `InboxViewModel.kt`, `ConnectionsViewModel.kt`, `ConnectionStore.kt`, `ProposalRepository.kt`, `ProposalStore.kt`, `OperationViewModel.kt` and `ProposalReviewScreen.kt` (SEE-88, SEE-89 and SEE-93 added the last six on purpose: one shows the owner whether their servers are supported, one reads a cached manifest's plugin names back off disk, one holds what the owner chose about a proposal, one reads that choice back, and two review a proposal and prepare it). `jupiter/` is an owner rather than a listed importer, because being written against the boundary is what a plugin *is*.
  - the swap plugin reaches its provider and nothing else of this app's (SEE-93). `StageBoundaryTest` reads `jupiter/`'s imports against an exact set of packages — the boundary, the decoder and instruction readers that already exist, the protocol's networks, the wallet's public selection and base58, and its own string resources — and fails if the code names a wallet interaction, a store, an approval, a policy evaluator, or either of the app's own transports. It also fails if the provider's host appears in any file but the one that dials it, if the build's plugin list is not in the composition root, or if any file outside `transactions/` reads the Solana message format itself: the plugin *calls* the one decoder and has no second one, because a plugin that parsed the message again could disagree with the review about what a transaction even contains.
  - the policy package can't act and can't speak (SAW-025, SAW-026, SAW-027) — the editor the owner writes the rules on included. `StageBoundaryTest` reads its imports, and every one of them is a read: the connection ID rule, the protocol's requests and networks, what the phone read out of a transaction's bytes, the owner's own activity records, the address rule, and the app's own strings, back button, and date format. Nothing that opens a wallet, a connection, or a socket. There is no `BLOCKED` in it and no branch that acts on a verdict. SAW-028 adds the other half of that line: the two files that speak to a sidecar have never heard of a policy, and the one file in `connections/` that has, has it to delete a removed connection's rules and nothing else. The rules never leave the phone, and neither does what they made of a request.
  - no backups of the phone's data
  - no app-declared background component except WorkManager code under `sync/` and SAW-055's `FirebaseMessagingService` under `push/`; SAW-056 lets that service accept only its exact fixed invalidation, SAW-057 limits it to validation plus authoritative empty-input work enqueue, and SAW-058 permits only a post-Sync notification and validated read-only tap route. SEE-105 lets that presentation read the cached kind and local source name, and nothing that can act. SEE-92 adds a second exact-match invalidation to the same service, a second empty-input job under `sync/`, a third and last Firebase-importing file (`push/FeedTopicClient.kt`, pinned by name) and a second notification channel, and lifts nothing: no foreground service, no new component, and no payload that is acted on. No foreground service, other direct service, JobScheduler, alarm, receiver, notification action, or wallet automation exists

  The stage that lifts a limit changes the guard on purpose.
- **Don't implement later tasks early.** A directory for a later component doesn't mean the component should be built yet.
- **Never fake success.** A command whose task hasn't landed must fail clearly, and a check must never pass without doing what it claims.
- **Live commands are display-only text.** They are never shell code or instructions to execute on the phone.

## UI

- The checked-in [approved SEE-64 v4 design](docs/design/README.md) governs Android theme and component presentation. Its system-following lime/dark and light palettes, typography, shapes, solid layers, semantic colour mappings, and screen hierarchy supersede earlier directions to use stock Material defaults, including historical stage descriptions that say “stock Material 3 only.”
- Before changing UI or resolving a UI merge conflict, read both design HTML files, `SeekerVaultTheme`, and the affected components. Preserve approved decisions when an unrelated review or older stage instruction conflicts with them; record a genuine unresolved conflict instead of silently substituting Material defaults.
- Use Jetpack Compose and Material 3 components with the approved v4 tokens. Do not replace the production theme with parameterless `darkColorScheme()` / `lightColorScheme()`, wallpaper-derived colours, or stock-purple defaults.
- Keep changes to the approved design intentional and documented. Do not rewrite the reference HTML to match an implementation regression.

## Tests and checks

- **Before handing off,** run these:
  - `pnpm test:push`: the Stage 5.3 connection-ownership, payload, handoff, notification, tap, and Firebase-off recovery acceptance suite; it uses injected delivery and never counts as a physical-device pass
  - `pnpm test:updates`: the Stage 5.2 production HTTP/2 and cross-component acceptance suite, separate from Stage 1
  - `pnpm check`: formatting, lint, types, tests
  - `pnpm test:hello`: the Stage 1 acceptance suite
  - `pnpm test:queue`: the Stage 2 acceptance scenario
  - `pnpm check:android`: Kotlin formatting, unit tests, Android lint, and the debug and instrumentation APKs
  - `pnpm check:broadcast`: the broadcast gateway's formatting, `go vet`, and its tests (SEE-90). It needs Go; nothing else does
  - `pnpm check:publisher`: the publisher templates' formatting, `go vet`, and their tests, including the ones that run the real gateway (SEE-95, SEE-96). It needs Go
  - `pnpm test:integration`: Stage 7.1's cross-component acceptance (SEE-98) — the real gateway, both real templates, two subscribers, the sidecar and an agent, then the direct-mode suites and the phone's cross-component cases. It needs Go, and it reports every leg as PASS, FAIL or NOT RUN
  - `pnpm check:loadtest`: the load harness's own tests (SEE-99) — its quantiles, the client policy ported from the phone's, its profiles and its boundaries. It needs Go and nothing else
  - `pnpm test:load`: SEE-99's load, isolation and failover measurement — fourteen scenarios over five workload profiles, each PASS, FAIL or NOT RUN. It needs Go, and `SEEKERVAULT_CENTRIFUGO` and `SEEKERVAULT_REDIS` for anything that streams; without them those scenarios are NOT RUN rather than passing. Run it when the gateway, the broker configuration, the fan-out or the phone's reconnect policy changes — a load report is only about the revision it names

  CI runs the same commands, plus `pnpm test:hello --device` on an emulator, and never commits.
- **Test every behavior change.** A deliberately broken test must make the relevant check fail.
- **Report physical-device checks as PASS, FAIL, or NOT RUN.** Mocks, emulators, and a successful APK build never count as a device pass.
- **Never commit secrets.** That covers credentials, tokens, `.env`, `local.properties`, keystores, real wallet keys, and machine-specific paths. Default checks must never spend mainnet funds.
- **Generated protocol code and fixtures come only from `pnpm generate`.** Don't edit them by hand. After changing `proto/`, run `pnpm generate` and commit the output. `pnpm check:generated`, which CI also runs, fails if the committed output is stale.
