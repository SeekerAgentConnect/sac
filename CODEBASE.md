## Project Overview

Seeker Agent Connect (repository: `SeekerAgentWallet`; compatibility package name: `seeker-vault`) is an Android app for the Solana Seeker phone that acts as a control center for requests from external AI agents, plus the self-hosted server software it talks to. Agents propose actions (message signing, transfers, Jupiter swaps) over MCP to a self-hosted TypeScript sidecar; the user reviews each request on the phone against per-connection policies and approves it through Mobile Wallet Adapter and Seed Vault Wallet. The sidecar never holds keys or signs. Stack: Kotlin/Compose (Android), TypeScript/Node (sidecar, test agent), Protobuf + Buf + Connect (phone–sidecar contract), Docker Compose (gateway/deployment).

## Architecture

The overview, with diagrams, is in `docs/architecture.md`.

**Stage 1 (accepted):**

- Hermes or the test agent calls the MCP tool `vault_display_command` on the sidecar.
- The sidecar delivers the text over the foreground-only `WatchCommands` stream (which opens with `ready`) to the open Android screen.
- The user taps OK, and `AcknowledgeCommand` returns `{id, result: OK}` to the MCP caller.
- The sidecar holds one watcher and one in-flight command, with a deadline (`LIVE_COMMAND_TIMEOUT_SECONDS`) and the errors OFFLINE, BUSY, TIMEOUT, CANCELLED, UNAUTHENTICATED, UNKNOWN_COMMAND, and INVALID_TEXT.
- The live flow is in memory. The sidecar is loopback-only, and remote agents use an SSH tunnel.
- Progress: the contract and rules (SAW-002), the sidecar bridge (SAW-003), the Android screen (SAW-004), the test agent (SAW-005), and the MacBook → Seeker guide (SAW-006), and the Hermes connection (SAW-007) exist. See `docs/protocol.md`, `docs/development/sidecar.md`, `docs/development/android.md`, `docs/guides/`, and `docs/integrations/hermes.md`.

**Stage 2 (complete in code):**

- SAW-009 defined the durable contract in `proto/seekervault/request/v1` and `docs/protocol.md`:
  - An agent creates a request over MCP and gets `request_id` and PENDING at once; it reads the result with `vault_get_request`.
  - The phone uses unary `RequestService` RPCs, and every reference names the connection and the request.
  - The lifecycle has ten states and explicit transitions, and each transition names who causes it.
  - Approval binds to a prepared version and its content hash, and it's the commit point before the wallet is invoked.
  - Idempotency keys fingerprint the action, so a changed retry is refused.
- SAW-010 serves it:
  - The sidecar stores requests in SQLite: `DATABASE_PATH`, by default `sidecar/data/sidecar.db`.
  - Each operation is one transaction that commits before it answers, and expiry is applied first.
  - Nothing runs on its own after a restart.
- SAW-011 adds pairing and separate roles (`docs/security.md`):
  - `pnpm pair` issues a one-use pairing token bound to `SIDECAR_PUBLIC_URL`, and shows it as a QR code. `PairingService.Pair` exchanges it for a new connection and its credential.
  - There are four credentials, each accepted in one place: `MCP_TOKEN` on `/mcp`, the pairing token on `Pair`, the phone credential on `RequestService` and `RevokeConnection`, and `PHONE_TOKEN` on the Stage 1 `LiveCommandService`.
  - One phone is active per sidecar. Pairing again, or revoking, cancels the previous connection's PENDING requests.
  - The sidecar stays on loopback, and a phone elsewhere reaches it through a trusted TLS endpoint.
- SAW-012 adds the phone's connections (`docs/guides/pairing.md`):
  - The app opens on Connections. Add connection scans a pairing code or takes it typed in, shows the server to confirm, and pairs.
  - Each connection is keyed by its connection ID: a JSON file of metadata, and the credential, encrypted under a Keystore key, in `noBackupFilesDir`. Nothing is backed up.
  - A credential goes only to its own URL. A code never changes an existing connection, and a credential the sidecar rejects is deleted.
- SAW-013 adds the pending inbox (`docs/guides/pending-requests.md`):
  - The phone fetches every page of PENDING requests when the app opens or comes back to the foreground, when a connection is opened, or on Refresh. Nothing is pushed, and nothing runs in the background.
  - Pending requests shows each request's source, action, age, and expiry. Request details acknowledges or rejects a queued ack.
  - An answer is stored first, keyed by connection and request ID, and sent again until the sidecar settles it. A repeat is recognized, and a request cancelled first is marked superseded.
- SAW-014 validates the workflow (`docs/testing/stage-2.md`):
  - `pnpm test:queue` and `Stage2AcceptanceTest` run the two-sidecar scenario: restarts, expiry, rejection, revocation, and isolation between connections.
  - `vault_request_ack` is served only with `MCP_DEMO_TOOLS=true`.
  - Hermes's example config allows the durable tools.

**Stage 3 (in progress):**

- SAW-016 signs a message the owner approved (`docs/guides/message-signing.md`):
  - `vault_sign_message` stores a request; the wallet is opened only after the owner taps **Approve and sign** on the phone.
  - The approval carries the SHA-256 of the exact message bytes, and the sidecar refuses any other hash.
  - `requests/signature.ts` verifies the signature against the request's wallet and its own copy of the message. The sidecar holds no key and signs nothing.
  - The tool takes the message as text only, and its UTF-8 bytes are what is signed: no public tool can queue bytes the owner can't read. `SignMessageAction.data` stays in the contract for a later stage.
  - The result gives the agent `wallet`, `signature`, and `signed_message_base64`, so it can verify the signature itself.
  - Nothing is broadcast, so a signing the phone lost track of is FAILED, never UNKNOWN.
- SAW-017 makes one wallet interaction produce one reported outcome (`docs/testing/wallet-lifecycle.md`):
  - The wallet is asked once, between the approval and the outcome. `ConnectionRepository.deliver`, which every retry goes through, talks to a sidecar and never to a wallet.
  - What the wallet did is stored before it is sent, sends are serialized per request, and the sidecar returns the same terminal result for a repeat, across a restart too.
  - An answer this phone never received is `SigningOutcome.Unresolved`: shown as unresolved, reported as a failure, and never signed again. `InboxViewModel.onAppVisible` settles them on each return to the foreground.
  - A rotation keeps the request, the approval, and the signing; the MWA sender waits for the next screen's rather than failing.
- SAW-015 connects the owner's wallet and publishes the binding (`docs/guides/wallet-setup.md`):
  - The app reaches the wallet only through `wallet/WalletAdapter.kt`; `MwaWalletAdapter` is the only file that imports the Mobile Wallet Adapter client, and it runs the wallet from `MainActivity`'s `ActivityResultSender`.
  - The phone keeps the selection and the wallet's authorization as one encrypted record in `noBackupFilesDir/wallet/` (SEE-84). The authorization never reaches a sidecar, a log, or a backup.
  - `RequestService.PublishWallet` carries the address and network to each connection. The sidecar stamps `bound_at`, and cancels the PENDING requests the new binding no longer fits.
  - `vault_get_address` gives agents the binding, or `WALLET_NOT_CONNECTED`. No address is ever invented.
  - Creating a wallet action is refused with `WALLET_NOT_CONNECTED` or `WALLET_MISMATCH`. The tools that create them come in the later tasks of Stages 3, 4, and 6.

**Stage 7.1 (in progress):**

- SEE-88 lets a server say what it is, and the phone decide whether it supports it (`docs/wiki/server-manifests.md`):
  - `proto/seekervault/server/v1/manifest.proto` is the document: identity, the phone–server contract version, a settings revision, the mode (`direct` or `gateway_feed`), one reference (a URL, or a gateway origin and a channel), the client plugins its operations need with a contract range each, the environments it serves, and a bounded name that is never believed. Its own package, because the Go gateway (SEE-90) and the publisher templates (SEE-95, SEE-96) publish one too and serve no `RequestService`.
  - `PairingService.GetServerManifest` serves the sidecar's own, under the phone credential and scoped to the caller's connection. An older sidecar answers UNIMPLEMENTED, which is the documented legacy-direct path: no manifest, nothing required, behaviour exactly as it was.
  - The sidecar's revision is real, not a constant: `sidecar/src/manifest.ts` fingerprints the content and migration 6 stores the revision on the `server` singleton, so the same settings republish the same revision and a change moves it up by one, never down.
  - `android/.../servers/` validates before anything is stored: the identity, the origin and the mode must be the ones the connection already has, a publisher may name only its own channel (`server/<its ID>`), and the revision must be orderable and never backwards. A manifest confirms where the phone is talking and can never redirect a credential or switch a transport, and a mode is never guessed.
  - Support is derived from the plugins compiled into the build on every read and never stored, so the same manifest becomes supported in a build that carries what it needs. Missing plugin, incompatible version, unsupported protocol, unsupported environment and refused manifest are separate states, and only supported, legacy and not-yet-asked are executable.
  - A server this build doesn't support is readable and rejectable: nothing is prepared, no wallet is opened, and nothing falls back to signing a raw message or an unaccounted-for transaction.
  - `Connection.mode` is stored (`ConnectionStore` version 2, which still reads a version 1 file), and `Connection.usable` carries the mode, so refresh, synchronization, push registration, wallet publication and every approval path exclude a feed at once. A feed holds no credential and never did.
  - This build resolves no feed: `connections/FeedGateway.kt` is the seam, the gateway is SEE-90, and `addFeed` reports that rather than pretending. No screen was redesigned.

- SEE-89 adds the document a publisher broadcasts, and keeps every decision about it on the phone (`docs/wiki/shared-proposals.md`):
  - `proto/seekervault/proposal/v1/proposal.proto` is its own contract, not `ActionRequest` with more subscribers: the publisher's identity and its own channel, a stable proposal ID, a revision that never goes backwards, the operation and the plugin it was written for, created/updated times, an absolute required expiry, an explicit open-or-cancelled status, an unverified note, and at most 32 bounded named terms. Nothing in it describes a subscriber, and the phone's boundary check fails if the field set changes.
  - There is no per-proposal protocol version: the publisher's manifest says which contract it speaks, and a feed cannot exist without that manifest having been validated (SEE-88).
  - `android/.../proposals/` is data and pure functions: the validated model keyed by publisher, channel and proposal; `ProposalRecord`, which keeps the publisher's half and this device's apart; the derived availability and standing; and `bindingProblem`, the one gate between a review and the wallet.
  - One idempotent apply path takes every snapshot read, stream event and duplicate push: the same revision with the same terms writes nothing, an older one is refused, a higher one replaces the publisher's half and leaves this device's decisions where they were, and the same revision with different terms is a contradiction the phone stops executing from. A dismissal is final for the proposal's identity, so a republication cannot undo it.
  - What is executed is the terms as they stood, this owner's parameters, their selected wallet, the plugin this build resolved and its contract, and one set of bytes — pinned before the wallet opens. There is one execution per proposal identity, ever; a second tap finds it; and one the app closed on is unresolved, never a failure.
  - Nothing on this side is published: a feed is excluded from `PublishWallet`, `PrepareRequest`, `SubmitResult` and generic sync by `Connection.usable`. The gateway learns only which channel this phone subscribed to.
  - Activity gained `ActivityKind.Operation` with a `ReviewedOperation`, and a feed's proposals go when the feed does while those records outlive it.
  - The path from a proposal to a signature is SEE-93's; SEE-89 left `ProposalFeed` as the seam and `bindingProblem` as the gate, and both are used as they stand. No screen was redesigned.

- SEE-90 adds the shared gateway both of those seams pointed at (`docs/wiki/broadcast-gateway.md`, `docs/development/broadcast.md`):
  - `broadcast/` is a Go service, and not `gateway/`: one is the owner's reverse proxy in front of their own sidecar, the other is the shared service developers publish to and phones read from.
  - `proto/seekervault/gateway/v1/` holds two services on purpose. `FeedService` reads and takes no credential; `PublisherService` takes one scoped to a single server, listens on its own socket, and is generated for Go alone — the phone is not a publisher, so `buf.gen.yaml` compiles no publisher client for it.
  - A credential is the whole grant: it says which server the caller publishes as, and every document is checked against that rather than against its own claim, so a publisher may name only its own channel and a withdrawal names no channel at all.
  - The gateway will not relay a redirection: a published manifest must be a `gateway_feed` naming this gateway's configured origin, because a `direct` manifest carries a URL and holding one would let a publisher point every subscribed phone somewhere of its choosing.
  - Every document is rebuilt from the fields that were validated, so an unknown protobuf field is dropped rather than relayed; over JSON a strict codec refuses a field the contract does not have, which is how an attempt to submit a wallet, an amount or a signature is answered.
  - The revision is the idempotency key: the same revision with the same content writes nothing, the same revision with different content is a conflict that says what is held, a lower one is stale, a moved creation time is refused, and a withdrawal is final.
  - A publication commits its outbox notice in the same transaction as the document, so a crash between persisting and fanning out leaves work to redo. Delivery is at-least-once and says so; two pending notices for one document collapse into the later one; a notice is cleared only at the revision it was sent at.
  - Reads are version-aware in the contract (`known_settings_revision`, `known_snapshot_sequence`, `Cache-Control: no-store`), a page is ordered by proposal ID, and every page of one walk reports the sequence it began at — a documented boundary that converges rather than a transaction.
  - The store is SQLite, one file, six tables, and no column for anything about a subscriber; reading a feed writes nothing down, and a boundary test reads the schema and the protos to keep it that way.
  - Nothing was fanned out in SEE-90 itself: `dispatch.Dispatcher` was the seam, and SEE-91 fills it. What closed the loop first was `proto/fixtures/seekervault/gateway/v1`, written from the running service by `broadcast/internal/gateway/fixtures_test.go` and read back by the phone's `GatewayProtocolFixturesTest`.

- SEE-98 is Stage 7.1's acceptance, and `pnpm test:integration` is where it lives (`docs/development/integration.md`, `docs/testing/see-98.md`):
  - **One command over four components.** It builds the gateway, `broadcastctl`, both templates and `publishctl`, runs `test-agent/src/stage71.acceptance.ts` against them with two subscribers, the sidecar as its own process and a real MCP agent, then the direct-mode acceptance suites unchanged and a filtered Android run. Every leg prints PASS, FAIL or **NOT RUN** with its reason.
  - **Mixed mode is the first thing it proves.** A paired sidecar answers the agent that asked while two public feeds are live, and a decision about a broadcast reaches nobody: the two subscribers' entire outbound traffic is feed reads, and the phone-side half of the same claim is `ProposalIsolationTest.aPairedSidecarAnswersItsAgentWhileAFeedAnswersNobody`.
  - **The privacy claim is a sweep of what the run wrote**, not an argument about the code: both publisher databases, the gateway's, every write-ahead log beside them, every process's log and every request the subscribers sent, searched for the owner's address, the message and the signature — with a positive control over the sidecar's own files, so a search that finds nothing cannot be a search that does not work.
  - **The provider is the committed captures, served to the binary.** `PREDICTION_PROVIDER_URL` points the shipped `prediction` binary at `publisher/internal/jupiter/testdata/` over loopback; only the timestamps are rewritten, because a market's close time decides whether it is published and a process reads the real clock.
  - **The broker leg is opt-in and says so.** With `SEEKERVAULT_CENTRIFUGO` the gateway runs behind the real pinned Centrifugo and the run checks that the publications reached the channel; without it, it checks the other half — `no_stream`, and the gateway's own log line — and reports the leg as NOT RUN.
  - Two harness rules worth keeping: a template's CLI is never run synchronously (a cycle it asks for calls a provider the test process is serving), and a probe that knocks on the wrong listener belongs to a third client, because what the two subscribers sent is itself asserted.

- SEE-97 makes the Sandbox/Production choice explicit and gives it one contract across the manifest, both templates, the gateway, both plugins and this phone's own records (`docs/wiki/environments.md`):
  - **A manifest says which environments a server *serves*; a connection records which one it *keeps*.** A feed starts in sandbox whenever its publisher serves one, only the owner moves it, and a manifest that stops naming the environment a connection keeps makes that server unsupported rather than moving it. A direct connection is always production, because an agent waiting for a signature cannot be handed a simulation.
  - **A rehearsal is the real thing minus the signature**: the same live data, the same bytes, the same review, the same rules, and then no wallet, nothing sent, and no signature or explorer link invented for something that did not happen. It is recorded as `Simulated`, it spends the proposal as any execution does, and it counts nothing against a threshold set on real money.
  - The promise is pinned in the `ExecutionBinding` and checked inside the wallet's own lock, beside the expiry and the wallet selection, so a mode switch cannot land between the check and the signature; and the sandbox branch is lexically outside `withWallet`, so there is no session in scope to sign with.
  - **The gateway refuses a manifest that changes the environments a server ID published** (`other_environment`): a promise a higher revision can raise is not a promise. A second environment is a second deployment, which is what the publisher's database stamp already enforced at its end.
  - Neither plugin reads the environment, and `PLUGIN_CONTRACT` is still 1: nothing about the boundary changed, only what core does with a preparation made in one of them.
  - An environment is not a Solana cluster and does not choose one: there is no Jupiter devnet to point sandbox at, the wallet's own network is still checked in both, and the app's existing devnet checks are about a different thing.
- SEE-95 adds the first publisher: the thing every other ticket in this stage pointed at (`docs/wiki/copytrading-template.md`, `docs/integrations/signal-api.md`, `docs/development/publisher.md`):
  - `publisher/` is a second Go module rather than a command inside `broadcast/`, because the gateway's operator and a publisher are different people and a template has to be copyable out; it shares the protocol and nothing else, and a test reads the gateway's own source where the two could drift.
  - One module, two templates: configuration, the store, the outbox, the API and the CLI are the core, and the swap signal is one `signals.Kind` that `cmd/copytrading` registers — SEE-96 is a second kind, and configuration cannot turn one into the other.
  - No feed client is generated for the module at all, so a template cannot read a feed: the same argument that keeps `publish.proto` out of the phone's generation.
  - The API is the one path in; the CLI is a client of it. Strict decoding refuses a field the contract does not have, so nothing about a subscriber can be sent, and a term by such a name is refused too.
  - The document is its own outbox: two revisions per row, so a retry sends identical bytes the gateway answers `UNCHANGED`, a revision moves only when content does, and a restart republishes nothing new.
  - `Idempotency-Key` is required on a create; a gateway that is down answers 202 pending and keeps being retried, and a refusal that retrying cannot fix answers 502 and waits for somebody to ask.
  - Sandbox and production are separate deployments, stamped into the database, so a copied compose file pointed at an existing volume is refused at startup.
- SEE-96 adds the second publisher, which finds its own signals (`docs/wiki/prediction-template.md`, `docs/integrations/jupiter.md#prediction-discovery-see-96`):
  - `cmd/prediction` is the same core with a provider client and a reconciler added, and with **nobody who may write a signal through its API**: its proposals are the reconciler's, so a caller's would be undone by the next cycle, and the three writing endpoints answer 403 with the filters named.
  - Two filters are the provider's own parameters, because they decide which events the listing returns at all; tags, keywords, the state and the close-time window are applied to the records that came back, over fields those records carry. Every market skipped is counted by reason, which is the answer to "my filters match nothing".
  - **Absence is not closure.** A tracked market missing from a filtered listing is asked about directly, and only the provider's own answer — closed, cancelled, settled or gone — withdraws a proposal; a provider that cannot be reached withdraws nothing. A filter is discovery rather than withdrawal, so a market that stops matching keeps its proposal until the source ends it.
  - Nothing is announced twice: the expiry is the market's own close time rather than anything derived from the clock, the idempotency key is derived from the market and its generation, and the outbox is the same two revisions — so a cycle every five minutes, a retry and a restart all wake nobody. A market that closes and re-opens gets a new proposal, because a withdrawal is final.
  - The provider's identifiers are published and its links are not: a URL a publisher chose, arriving on a phone, is what the manifest rules exist to prevent. The provider's key lives in one request header, and a test searches every answer and the whole log for it.
  - There is no model in it: no recommendation, no probability of its own, and no term a side could be published in.
- SEE-94 adds the second client plugin, and with it the app's first chain endpoint (`docs/wiki/jupiter-prediction.md`, `docs/security.md#resolving-a-lookup-table`):
  - `jupiter.prediction` reads which market a publisher named, asks the provider what that market currently is, asks the owner which side and how much, prepares a real order, resolves the transaction's accounts and reads the order back out of the bytes.
  - A publisher names a market and is believed about nothing else; the market is read before an order is requested, so a stale signal shows as a closed market rather than as an order that fails.
  - The provider only ever returns a versioned transaction whose accounts come from address lookup tables, so the phone reads them: `solana/` is a shared, provider-neutral component with one read method, discovering the tables from each transaction and validating ownership, format, indices and the rebuilt order.
  - The endpoint is the application's and empty by default; a table that cannot be fetched or validated blocks signing with its own reason, and there is no parameter-only review anywhere.
  - The provider co-signs, so the rule is "exactly one signature is missing and it is the owner's" rather than "nothing else signs".
  - It stops at submission plus links: the transaction on an explorer and the market on the provider's platform, with no position link invented and no URL stored.
  - `PolicyAction.Prediction` gives the owner's rules a word for a stake on an outcome.
- SEE-93 writes the first client plugin against SEE-86's boundary and joins SEE-89's record to a wallet (`docs/wiki/jupiter-swap.md`, `docs/integrations/jupiter.md`):
  - `jupiter.swap` reads a spot-swap signal's terms, asks the owner for an amount and a slippage within the publisher's ceiling, gets a quote and an unsigned transaction from Jupiter itself, and reads those bytes back independently. It reaches one host of its own and imports nothing that could sign, store or approve.
  - An asset is a mint and never a ticker, so there is no way to propose "buy Bitcoin" — only a specific wrapped mint. Direction is the ordered pair, with no separate side field.
  - The transaction is asked for in the **legacy** format and as a **single hop**, because a versioned message loads accounts from lookup tables a phone that reaches no chain cannot resolve — and the provider's own statement of what its tables hold is a builder's account of its own bytes. The hop count is then verified in the bytes rather than trusted from the request.
  - The review establishes the authority, both token accounts as the owner's own derived addresses, the exact input amount, the floor the program will enforce, the absence of a platform fee, and every other instruction as one of the five a swap has a reason for. It does not read the route plan, and says so: the plan cannot change any of those, because the program checks them itself.
  - `operations/` is the path a person walks and names no provider. A feed's **Signals** sit where a direct connection's pending requests do; Approve appears only for bytes accounted for whole; approving re-reads the rules, then takes the wallet lock, and only inside it binds and records.
  - `PLUGIN_CONTRACT` stays 1 and what it means was settled here rather than changed, because nothing had ever been written against it. The build's plugin list moved to the composition root.
  - A direct-mode swap request is still not executable, and Stage 6's server-side path was not resurrected.
- SEE-92 extends SEE-73's push pipeline to a publisher's public feed (`docs/wiki/broadcast-gateway.md#the-push-relay`, `docs/guides/firebase.md#the-broadcast-relay-and-feed-topics-see-92`):
  - The notifying is the gateway's, not a publisher's: `internal/relay` sends **two constant fields** to the feed's public topic after a publication commits, and which feed changed is the topic rather than the payload. A publisher receives no credential and has no field to put a topic in.
  - `FeedService.GetFeedTopics` states the topic, with `GATEWAY_PROBLEM_NO_PUSH` when a deployment relays nothing. The phone never derives a name, because a name derived twice drifts into silence rather than into an error — and an Android test reads the relay's Go source to keep the two literals in step.
  - On the phone nothing new was declared: one more exact-match invalidation on the existing service, one more empty-input job under `sync/`, one more Firebase-importing file, one more notification channel. The alert opens the feed it is on, because no screen lists a proposal until SEE-93 and SEE-94.
  - Nobody keeps a list of subscriptions: Firebase owns membership, the gateway is never told who joined, and the phone derives its own from the owner's connections — a stale topic unsubscribes itself when a hint arrives on it.
  - The real Firebase send is an opt-in test and **NOT RUN** here; the device run is the owner's (`docs/testing/stage-7-1.md`).
- SEE-91 fans the gateway out and makes the phone listen (`docs/wiki/broadcast-gateway.md#the-stream`, `docs/testing/stage-7-1.md`):
  - Centrifugo v6.9.6 over its **unidirectional gRPC** transport, with Redis 8 as the engine; both pinned where the deployment names them, and the client schema vendored with its digest.
  - A listener on that transport can send nothing after it connects, so it cannot subscribe itself: the channels come from a ticket the gateway mints (`FeedService.GetStreamTicket`). The ticket says which channels and nothing about who — an empty subject, an expiry, no identifier of any kind, and no record kept — and names no host, so the stream is one path on the gateway's own origin.
  - A publication carries `seekervault.gateway.v1.FeedEvent`: our envelope, validated on arrival by the same rules a read is validated by. An event of a kind the phone does not know sends it to the snapshot rather than being read as nothing.
  - Recovery happens once, at connect, from `(epoch, offset)`. `recovered: true` is the only proof of continuity; every other answer reads the authoritative snapshot, because the broker's history is a bounded cache and the documents are the gateway's. No buffer joins the two: both apply through SEE-89's revision-ordered idempotent path.
  - On the phone, `feeds/` is a new package with a new storage subpackage, the listener is foreground-only, and no background component was added. The broker is behind one file, pinned by `FeedBoundaryTest`.
  - Proven with services rather than asserted: `feeds/UniStreamInteropTest` (always runs) drives the real generated client over TLS and HTTP/2 against hand-built gRPC frames, and `feeds/CentrifugoStreamIntegrationTest` (opt-in) drives two real broker nodes and a real Redis. What is documented rather than hidden: the JSON history API cannot render binary payloads, and the broker's queue bound protects the broker rather than a slow phone.

- SEE-87 makes the Node sidecar's MCP interface one optional adapter over the request core (`docs/wiki/mcp-adapter.md`):
  - `MCP_ENABLED` is the switch and defaults to on, so an existing deployment keeps every setting and behaviour it has. Off, `/mcp` answers 404 and so do both OAuth metadata paths, and no MCP setting is required.
  - A leftover `MCP_TOKEN`, `MCP_ALLOWED_HOSTS` or `MCP_DEMO_TOOLS` is ignored and named in the startup log; `MCP_OAUTH_*` is refused, because the profile would advertise authorization for an endpoint the deployment does not serve. A broken switch value leaves the adapter on.
  - `sidecar/src/requests/agent-api.ts` is the whole of what an adapter may ask the core for. It forwards and decides nothing: idempotency, validation, the lifecycle, the pending limit and result handling stay in the store, so agent-facing tool names, contracts, error codes and result delivery are unchanged.
  - It authenticates nobody and holds nothing. `/mcp`'s token and OAuth checks stay in `mcp-endpoint.ts`; the phone credential still reaches `RequestService` and nothing else.
  - Pairing, stored request identity, the phone API, production updates, push, `/healthz`, startup and shutdown are identical in both modes. Nothing is loaded or accepted at runtime.
  - The distinction the stage needs: this sidecar is the owner's private server, and the Go publisher templates (SEE-95, SEE-96) are a developer's broadcast servers that speak no MCP.

- SEE-86 prepares the existing core for bundled client plugins and a later SDK extraction (`docs/wiki/client-plugins.md`):
  - A plugin owns three things — the parameters an operation leaves to the owner, where the execution data comes from and the exact bytes that would be signed, and what those bytes establish when read back. Presentation, approval and the wallet stay in core.
  - What a plugin is handed is exhaustive: the connection ID, the operation, the environment, the structured request, and the owner's selected wallet as a public address and network. No credential, no wallet authorization token, no transport handle, and no way to approve or send.
  - Operations are named at the protocol's own level (`swap`), so no provider's name appears in core transport, policy, transaction or activity code.
  - An operation no plugin serves, one with nothing prepared, and one whose bytes couldn't be read all establish nothing and can never be ALLOWED. Rules written for one thing are not inherited by an operation they were never applied to.
  - `PluginRegistry.bundled()` is the build-time selection and is empty: the boundary lands before anything is written against it, so a swap behaves exactly as it did. SEE-93 and SEE-94 add to that one list.
  - Nothing is downloaded and there is no dynamic load path. No storage format, proto or screen changed, so the app starts on the same persisted data.

Later stages (see `RFC.md` §3–6):

- **Agent → sidecar (MCP):** agents call `vault_*` MCP tools (`get_address`, `get_capabilities`, `sign_message`, `transfer`, `swap`, `get_request`). The sidecar persists an *action request* (not a prebuilt transaction) and immediately returns `request_id` + pending; retries must not create duplicate payments.
- **Phone → sidecar (Connect API, unary):** the Android app pairs via QR code (server address + one-time token), then calls `Pair`, `ListPending`/`GetRequest`, `PrepareRequest`, `SubmitResult`. Pending requests are fetched on app open/refresh; there's no push or persistent stream.
- **Transaction prep:** the sidecar builds a fresh unsigned transaction at review time (blockhash expiry); swaps use Jupiter `/build`. Approval is bound to a specific `PreparedTransaction` version.
- **Policy:** policies live and are enforced only on the phone, per connection. The phone parses the actual transaction and produces a `PolicyEvaluation` of `ALLOWED` or `UNDER_RESTRICTIONS`; unrecognized contents are marked unverified. Manual approval is always required.
- **Signing:** the phone invokes MWA `signAndSendTransactions` from an Activity; Seed Vault Wallet signs and sends. The result returns to the sidecar and then to the agent. On-chain confirmation is checked separately from MWA's submission response.
- **Contract:** `proto/` is the single source of truth, and both `sidecar/` and `android/` consume generated code.
- **Deployment:** `docker compose up` in `gateway/` runs the sidecar (persistent storage on a volume) and the gateway, both built from the checkout, as plain HTTP on a loopback address. Adding `-f compose.public.yaml` is the internet-facing configuration: HTTPS on the operator's own domain, with a narrower set of public endpoints. Adding `-f compose.oauth.yaml` as well turns on the optional OAuth profile, so a hosted MCP client authorizes a person at the operator's own authorization server instead of carrying `MCP_TOKEN` (SAW-036). The test agent is in the `agent` profile and does not start with the stack. See `docs/guides/self-hosting.md` and `docs/integrations/claude.md`. `render.yaml` and `deploy/render/` run the same sidecar behind a Caddy gateway in one container on Render, with Render terminating HTTPS (`deploy/render/README.md`). `deploy/server/` runs the sidecar alone on its own TLS listener behind a raw TCP forward (Tailscale Funnel `--tcp`), which is the only layout that carries the phone's live update stream (`deploy/server/README.md`).
