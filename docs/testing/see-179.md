## What the deployment serves (before the fix)

The deployed gateway (`https://seeker-gateway-sg8g3.ondigitalocean.app`, `gateway-0.2.3`) answers
`GetServerManifest` and `ListRecommendedFeeds` for both demo feeds with `settingsRevision "1"` and
**no `supportedNetworks`**:

| Feed | Server ID | Revision | `feed.supportedNetworks` |
| --- | --- | --- | --- |
| CopyTrading (Signals demo, sandbox) | `b1ffc4d0-f20f-4f31-875b-4a0e0c9694ef` | 1 | absent |
| Polymarket (Prediction demo, production) | `e8d74180-b796-4570-9230-d0e888f6927d` | 1 | absent |

An absent list is "no networks declared" on the phone (`docs/wiki/server-manifests.md`). That is
where the app's "No network declared" text comes from. It is the stored manifest's
`supportedNetworks`, which also drives the wallet picker filter and the signing gate
(`ConnectionWallet.compatibleProfiles`, `WalletRepository.bind`/`walletReadiness`).

## Root cause

The demos do declare their network. Both images (`copytrading-0.2.1` and `prediction-0.2.1`,
OCI revision `6d306cf`) contain SEE-174. The binary reads `PUBLISHER_SUPPORTED_NETWORKS`, and the
App Platform environment for these demos leaves it unset, which `config.LoadTemplate` turns into the
template's own `[mainnet]`. A local probe with the deployed environment returned
`networks: [mainnet]`. The manifest they built was lost on the way to the gateway:

1. **2026-09-29 20:40 UTC.** Both demo apps and the gateway were redeployed at once. The gateway's
   new `gateway-0.2.1` deployment ran its deploy step from 20:40:15 to 20:40:44. The previous
   `gateway-0.2.0` (revision `64b55ab`, **before SEE-174**) was superseded at 20:41:07.
2. The demos keep `PUBLISHER_DATABASE_PATH` under `/data`, which App Platform does not persist.
   They started with an empty database, at manifest revision 1, now carrying `[mainnet]`. The
   Prediction log shows `markets: 0` and every market republished at generation 1.
3. They published at 20:40:26 (Prediction) and 20:40:31 (Signals), to the **old** gateway. Its
   `rules.Manifest` rebuilds the feed reference field by field and did not know
   `supported_networks`, so the document it compared was identical to the revision 1 it already
   held. It answered `UNCHANGED`, and both logs say `"the manifest is published","revision":1,
   "status":"unchanged"`.
4. The publishers recorded revision 1 as confirmed and never sent it again. The new gateways
   (0.2.1, 0.2.2, 0.2.3) kept serving the held revision 1, with no networks.

**And it could not recover by restarting**, which is the implementation defect fixed here. A
restarted demo starts again at revision 1 with `[mainnet]`, and the current gateway refuses it
with `revision_conflict` (held revision 1). `publisher-support` treated that as permanent and
stopped. The gateway names the revision it holds in `GatewayErrorDetail.held_revision`; the
protocol comment says this exists for "a publisher that lost its own state — a template that was
redeployed". `publisher-support` never read it, so the documented recovery ("read it, decide,
republish higher", `docs/guides/server-development.md`) was not implemented. On App Platform, with
no volume, every redeploy is at revision 1, so no settings change could ever reach the gateway.

The Android path was traced and is not at fault. `ManifestValidation` reads
`feed.supported_networks`. A higher revision reaches an existing connection through the feed
stream's manifest event (`ForegroundFeedManager` → `applySettings`) or the snapshot read
(`refreshSettings`), and both replace the stored manifest. Discover reads the catalog's own
`supported_networks`.

## The fix

`packages/publisher-support`:

- `gateway.Refusal.Held` carries `held_revision`.
- `publish.Drainer.PassManifest` handles `stale_revision` and `revision_conflict` that name a held
  revision. It republishes at the held revision, which the gateway answers `unchanged` when it
  already holds these settings, and then, if the gateway holds something else, at the next
  revision. It tries at most twice and then records the refusal as before. Other refusals
  (`other_environment`, a `mode` conflict, …) are unchanged.
- `store.ManifestCatchUp` moves the stored revision forward only.
- `store.ManifestRevision`, called once per start, now also clears the confirmation, so a start
  sends the manifest again, as its own doc comment already said it did. A volume-backed deployment
  can then recover by restarting too.

## Signals and Devnet

The ticket expects Signals on Devnet. That is **not possible without mislabeling**. The Signals
demo is the CopyTrading template, whose only operation is `jupiter.swap`, and Jupiter swaps
execute only on Solana Mainnet. `examples/demo-signals/cmd/copytrading/main.go` fixes the template
to `[mainnet]`, and `config.LoadTemplate` refuses `PUBLISHER_SUPPORTED_NETWORKS=devnet` at
startup. The demo's `sandbox` environment is not Devnet: the phone simulates against Mainnet data
and signs nothing (`docs/wiki/environments.md`). After the fix, Signals shows **Mainnet**. A
Devnet feed would need a template with an operation that runs on Devnet.

## Deployment (to be run by the operator; NOT RUN here)

The DigitalOcean specs live in the `do-deploy` repository, and nothing was deployed from this
branch.

1. Build and push demo images from this branch, or from `master` once merged, through the
   release workflow, and point both App Platform demo apps at them. No environment change is
   required. Optionally add `PUBLISHER_SUPPORTED_NETWORKS=mainnet` to both demo components to make
   the declaration explicit. Do **not** set `devnet` on Signals: the demo refuses to start.
2. Deploy the demos **after** the gateway's rollout has finished. The gateway is already at
   `gateway-0.2.3`, which supports the field.
3. On start, each demo logs `the gateway holds another revision of the manifest; catching up with
   it`, then `"the manifest is published","revision":2,"status":"stored"`.
4. Check:

   ```sh
   for s in b1ffc4d0-f20f-4f31-875b-4a0e0c9694ef e8d74180-b796-4570-9230-d0e888f6927d; do
     curl -sS -X POST https://seeker-gateway-sg8g3.ondigitalocean.app/seekervault.gateway.v1.FeedService/GetServerManifest \
       -H 'Content-Type: application/json' -d "{\"serverId\":\"$s\"}"; echo
   done
   ```

   Each answer must show `"settingsRevision":"2"` and
   `"supportedNetworks":["SOLANA_NETWORK_MAINNET"]`.
5. Phones: existing connections need no reconnecting. Open the app; the stream or the next snapshot
   delivers revision 2, and the connection shows Mainnet and offers Mainnet wallet profiles. A
   newly added feed reads revision 2 directly. If a phone still shows no network after it has been
   open with the feed's stream connected, remove and re-add the feed. The manual refresh on a
   feed's detail sheet re-reads proposals, not the manifest.

**NOT RUN:** the redeploy itself and the on-device checks (new connection, existing connection,
wallet picker filtered to Mainnet). These need the demos redeployed and a device or emulator.
