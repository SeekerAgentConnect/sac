### Independence, proved by building each demo with the other absent

This is the Docker build context, reproduced on the filesystem: for each demo, a fresh directory
containing **only** `publisher-support/` and that demo — exactly what its `Dockerfile` copies in.

```sh
for demo in demo-copytrading demo-prediction; do
  mkdir -p /tmp/isolation/$demo
  cp -R publisher-support /tmp/isolation/$demo/publisher-support
  cp -R $demo            /tmp/isolation/$demo/$demo
  (cd /tmp/isolation/$demo/$demo && go build ./... && go vet ./... && go test ./...)
done
```

**PASS** for both.

```
demo-copytrading: builds, vets and tests with ONLY publisher-support beside it
  demo dir(s): demo-copytrading publisher-support
demo-prediction: builds, vets and tests with ONLY publisher-support beside it
  demo dir(s): demo-prediction publisher-support
```

Each tree contains exactly one `demo-*` directory, so neither build could have reached the other
demo even by accident.

### HTTP publication against the real feed gateway

Both opt-in tests start the real `feed-gateway` binary as a separate process with its own SQLite
database, register the publisher with the real `feed-gatewayctl`, and publish over the gateway's
documented authenticated Connect API.

```sh

cd demo-prediction   && SEEKERVAULT_FEED_GATEWAY=/tmp/feed-gateway go test ./internal/discovery/ -run Gateway -v
```

**PASS**, and they ran rather than skipped:

### Two independent sources, per-source isolation, and the privacy sweep

```sh
pnpm test:integration --no-android
```

**PASS** for both legs that could run:

```
Stage 7.1 integration (SEE-98)

  PASS    the cross-component run (gateway, both templates, two devices, the sidecar and the agent)
  PASS    the direct-mode acceptance suites, unchanged
  NOT RUN the stream, against the pinned broker — SEEKERVAULT_CENTRIFUGO is not set
  NOT RUN the phone's cross-component cases — --no-android
```

This run builds `copytrading` and `publishctl` from `demo-copytrading/` and `prediction` from
`demo-prediction/`, starts both as separate processes with separate databases and separate
credentials against one gateway, and attaches two independent readers. The cases that matter to this
ticket:

```
▶ what a phone reads from a feed
  ✔ is the same document on two devices, and a revision it holds is not sent again
  ✔ carries the publisher's terms, and nothing about any subscriber
▶ the transport
  ✔ serves the same documents after the gateway restarts on its own database
  ✔ republishes nothing when a publisher restarts and its settings stand
▶ mixed mode: the owner's own sidecar, while two feeds are live
  ✔ read both feeds while that happened, and told neither publisher anything
▶ the two environments
  ✔ published both deployments as sandbox, and say so in their own answers
  ✔ refuses to start a production deployment on a sandbox database
▶ privacy, over what this run actually wrote
  ✔ finds nothing about a subscriber in either publisher's files, or the gateway's
  ✔ finds all of it on the owner's own side, which is what proves the search works
```

"Republishes nothing when a publisher restarts and its settings stand" is the restart check: one
demo restarts, its identity, revisions and outbox state come back out of its own file, and nothing
is published again — so no subscriber is notified and the other source is untouched. The privacy
sweep reads **both publisher databases and the gateway's**, every write-ahead log beside them and
every process log, and finds nothing about a subscriber in any of them.

### Source, credential and data separation

| | CopyTrading | Prediction |
| --- | --- | --- |
| Module | `demo-copytrading/` | `demo-prediction/` |
| Image (local tag) | `seeker-publisher/copytrading:local` | `seeker-prediction/prediction:local` |
| Compose project | `seeker-publisher` | `seeker-prediction` |
| Volume | `publisher-data` | `prediction-data` |
| Database | `/data/publisher.db` | `/data/prediction.db` |
| Published port (default) | `127.0.0.1:8092` | `127.0.0.1:8094` |
| Publisher ID, gateway credential, API token | its own | its own |
| Secrets directory | `PUBLISHER_SECRETS_DIR`, its own | `PUBLISHER_SECRETS_DIR`, its own |

Nothing is shared at run time. In `deploy/server/`, where both may run beside each other, they keep
their existing separate volumes `copytrading-data` and `prediction-data` and their separate
databases `/data/copytrading.db` and `/data/prediction.db`.

Every project name, volume name and database path above is **unchanged** from before the split, so
an existing installation mounts the same data and finds the same publisher identity, revisions and
pending publications. No identity is regenerated because a directory changed. `deploy/server` reads
`COPYTRADING_IMAGE` and falls back to the old `PUBLISHER_IMAGE`, so a pre-SEE-134 `.env` keeps
working, and adds `PREDICTION_IMAGE`.

## What was deliberately not done

- **No gateway-private routing was restored.** Devices subscribe to the public gateway; neither demo
  stores a subscriber identity or receives any owner input, decision, signature or outcome.
- **No portable deployment redesign.** `deploy/server/` was made *true* again — the two Dockerfile
  paths, the two image variables, the two repointed Caddyfile symlinks — and nothing about its
  structure changed. Separating portable orchestration from ingress is SEE-135's.
- **No final documentation reconciliation.** That is SEE-136's.
- **No `feed-publisher-client` package and no new service.** `publisher-support` is a source library
  with no command, no image, no listener and no deployment, and its `gateway` package is an ordinary
  authenticated HTTP/Connect call any HTTP client in any language could make.

## Known limitations

- Image builds and any `docker compose up` step in either guide are unverified on this machine; see
  the follow-up above.
- The live-provider and physical-device checks remain opt-in and unrun, as in the preceding tickets.
- `docs/testing/stage-7-1.md` keeps the paths that existed when it was written, with a note at the
  top saying where each moved. A record that claimed different commands had been run would not be a
  record.

## Handoff

SEE-135 owns separating portable orchestration from optional ingress and host-specific
configuration. It must not reset a volume, make a demo or the MCP server mandatory, move SQLite onto
a network, or keep mandatory network-namespace sharing. The volume, project and database identities
listed above are the ones it has to preserve.
