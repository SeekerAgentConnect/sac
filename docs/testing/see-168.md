### `latest` on a first publish

npm set `latest` to the release candidate on each package's first publish, whatever `--tag next`
asked for, and it refuses to remove a `latest` tag afterwards:

```
$ npm dist-tag rm @seeker_agent_connect/mcp-server latest
npm error code E403
npm error 403 Forbidden - DELETE .../dist-tags/latest
```

This is npm's behaviour for a package that has no versions, not a defect in the release plan: there
was no stable `latest` for a prerelease to advance. Every subsequent release obeys the rule, and
the release workflow now reads `latest` before and after a prerelease publish and fails if it
moved. Documented in `docs/development/releases.md`.

## Acceptance criteria

### 1. A fresh external project installs the SDK and runs a minimal example — PASS

In `/tmp/…/external-verify/sdk`, outside the checkout, with an empty npmrc (no credential) and a
private cache:

```
npm install @seeker_agent_connect/server-sdk@0.2.0-rc.1 typescript@6.0.3 @types/node@24.13.4
```

- The repository's own documented consumer example, `packages/server-sdk/examples/minimal.ts`,
  copied in verbatim, **type-checks** against the published declarations (`tsc --noEmit`, `strict`,
  `verbatimModuleSyntax`, `module: nodenext`).
- A variant that completes without a paired phone **runs**:
  `{"pairingUri":true,"serverId":true,"preparedIdempotencyKey":"external-1","phoneApiStarted":true}`,
  exit 0. It opened SQLite, served the phone API, issued a real `seekervault://pair` URI and shut
  both down.
- Nothing in the installed tree contains a `workspace:` specifier or a path from this machine.

The declarations were also shown to be load-bearing: an earlier example that invented option names
was rejected by `tsc` with four errors, which is the behaviour a consumer needs.

### 2. Each MCP npm artifact starts from a clean installed package — PASS

From the registry, not from a tarball on disk:

```
npm exec --package=@seeker_agent_connect/mcp-server@0.2.0-rc.1 -- seeker-agent-connect-mcp --help
npm exec --package=@seeker_agent_connect/mcp-skr-staking@0.2.0-rc.1 -- seeker-skr-staking-mcp --version
```

Both print their own version. A registry-installed `mcp-server` was then started against a
throwaway data directory on `127.0.0.1:18080`:

- `GET /healthz` → **200**
- `pair` → a real `seekervault://pair?v=1&url=…&server=…&token=…`
- MCP `initialize` over Streamable HTTP at `/mcp` with the bearer token → a `serverInfo` result
- `SIGTERM` → clean exit, and `direct-server.db`, `…-owner.sqlite` and `…lock` left in the data
  directory

The exhaustive per-artifact audits run in CI and are stronger than this: `pnpm test:server-sdk-package`,
`pnpm test:mcp-server-package` and `pnpm test:skr-staking-package` pack the exact tarball, compare
dry-run and real file lists, audit the published manifest, install outside the workspace both
locally and global-style, and drive pairing, MCP discovery, a phone round trip, restart persistence
and duplicate-store refusal. All three pass.

### 3. Docker artifacts build and run outside the checkout — NOT RUN

No Docker daemon on this host (see the access table). What was done instead:

- Every released image gained `org.opencontainers.image.{title,description,source,url,documentation,licenses,vendor,version,revision}`,
  with `VERSION`/`REVISION` as build args the release workflow fills from the tag and the commit.
- `pnpm check:release` asserts each released Dockerfile carries the source, revision and version
  labels, that its declared platforms are exactly `linux/amd64` and `linux/arm64`, and that the
  Dockerfile it names exists.
- Ports, volumes, environment, health and shutdown for all six images are documented in
  `docs/guides/installation.md`, including why the three `scratch` Go images carry no
  `HEALTHCHECK` (no shell, no shipped probe) and are probed over HTTP instead.

CI already builds both demo images on every run, and the release workflow builds all six for both
platforms. Neither has been executed for this branch.

### 4. A release-candidate pipeline proves publication — PARTIAL

**npm: proven.** Published, public, installed and executed from the registry by an unauthenticated
consumer, as above.

**GHCR: blocked**, on account setup that cannot be done from a workflow or from here:

1. The repository secret `GHCR_TOKEN` does not exist. It must be a **classic** PAT with
   `write:packages`, held by a member of the SeekerAgentConnect organisation. A fine-grained PAT
   cannot write GHCR, and this repository's `GITHUB_TOKEN` cannot write another owner's namespace.
2. After the first push, each package must be made **public** by hand — a package created from a
   private repository is private, and `BrRenat/SeekerAgentConnect` is private.
3. Each package should be linked to the repository in the same settings page.

The workflow fails immediately, with that explanation, when the secret is absent, rather than part
way through a build. Steps are in `docs/development/releases.md` § GHCR access.

### 5. Version, dist-tag and revision consistency — PASS (npm), pending for images

One version per component in `release/components.json` names both artifacts, and
`pnpm check:release` proves the npm manifests, the in-source `VERSION` constants and that file
agree. `scripts/release-plan.test.mjs` (10 tests) covers the tag rules: a stable release gets
`latest` and `:latest`, a candidate gets `next` and no `:latest`, a development build gets only
`sha-<commit>` and `develop`, a hyphenated identifier survives the tag, and a tag that disagrees
with the manifest stops the release.

### 6. No credentials or unintended local data in the artifacts — PASS

The three audits assert the packed file list contains only `LICENSE`, `README.md`, `package.json`
and `dist/**`; no `src`, test, testing or fixture path; no `.ts` (other than declarations), `.map`,
`.db`, `.env` or `.tgz`; no `workspace:`, `catalog:`, `file:` or `link:` specifier in the published
manifest; and no absolute path from the building machine in any packed text file. The images embed
no credential and no deployment host — the gateway deliberately has no default for
`BROADCAST_PUBLIC_URL` or for its store, so it refuses to start half-configured.

**One real defect was found and fixed here.** `servers/mcp-skr-staking` kept `@connectrpc/connect`
and `@connectrpc/connect-node` as dev dependencies. That resolved inside the workspace, but its
build vendors the SDK, whose runtime needs both — so the published package would have failed on its
first `npx`. They are runtime dependencies now, and the staging step refuses to stage a manifest
that omits anything the vendored SDK needs.

### 7. Installation and deployment docs — PASS

`docs/guides/installation.md`: `npm install`, both `npx` invocations, `docker run`, the existing
Compose presets driven by their image variables, a complete checkout-free Compose file, pinning and
rollback by exact version and by digest, and a table mapping every previous Docker Hub tag to its
GHCR replacement with the note that volumes, ports, variables and uid are unchanged.

### 8. Registry links, digests and results in the report — PARTIAL

npm links are above. **Image digests do not exist yet**, because nothing has been pushed. The
release workflow writes the image reference, the pushed tags and the digest into its run summary,
which is where they will come from.
