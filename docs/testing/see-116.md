# SEE-116 — design-guide agent and refresh workflow

This record covers the instruction boundary that makes component implementation repeatable and
keeps design changes flowing from the guide into code. The generated export was not changed by
SEE-116.

## Documented contract

| Acceptance | Evidence |
| --- | --- |
| One component can be implemented from the guide and its folder | `design/README.md` fixes the read order as `spec.md` → variant HTML → variant PNG → `tokens.json`, defines units and scale, pins the component API, and gives the record/compare/inspect loop. |
| Design changes use one path | `design/UPDATING.md` records the ticket's nine steps from editing and exporting all three pages through separate follow-up tasks and final consistency checks. |
| Component specs have one shape | `design/components/_template/spec.md` requires purpose, tier, Compose name/signature, enums derived from `data-variant`, allowed child components, builder notes, generated references, and open questions. |
| Token gaps cannot be hidden by generic dimensions | The guide deprecates `Dimensions.kt`'s pass-through `dpN` block for production `:designsystem` components, requires named tokens to match `tokens.json`, and tells agents to report a missing token rather than invent one. The implementation test result is recorded below. |
| Agents load the instructions | `CLAUDE.md` sends every Android UI task to `design/README.md` and every guide refresh to `design/UPDATING.md`. |
