# SEE-177 — prediction demo: one entry per event, keyword/category coverage, no Retry

## Where the duplicates came from

Provider listing → `discovery.Reconciler.collect` → `Pass` → store → drainer → gateway → phone.
`collect` already returned one candidate per *market*, and `Pass` applied `PREDICTION_MOST_OPEN` to
markets, so the three outcome markets of `POLY-798787` (`POLY-3350393`, `POLY-3350396`,
`POLY-3350399`) became three proposals. The gateway and the app render each proposal they receive
and do no grouping of their own, so the fix is at the source: `internal/discovery/select.go` groups
candidates by venue + event before the ceiling is applied, and the reconciler withdraws any second
open proposal for one event. A withdrawal moves a proposal to the phone's History as "Cancelled by the
publisher"; an executed record, its Activity entry and any position stay as they were
(`ProposalState.proposalStanding` checks execution first; `PositionTracker.purchasesOf` reads only the
execution), so no app change was needed.

**Actual topic availability.** Polymarket currently lists no open crypto or tech event mentioning
"seeker", "solana mobile" or "artificial intelligence" that closes between 24 hours and 180 days out
within the four pages per bucket; those three buckets stay uncovered with that reason rather than
being filled with something else. The other seven are covered by eight distinct events. 578 eligible
markets collapse to 149 events; before this change the ceiling applied to markets in close-time
order, so sibling outcomes of one event could take several of the eight slots, as in the reported
screenshot (the old code was not run live for comparison). Zcash has exactly one
eligible event. `POLY-798787` itself closed at the end of September and is no longer listed, so the
live run cannot show it; the fixtures above reproduce it.

A rate-limited run a minute earlier read 3 of 8 pages and recorded `partial`, with every bucket it
had not reached reported `walk_incomplete` rather than `no_eligible_candidate`.
