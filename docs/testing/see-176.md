## Gateway end to end, as real processes

`feed-gateway` and `feed-gatewayctl` built from this branch, one SQLite file, the gateway on
`127.0.0.1:18080`/`:18081`, manifests published with `curl` over the publisher API. Log:

1. `register` A public + `--recommend yes --description …` (with an operator label and host), B
   restricted + listed, C described but not listed, D listed with no manifest; E relay-only with
   `--recommend yes` → **refused** ("a server that does not publish has nothing to recommend").
2. A, B and C publish manifests. `ListRecommendedFeeds` → **exactly A (Public) and B (Restricted,
   with its auth origin)**; C (unlisted), D (no manifest) and E (relay-only) absent.
3. `pageSize: 1` → A with a token; the token → B, no further token. `pageSize: 101` →
   `invalid_argument` `bad_page_size`.
4. `feed-gatewayctl listing --server A --recommend no` and a new description for B **while the
   gateway runs** → the next read has only B, with the new description (no restart, no cache).
5. B republishes at revision 2 under a new name → still listed, same description, new name and
   revision.
6. B's `ListRequests` without a session → `permission_denied` `access_required`: listing opened
   nothing. A's `GetServerManifest` after unlisting → still served.
7. The catalog body never contains the operator's label or host.

## Acceptance criteria

1. **Register or edit with Show in app recommendations and a description; survives restart in both
   backends — COVERED.** `sqlite/listing_test.go` `TestAListingIsTheOperatorsAndSurvivesARestart`,
   `postgres/listing_test.go` (same name, run against Postgres), `admin/listing_test.go`
   `TestRegisteringAListedFeedThroughTheUI`, `TestEditingAListingExplainsWhatIsMissingAndMovesNothingElse`,
   `feed-gatewayctl/listing_test.go`; E2E steps 1 and 4.
2. **Existing registrations migrate to unlisted; listing changes nothing about access or
   subscriptions — COVERED.** `TestTheListingColumnsMigrateEveryRegistrationToUnlisted` (SQLite v7 → v8
   and Postgres v3 → v4, access epoch unchanged), `catalog_test.go`
   `TestListingAndAccessAreSeparateAndNeitherIsResetByARepublication`; E2E steps 5 and 6.
3. **The API includes eligible Public and Restricted feeds and excludes unlisted, disabled-publishing,
   relay-only, missing-manifest and incomplete ones — COVERED.** `TestTheCatalogIsEveryCompleteListingAndNothingElse`,
   `TestAnOfflinePublisherStaysInTheCatalog`; E2E step 2.
4. **A fresh app with zero connections loads Discover and shows names, descriptions and access types
   — COVERED.** `DiscoverActivityTest.aFreshInstallBrowsesTheCatalogAndConnectsAPublicFeedThroughAddConnection`
   (nothing is read before the tab is shown).
5. **Loading, empty, failure/retry, refresh, pagination and back navigation — COVERED.**
   `DiscoverViewModelTest` (all nine cases), `AppNavigationTest.discoverIsAPeerTabAndEverythingOpenedFromItReturnsToIt`,
   `discoverRoutesSurviveASaveAndRestore`; the list's scroll state is hoisted in `SeekerVaultApp`.
6. **A Public feed connects through existing onboarding and wallet/network selection and reflects its
   state at once — COVERED.** `DiscoverActivityTest` (confirmation prefilled, nothing stored before
   **Add feed**, manifest read over real HTTP, wallet picker on the new connection's sheet over
   Discover, then the card reads **Connected · Open**). Network filtering is SEE-174's unchanged
   picker (`ConnectionWalletTest`, `WalletRepositoryTest`).
7. **A Restricted feed can be requested, stays pending across restart, then connects after approval;
   immediate approval also works — PARTIAL.** Discover starts the existing flow
   (`DiscoverActivityTest.aRestrictedFeedIsAddedFromDiscoverAndShownByItsAccessStateNeverAsConnected`)
   and shows each persisted state (`CatalogStandingTest.aRestrictedFeedShowsItsPersistedAccessStateAndIsConnectedOnlyWhenAdmitted`).
   Pending across restart, delayed and immediate approval are `FeedAccessManager`'s existing,
   unchanged behaviour: `FeedAccessStoreTest.theWholeStateMachineSurvivesTheRoundTrip`,
   `FeedAccessManagerTest.theSessionComesBackAfterARestart` and
   `anApprovedDeviceRedeemsItsInvitationAndConnects`. **Gap:** no test drives a whole restricted request
   from a Discover tap through a wallet signature to approval; that needs the device run below.
8. **Rejection, revocation/expiry, cancelled signing and retryable failure never grant access —
   COVERED** for the Discover side: `CatalogStandingTest` (Rejected, Revoked, Expired, no record
   after a cancelled signature, request in flight), and the activity test's cancelled wallet choice
   leaves "Access not requested yet". The refusals themselves are `FeedAccessManagerTest`'s.
9. **Already-connected feeds open their connection; repeat taps don't duplicate — COVERED.**
   `CatalogStandingTest.aPublicFeedAlreadyHeldIsConnectedAndOpensItsConnection`,
   `aHeldFeedIsFoundByTheRepositorysOwnDuplicateRule`, `aFeedBeingAddedCannotBeStartedTwice`;
   `DiscoverActivityTest` (second tap opens, still one connection); `openCatalogConnect` refuses from
   anywhere but the bare tab.
10. **Stale access policy is revalidated; Restricted content stays inaccessible without a grant —
    COVERED.** Adding always reads the manifest (`ConnectionRepository.addFeed`, unchanged); a card's
    reference keeps the restricted floor (`CatalogFeedTest.aCardsReferenceReadsBackThroughTheOrdinaryParser`);
    a held feed's restriction comes from its own manifest, not the card; gateway
    `TestTheCatalogIsEveryCompleteListingAndNothingElse` reads the listed restricted feed and is
    refused on every path; E2E step 6.
11. **No admin secrets, subscriber data, invitations, private content or presence in responses —
    COVERED.** `TestTheCatalogCarriesNoOperatorOrReaderData`, the pinned field list in
    `TestTheContractIsBoundedAndSaysNothingAboutAnyone`, `ConnectFeedCatalogTest` (the phone sends
    only a page size and token); E2E step 7.
12. **Manual links, direct connections and notification batching keep working — COVERED** by the
    unchanged suites that pass (`ConnectionsViewModelTest`, `AddConnectionRouteTest`,
    `FeedReferenceTest`, the SEE-175 notification suites). A feed added from Discover is an ordinary
    new connection, so its first snapshot is its silent backlog.
