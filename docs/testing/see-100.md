# SEE-100 — the server development guide, walked

[`docs/guides/server-development.md`](../guides/server-development.md) is a set of instructions, so
the only honest way to publish it is to follow it and write down what happened. This is that record:
every step, the command that was actually run, what it answered, and **PASS**, **FAIL** or
**NOT RUN**. A step marked NOT RUN says what would have to exist to run it.

Nothing here spent money, touched a wallet, sent a real push notification to anybody's device, or
loaded a public API beyond one listing walk.

## The revision tested

The SEE-100 commit on `superset/feat/see-85`, on top of `0f95c3a` (SEE-99's report). The five
binaries were built from that tree with `go build`:

| Component | Where it came from |
| --- | --- |
| `broadcast`, `broadcastctl` | `broadcast/cmd/…` at this revision |
| `copytrading`, `prediction`, `publishctl` | `publisher/cmd/…` at this revision |

| Redis | **8.2.10**, built from the release tarball |
| Node / pnpm | 24.21.0 / 12.3.4 |
| Provider | `https://lite-api.jup.ag`, the keyless host, for one discovery cycle |

**Everything ran as native processes rather than in containers**, because there is no Docker daemon
available to this account (the same limitation `docs/testing/stage-7.md` and
`docs/wiki/broadcast-gateway.md` record). So the guide's Compose commands are NOT RUN here and the
same deployment was assembled by hand from the same configuration: the gateway with its own
environment, the broker on the shipped configuration file with only its two secrets and the Redis
address given to it, and real Redis behind it. What is therefore **not** covered is the proxy hop,
TLS, and the container hardening — named, rather than folded into a pass.

The topology: Redis on `7379`, the broker on `8100` (API) and `11100` (unidirectional gRPC), the
gateway on `8190` (reads) and `8191` (publications), the CopyTrading template's API on `8092`, the
Prediction template's on `8094`, and a controlled push endpoint on `8195`. The guide uses the
documented defaults (`8090`/`8091`) instead, which is what a reader following it will have.

## The three answers worth keeping

**What `register` prints** (step 3). The 43-character secret is redacted here to its shape; it was
shown once and is not in the database — `broadcastctl`'s own test asserts that:

```
publisher   b3f491be-5a91-48a6-964d-d13171a9cc7b
channel     server/b3f491be-5a91-48a6-964d-d13171a9cc7b
credential  120ec2d5

xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

That credential is shown once and is not stored. Give it to the publisher as BROADCAST_CREDENTIAL,
and keep it out of version control. Rotate with `rotate`, then `revoke --credential <id>`.
```

**What the relay actually sent** (step 25), captured at a loopback endpoint the operator named — the
same loopback allowance the credential's `token_uri` makes for development, which is why this could
be observed without mocking the relay:

```json
{ "message": { "topic": "feed.sandbox.b3f491be-5a91-48a6-964d-d13171a9cc7b",
               "data": { "kind": "feed_invalidation", "version": "1" },
               "android": { "collapse_key": "seeker-vault-feed-invalidation-v1",
                            "priority": "HIGH", "ttl": "300s" } } }
```

Two constant fields, and nothing else. No proposal, no revision, no sequence, no publisher, and
nothing about a subscriber. One token exchange happened, at the `token_uri` in the credential, and
nothing was ever addressed to a device rather than a topic.

**Two phones, one document** (step 19). Two listeners on the transport the app listens on, each with
its own ticket and its own connection, then one publication:

```
phone 2: stream opened on feed:server/b3f491be-5a91-48a6-964d-d13171a9cc7b
phone 1: stream opened on feed:server/b3f491be-5a91-48a6-964d-d13171a9cc7b
phone 1: 34438448 revision 1, open (offset 7)
phone 2: 34438448 revision 1, open (offset 7)
```

Then, with both still attached, `SIGTERM` to the broker (step 20):

```
phone 1: stream closed 3001 shutdown
phone 2: stream closed 3001 shutdown
```

`3001` is the code the app's own recovery policy treats as reconnect-and-recover, and the client
used here is the load harness's listener, which is a port of the app's policy rather than a second
opinion about it (`loadtest/internal/listen/policy.go`).

## The one thing that blocks every device step

**This build of the app has no way for an owner to add a feed.** Everything after that point is
implemented and exercised: `ConnectionRepository.addFeed` resolves a manifest through the live
`ConnectFeedGateway`, and the snapshot, the stream, the signals list, the review, the execution, the
record, the environment switch and the notification tap route are all there and all covered by the
suites `pnpm test:integration` runs. What is missing is the screen: nothing in the
Add-connection flow calls `addFeed`, and `AndroidManifest.xml` declares no deep link for
`seekervault://feed`, so a feed reaches a phone only from a test.

That is why every row of the checklist below is NOT RUN rather than untested — the first step cannot
be taken. It is an app-side gap, on the phone's side of the boundary this ticket documents: the
gateway mints tickets, the templates print references, and `docs/testing/stage-7-1.md`'s device
runbook and [`docs/testing/see-98.md`](see-98.md#the-device-checklist-for-the-owner)'s checklist both
already assume a screen that does not exist. No child of SEE-85 owns it.

## What is not here

- **The Compose deployment, TLS, and the proxy hop.** No Docker daemon on this machine. The compose
  files and both Caddyfiles are validated without one (`docker compose config`, `caddy validate`) as
  `docs/testing/stage-7.md` records; nothing here revalidates them.
- **A real push delivery.** The relay's own behaviour is measured — the topic it derives, the body it
  sends, the token it exchanges, the fact that nothing is addressed to a device — and Firebase's part
  and a phone's part are not.
- **A production publisher.** Everything here is sandbox, which is what both `.env` examples ship as.
- **Load and failover at size.** [`docs/testing/see-99.md`](see-99.md) is that, on the same stack.
- **Anything that needed a feed on a phone.** See above: the first step of every device row cannot
  be taken in this build.
- **A second opinion about the app's own behaviour.** The states a phone resolves a manifest to are
  covered by its own suites; what this record proves is what a publisher can observe from outside.
