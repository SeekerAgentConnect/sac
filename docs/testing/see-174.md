## Acceptance criteria

### 1. A/Mainnet, A/Devnet and B/Mainnet persist and stay distinguishable after restart — COVERED

- `wallet/WalletRepositoryTest`: `keepsTheSameAddressOnTwoNetworksAndAnotherAddressApartAfterARestart`
  saves the three profiles, reopens the store, and checks each keeps its own ID, network and sealed
  authorization. `theSameAccountInAnotherWalletAppIsAnotherProfile` and
  `reconnectingTheSameAccountRefreshesItsProfileInsteadOfDuplicatingIt` pin the deduplication key
  (wallet package, address, network).
- `wallet/storage/WalletStoreTest`: `keepsEveryProfileAndTheAuthorizationsTheyShareAsOneSealedRecord`,
  `anUnreadableProfilesRecordIsNoProfiles`.
- `wallet/WalletViewModelTest`: `theSameAddressOnAnotherNetworkIsASecondProfile`.
- `wallet/WalletScreenTest`: `showsEachProfileWithItsNetworkAndWalletAppApartFromTheAccountLabel`,
  `marksTheNetworkTheOwnerIsAddingOn`.

### 2. Only profiles on the server's declared networks are offered; no match adds one and resumes — PARTIAL

- Binding is refused for a network the server did not declare, and allowed for one it did:
  `wallet/WalletRepositoryTest` `onlyProfilesOnADeclaredNetworkCanBeBound`;
  `wallet/WalletViewModelTest` `refusesAProfileOnANetworkTheServerDoesNotDeclare`.
- The setup flow opens for a newly added connection and does not offer earlier additions as its
  own: `wallet/WalletViewModelTest` `aNewConnectionChoosesItsWalletNext`; the activity-level
  picker is driven by `WalletActivityTest` `choosesTheWalletOnTheConnectionsOwnSheetAndTellsOnlyItsServer`.
- **Gap:** the picker's list filter itself (`compatibleProfiles` in
  `connections/ConnectionWallet.kt`) and the "Add wallet for &lt;network&gt;" prefilled path back
  into the same setup have no dedicated unit test. They reuse the same network check the binding
  tests pin, but the list offered for a Mainnet-only versus a multi-network server is not asserted
  directly.

### 3. Direct server X uses A/Devnet while Y uses B/Mainnet; each address query returns its own — COVERED

- `wallet/WalletRepositoryTest` `eachPairedServersAddressQueryAnswersItsOwnBinding` runs over the
  real `ConnectionRepository` and two fake sidecars: X holds A/Devnet, Y holds B/Mainnet, the
  binding survives a restart, and no authorization token reaches either server.
- `wallet/WalletRepositoryTest` `twoDirectServersEachHearOnlyTheirOwnBinding`;
  `wallet/WalletViewModelTest` `givesTwoConnectionsTheirOwnProfilesOnTheirOwnNetworks` and
  `bindsADirectConnectionAndTellsOnlyItsOwnServer`.
- The server side of the address query is unchanged by SEE-174 (one binding per connection).

### 4. A feed bound to B/Mainnet prepares, reviews and signs with B — COVERED

- `wallet/WalletRepositoryTest` `signsWithTheConnectionsOwnProfileAuthorizationAndApp`: two feeds
  on two profiles in two wallet apps; signing for the second uses B's address, B's token and B's
  wallet app, whatever else is saved.
- `operations/OperationViewModelTest`, `operations/PredictionOperationTest`,
  `operations/AlternateProviderTest` and `operations/OperationPrivacyTest` now bind the feed
  explicitly and approve with `walletFor(CONNECTION)`; there is no global selection left for them
  to read.

### 5. Two restricted feeds on different addresses stay readable; one's changes don't touch the other — COVERED

- `access/FeedAccessManagerTest` `twoFeedsBoundToTwoWalletsAreBothReadableAndEachAnswersForItself`:
  both sessions live at once; revoking one leaves the other; the same address on another network
  keeps its access (the proof is address-only); another address loses it.
- `access/FeedAccessManagerTest` `anotherWalletDoesNotInheritThisOnesAccess`: a new wallet starts a
  new request and drops the old session.

### 6. Adding, renaming or reconnecting a profile publishes nothing and cancels nothing — COVERED

- `wallet/WalletRepositoryTest` `addingOrReconnectingAProfileTellsNoServerAnything`,
  `renamingKeepsTheAccountLabelApartAndChangesNothingElse`, `cancellingInTheWalletChangesNothing`.
- `wallet/WalletViewModelTest` `addsAProfileOnTheChosenNetworkAndBindsItToNothing`;
  `WalletActivityTest` `addsAWalletOnTheWalletsTabAndChoosesItForNobody`.

### 7. Rebinding one direct server cancels only its own pending requests; offline publication retries without stale signing — COVERED

- `wallet/WalletRepositoryTest` `rebindingOneDirectServerTellsOnlyThatServerAndReportsWhatItCancelled`
  and `aServerThatMissedItsBindingSignsNothingUntilItHearsIt` (neither the old nor the new profile
  signs while the server is unreachable; the retry lands and only then is the connection ready).
- `wallet/WalletViewModelTest` `namesTheServerItCouldNotTellAndTellsItAgain`;
  `WalletActivityTest` `aServerThatCouldNotBeToldHearsItsWalletWhenTheAppComesBack`.
- `inbox/InboxViewModelTest` `asksNothingWhenTheWalletChangedWhileTheOwnerWasReviewing`: a rebinding
  the server did not hear leaves the connection `PublicationPending` and the approval opens no
  wallet.

### 8. Rebinding a feed invalidates its prepared transaction — COVERED

- `operations/OperationViewModelTest` `rebindingTheFeedDropsWhatWasPreparedForItsOldWallet`: the
  preparation, inspection and acknowledgement go, the problem is `WalletChanged`, the shared signal
  is untouched, and the review from before the change reaches no wallet.

### 9. Mismatch, unsupported provider network, stale review, removed profile or changed binding cannot sign — COVERED

- Wallet/network mismatch: `wallet/WalletRepositoryTest`
  `aRequestForAnotherNetworkIsNotSignedWithAFallbackProfile`; `inbox/InboxViewModelTest`
  `reportsARequestForAnotherWalletInsteadOfSigningWithThisOne`.
- Undeclared network: `wallet/WalletRepositoryTest`
  `aConnectionIsReadyOnlyWithItsOwnProfileOnADeclaredNetwork`; `operations/OperationViewModelTest`
  `aFeedWithoutAWalletOnADeclaredNetworkPreparesNothing`.
- Unsupported provider network (pre-existing, still passing): `operations/OperationViewModelTest`
  `aWalletOnAnotherNetworkIsRefusedBeforeAnythingIsAsked`.
- Removed profile / changed binding: `wallet/WalletRepositoryTest`
  `aReviewOfARemovedProfileNeverReachesTheWallet`,
  `aReviewForAConnectionThatWasReboundNeverReachesTheWallet`.

### 10. Two open reviews use the correct sessions; rebinding while waiting for the lock is rechecked — COVERED

- `wallet/WalletRepositoryTest` `aRebindingQueuedBehindTheWalletLockIsCheckedAgainBeforeTheHandoff`:
  two reviews wait behind a held wallet lock while one connection is rebound; only the review whose
  connection still names its profile reaches the wallet.
- `inbox/InboxViewModelTest` `neverSettlesAnotherConnectionsRequestWithThisOnesReply`: one profile
  bound to two direct connections, each signing only its own request.

### 11. Token rotation and authorization failure hit the right scope; shared grants survive removal — COVERED

- `wallet/WalletRepositoryTest` `aRotatedTokenIsKeptForEveryProfileSharingIt`,
  `anExpiredAuthorizationNeedsReconnectingForItsOwnProfilesAndNoOthers`,
  `removingOneProfileLeavesTheAuthorizationAnotherStillUses`,
  `everyAccountOneAuthorizationNamesIsAProfileSharingIt`.
- `wallet/WalletViewModelTest` `reconnectsAProfileInItsOwnWalletAppOnItsOwnNetwork`,
  `refusesAReconnectThatAuthorizedAnotherAccount`; `wallet/WalletScreenTest`
  `warnsOnlyOnTheProfileThatNeedsReconnecting`.

### 12. Removing a used profile shows its impact, falls back to nothing, and loses no history — PARTIAL

- `wallet/WalletRepositoryTest`
  `removingAUsedProfileLeavesItsConnectionsWithoutAWalletAndTellsOnlyTheirServers`: the affected
  connections are listed first, lose their binding, nothing is chosen in its place, and only their
  direct servers hear "no wallet".
- `wallet/WalletScreenTest` `confirmsARemovalNamingTheConnectionsThatUseIt`,
  `saysWhenARemovedProfileIsUsedByNoConnection`; `wallet/WalletViewModelTest`
  `removingAProfileLeavesItsConnectionWithoutAWalletAndPicksNoOther`, `cancellingARemovalKeepsTheProfile`;
  `WalletActivityTest` `removingAWalletLeavesItsConnectionWithoutOne`.
- **Gap:** no test removes a profile and then reads history or an in-flight confirmation. Both are
  keyed by the record's own address and network, not by a profile ID, so removal has nothing to
  rewrite; that is by construction, not by a SEE-174 assertion.

### 13. Migration preserves bindings and credentials, repeats safely, cancels nothing spuriously — PARTIAL

- `wallet/storage/WalletStoreTest` `migratesTheSingleSessionIntoOneProfileAndDropsItOnlyOnceCommitted`,
  `aMigrationThatCannotCommitKeepsTheSessionForTheNextStart`, plus the pre-existing two-file and
  format-2/3 upgrade tests.
- `wallet/WalletRepositoryTest` `migratesTheSingleWalletIntoAProfileAndBindsTheConnectionsThatUsedIt`
  (the same binding is republished, so nothing new is cancelled),
  `aMigrationInterruptedAtAnyStepEndsInTheSameProfileAndBinding`,
  `withNoUsableWalletLegacyConnectionsWaitForOneAndNothingIsInvented`.
- `connections/storage/ConnectionStoreTest` `keepsEachConnectionsWalletProfileAndItsServersNetworks`,
  `aManifestCachedBeforeNetworksExistedDeclaresNone`.
- Restricted-feed grants: covered only through the address-only rule in criterion 5; there is no
  test that migrates a stored grant across the upgrade.

- Publisher support: `network/network_test.go` (all five tests), `config/config_test.go`

  `TestATemplateSaysWhatItRunsOnAndTheConfigurationMayOnlyNarrowIt`, `manifest/manifest_test.go`

- `wallet/WalletRepositoryTest` `aPositionFollowUpUsesItsOwnerNotTheFeedsNewWallet`: the follow-up
  resolves the position's owner and network, never the feed's new binding, and is blocked when that
  profile is gone.
- The per-record cluster is pre-existing coverage: `inbox/InboxViewModelTest`
  `theHistoryKeepsTheTransferItsClusterAndItsTransactionId`, `history/HistoryDetailMappingTest`
  `anApprovedConfirmedTransferHasOneConfirmedTransactionOnTheRightCluster`.
- **Gap:** no test rebinds a connection and then reads its history, explorer link or confirmation
  polling. They read the network stored with each record, which rebinding does not touch.
