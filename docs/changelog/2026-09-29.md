# 2026-09-29

## Added

- **Several Solana wallet profiles, one per connection (SEE-174).** The phone no longer has one
  global wallet. The **Wallets** screen saves any number of profiles — an account in one wallet app
  on one network (Mainnet, Devnet or Testnet) — and lists each with its network, wallet app and how
  many connections use it, with **Rename**, **Reconnect**, **Remove** (after an impact summary naming
  the connections that use it) and an add form for a network and a wallet app. Adding always asks
  the wallet for a fresh authorization, so a second account from the same wallet can be chosen, and
  saves every account the wallet returns; the same app, address and network is one profile,
  refreshed rather than duplicated. Every connection names one profile: the picker opens right after
  a connection is added, offers only profiles on a network the server declares (or **Add wallet for
  &lt;network&gt;**, prefilled), and the connection's detail sheet has a **Wallet** row with the full
  address, wallet app and network, which is where it is deliberately changed. Reviews, preparations,
  provider resolution, rules, restricted-feed proofs, the wallet handoff and signing all resolve the
  connection's own profile and recheck it inside the wallet lock; nothing ever falls back to another
  profile. A direct server is told only its own connection's binding, tracked per connection and
  per binding, so the same binding republished at start cancels nothing. Rebinding a feed drops its
  preparation and acknowledgement; rebinding a restricted feed keeps access for the same address and
  asks again for another. Position sales use the position owner's own profile, and history,
  explorer links and confirmation tracking keep each request's own network. See
  `docs/wiki/wallet-profiles.md`, `docs/guides/wallet-setup.md` and `docs/testing/see-174.md`.
- **Servers declare their Solana networks (SEE-174).** `SolanaNetwork` and `supported_networks` in
  the manifest's reference (`direct.supportedNetworks`, `feed.supportedNetworks`); empty means no
  networks declared, never Mainnet or all. The server SDK takes `supportedNetworks` on
  `openDirectServer` (no default; `parseSupportedNetworks` and helpers exported), the MCP server
  reads `SAC_SUPPORTED_NETWORKS` (no default), the SKR staking server always declares Mainnet, and
  the publisher templates read `PUBLISHER_SUPPORTED_NETWORKS` (the demos default to `mainnet` and
  refuse `devnet`/`testnet`; plain `config.Load` declares none) through the new
  `publisher-support/network` package. The gateway validates, normalizes and carries the field
  through its manifest rebuild and refuses bad values with the new `GATEWAY_PROBLEM_BAD_NETWORK` =
  55; the phone refuses unspecified, repeated or more than eight values (`bad_network`) and skips
  values it doesn't know. A changed list is a new settings revision. See
  `docs/wiki/server-manifests.md#supported-networks`.

- **Discover tab for gateway-recommended feeds (SEE-176).** A gateway operator can list a feed in
  the app's catalog with **Show in app recommendations** and a plain-text public description (admin
  page on *Add server* and each server's page; `feed-gatewayctl register --recommend --description`
  and the new `feed-gatewayctl listing`). It is off by default and independent of Public/Restricted
  access. The gateway serves the catalog through the new, paginated
  `FeedService.ListRecommendedFeeds`: only listed, publishing, described feeds with a usable
  manifest, ordered by name, as an explicit public DTO with the registered access policy and nothing
  about the operator or any reader, uncached. The app gains a fifth tab, **Discover**, reading the
  catalog from `-Pseekervault.discoveryUrl` (defaulting to the relay URL): cards with name,
  description, Public/Restricted and networks, a detail sheet, loading/empty/error/retry/refresh and
  pagination. **Connect** and **Request access** open the ordinary Add connection flow prefilled
  (manifest revalidation, confirmation, wallet picker with network filtering, and for a restricted
  feed the existing wallet proof and publisher approval); each card shows the phone's own
  connection and persisted access state, never "connected" before the gateway admits the device.
  See `docs/wiki/discover.md` and `docs/testing/see-176.md`.

## Changed

- Wallet storage is one sealed `wallet-profiles` record (format 4) holding every profile and the
  authorizations they share; the connection store is format 7 and keeps each connection's
  `walletProfileId` and its manifest's supported networks. An expired authorization marks only the
  profiles that use it as needing reconnect, and removing a profile deauthorizes in the wallet only
  when no other profile still uses the authorization.
- Reconnecting a profile that shares an authorization reauthorizes that grant in place instead of
  splitting the profile onto a new one: a rotated token reaches every profile the wallet still
  authorizes, and removing the reconnected profile no longer revokes the token another profile
  signs with (SEE-174 review).
- A restricted feed rebound while its access challenge was pending no longer signs the proof with
  the old wallet: the proof is signed only while the feed still names the profile it was built for,
  checked inside the wallet lock, and a result that became stale after signing is discarded
  (SEE-174 review).
- `vault_get_address` answers the wallet of the calling sidecar's own connection, and
  `WALLET_NOT_CONNECTED` means no wallet is chosen for that connection.

## Fixed

- **Connecting a feed, or a burst of requests, no longer floods the app with banners (SEE-175).**
  The foreground banner used to announce every item that appeared in the inbox since its last look,
  so a newly connected feed's backlog, the catch-up read after coming back to the app, or twenty
  requests in a row each queued their own six-second banner. Now:
  - Only items that reached the phone **as news** are announced. The repositories say which those
    are before they publish them (`notifications/ArrivalLedger`): a live stream event always is; a
    whole read (a feed snapshot, a direct synchronization, a legacy fetch) is news only after the
    connection's first read in the foreground session; history a feed stream replays on opening is
    catching up. The inbox, counts and unread state are unchanged — nothing is dropped or marked
    read.
  - Requests and signals arriving together are **one banner** — "5 new requests · From Home
    sidecar", or "12 new items to review · From 3 connections" — that opens the Inbox; a single
    isolated item keeps its own words and opens its review. Items are counted by unique identity
    (connection + namespace + ID), so repeats, status updates and cross-server ID reuse never
    inflate the count.
  - The banner's six-second lifetime is fixed when it appears and never extended by merging. After
    it leaves (timed out, swiped or tapped) a **30-second cooldown** starts; what arrives meanwhile is
    held (at most 99 counted, then "99+") and shown as one banner when it ends. At most one incoming
    banner is presented about every 36 seconds under sustained traffic, and dismissing one never
    brings the same burst straight back.
  - Service messages and disconnections are not throttled and are queued ahead of an incoming banner
    that is not yet visible.
  - Review fixes: an item published while a feed's or direct server's first snapshot was being read
    is still announced when its live event follows, once (the snapshot/live handoff); a read by a
    background worker, or one that outlives its foreground session, never makes the next catch-up
    news; a direct stream's replayed history is catching up like a feed's; and a banner held through
    the cooldown, or queued behind another, leaves out any review the owner opened meanwhile.

  See `docs/wiki/in-app-notifications.md#bursts-and-backlogs-see-175`.

## Migration and deployment

- **Discover (SEE-176): gateway first, then phones.** The gateway migrates by itself (SQLite schema
  v8, Postgres schema v4) and every existing registration becomes **unlisted**, so nothing appears in
  any catalog until an operator opts a feed in and writes its description. A phone on an older
  gateway shows "This gateway doesn't offer a catalog yet" in Discover; everything else is
  unchanged. Builds read the catalog from `seekervault.discoveryUrl`, or the relay URL when unset.

- **Deploy servers first, then phones.** Update direct servers, the SKR staking server and
  publishers, and set `SAC_SUPPORTED_NETWORKS` or `PUBLISHER_SUPPORTED_NETWORKS`; update the
  gateway so it relays the field. An older phone ignores the field and keeps signing as before. An
  updated phone **gates signing for any connection whose server declares no networks** — including
  legacy direct sidecars that publish no manifest — and shows that the server has to be updated; the
  connection, its requests and its history stay readable. Setting the networks moves each server's
  settings revision once, and every phone rereads the manifest.
- **The phone migrates by itself.** On first start the single wallet session becomes one profile
  with IDs derived from its address, network and wallet app, so an interrupted migration repeats
  into the same IDs; the old session is deleted only after the new record is committed. Every
  connection stored before format 7 is bound to that profile (or to none when there was no usable
  wallet), idempotently, and the first publication sends each direct server the binding it already
  held, so no pending request is cancelled by the upgrade. Restricted-feed grants stay with their
  connection and address.
- Load-test publishers declare no network.
- Real-device Mobile Wallet Adapter checks for this change have not been run yet; Testnet is covered
  by fixtures only (`docs/testing/see-174.md`).
