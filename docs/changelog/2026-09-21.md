# 2026-09-21

## Fixed

- **`BROADCAST_PUSH_CREDENTIALS` accepts the service-account JSON document, not only a file path.** App Platform cannot mount a secret file; a JSON env on `gateway-0.1.4` was opened as a path and the process exited, which DigitalOcean rolled back. The value is a path unless it starts with `{`. PEM newlines that arrived as a two-character `\n` (YAML/env quoting) are still parsed. Compose file mounts are unchanged.

- **SEE-142: MCP h2c healthcheck leaked HTTP/2 sessions on timeout.** The
  container probe rejected after the deadline but left the request and
  `http2.connect` session open, so `node mcp-server/dist/healthcheck.js` could
  stay alive until Docker's outer timeout. Timeout and error paths now destroy
  the stream and session, keep the original error, and let the process exit
  nonzero without `process.exit()`. HTTP/1 and native-TLS checks are unchanged.

## Added

- **SEE-144: a gateway push relay for independently hosted direct MCP servers.** A developer's own
  direct server can now wake a backgrounded SAC app without holding a Firebase service-account
  credential, without running a Firebase project and without an account system. The gateway's
  operator keeps the credential; the developer gets a scoped relay credential that does exactly one
  thing; the owner's phone decides which servers may wake it, one direct connection at a time.

  What is relayed is a fixed, content-free `request_invalidation` — byte for byte the message a
  server with its own Firebase project already sends, under the same collapse key and TTL, so a
  phone cannot tell the two senders apart and does not have to. The relay's request has two fields,
  a handle and one of `created`/`updated`, and the gateway builds the message from constants: there
  is no field anywhere for text, a title, a topic, a target, a priority or a TTL. **Nothing else is
  proxied** — no request, approval, signature, result or private content passes through the
  gateway, and SAC keeps pairing, streaming, synchronizing and submitting decisions directly.

  Three authorities, each a separate secret held by a separate party: the operator registers a
  server and enables relay for it; the phone's installation proves ownership of itself with a
  secret the gateway minted once and kept only as a hash; the server presents its own relay
  credential. A send happens where all three meet, so "a server cannot wake a phone that did not
  agree", "a phone cannot be redirected by somebody who saw its FCM registration" and "a server
  cannot use another server's handle" are properties of the store's queries rather than checks
  somebody has to remember. Every way a handle fails to authorize a send — fabricated, revoked,
  expired, or another server's — is one refusal with one shape.

  SEE-141's admin surface grows capabilities rather than a second panel. A registration may publish
  a feed, relay push, both, or neither while an operator decides; a relay-only registration needs
  no manifest and publishes no feed. Credentials are issued **for** a capability, so a publishing
  credential never gains relay permission and a relay credential never gains publishing or
  administrative access. Enabling and disabling is a switch that refuses credentials while it is
  off and finds the same ones working when it is back on; revoking is the thing that cannot be
  undone. Both take effect on the next call, with no restart. `feed-gatewayctl` gains `--for` and a
  `capabilities` command and sees exactly the same state.

  Schema version 5 adds those capabilities and the relay's two records — an installation and a
  binding. Every row that already existed migrates to precisely what it already was, so SEE-141's
  behaviour is unchanged by the migration rather than restored by a special case. The two new
  tables hold routing and authorization metadata only; the boundary test that pins the whole schema
  now pins them too, so a column that could carry a request or a decision would have to be argued
  for by name. The gateway's SQLite file remains the accepted ephemeral demo limitation: **push
  bindings do not survive losing it**, and the documented recovery is re-enrollment and rebinding
  without re-pairing any direct connection.

  On the app: one relay, the one the build was configured with
  (`-Pseekervault.relayUrl`, empty by default). A server may advertise a relay over its
  authenticated connection and the app ignores the advertisement unless it names exactly that
  origin — which is what stops an advertisement from being a way to collect device registrations.
  The lifecycle reconciles rather than remembers, so a gateway that lost its database, an app that
  was reinstalled and a connection removed while offline all end in the same place; a revocation
  that could not be made is kept as work and repeated, because a disconnection has to be final from
  the owner's point of view even when it happened on a train.

  In the SDK: `relay: { relayUrl, serverId, credential }` on `openDirectServer`, three environment
  variables on the MCP adapter (`RELAY_URL`, `RELAY_SERVER_ID`, `RELAY_CREDENTIAL`), and no
  Firebase dependency of any kind. Direct Firebase delivery is unchanged and stays supported for
  operator-controlled installations; configuring both is **refused at startup**, because both fire
  on the same committed update and a phone would be woken twice for one change. A relay handle gets
  its own column, its own type and its own RPC (`PairingService.SetRelayHandle`): an FCM target
  addresses a device and works for whoever holds it, a handle addresses one authorization at one
  gateway, and putting one where the other belongs would wake nobody.

  Best effort throughout. An unreachable relay, a rejected device target or a gateway with no
  Firebase credential never fails a request, a synchronization or a decision — and an accepted send
  is Firebase having taken a message, which the operator's page says rather than claiming a device
  is online. Public-feed topic delivery, direct streaming and existing notification behaviour are
  unchanged.

  Walkthroughs: [`docs/guides/server-development.md`](../guides/server-development.md#17-waking-a-phone-from-a-server-you-host-yourself)
  for a developer, [`docs/guides/firebase.md`](../guides/firebase.md#the-direct-server-push-relay-see-144)
  for the operator, and [`docs/wiki/feed-gateway.md`](../wiki/feed-gateway.md#the-private-relay-for-servers-the-operator-does-not-host-see-144)
  for what each party stores.

- **SEE-141: a password-protected admin page on the feed gateway.** The operator can register
  publisher servers, rotate and revoke credentials and remove a publisher from a browser, instead of
  running `feed-gatewayctl` on the host that holds the database. It ships in the gateway's existing
  image and process, on a third listener (`BROADCAST_ADMIN_ADDRESS`, default `127.0.0.1:8092`) under
  a configurable prefix (`BROADCAST_ADMIN_PATH`, default `/admin`), and it **does not exist** unless
  `BROADCAST_ADMIN_PASSWORD_HASH` is configured — no handler, no listener, no route, and no
  unconfigured setup page. `feed-gatewayctl password` prints the hash; it needs no database, so the
  bootstrap works before one exists and after one is lost.

  Registering takes effect immediately: the gateway is not restarted and none of its environment
  changes. A registration is one transaction — the publisher, its optional host and its first
  credential, or nothing — and a server ID that is already registered is refused rather than
  silently given another credential. The raw credential is shown once, beside the server ID, the
  public gateway origin, the actual publisher API URL and the channel, and appears nowhere
  afterwards. Rotation stays additive and revocation is enforced on the next publication;
  `forget` remains separate and destructive, behind typing the publisher's own ID back.

  The page is protected by one configured password (PBKDF2-HMAC-SHA256 from Go's own
  `crypto/pbkdf2`, so the module list is unchanged), server-side bounded sessions in an `HttpOnly`,
  `SameSite=Strict` cookie with a logout that actually revokes, a per-session CSRF token plus the
  browser's `Sec-Fetch-Site`, login rate limiting under the same trusted-proxy policy read limiting
  uses, and `Content-Security-Policy: default-src 'none'` with one stylesheet and one script served
  from the image. A publishing credential is never an administrator credential and an administrator
  session is never a publishing credential. It reports only what the store can prove: no subscriber
  is counted and no publisher is called "connected".

  [`feed-gateway/README.md`](../../services/gateway/README.md#with-the-admin-page),
  [`docs/wiki/feed-gateway.md`](../wiki/feed-gateway.md#the-operators-admin-page),
  [`docs/development/feed-gateway.md`](../development/feed-gateway.md#the-operators-admin-page) and
  [`docs/testing/see-141.md`](../testing/see-141.md).

- **A third-party integration walkthrough that needs no SDK.**
  [`docs/guides/server-development.md`](../guides/server-development.md) now carries the whole
  operator-mediated path: what to tell the gateway operator, what each of the five values they hand
  back means, and publishing a manifest, a feed item, an update and a withdrawal with nothing but
  `curl` — no Direct Server SDK, no phone-facing gRPC server, no sidecar, no inbound port. It
  records every refusal the API can answer with its real status and code, how to share the feed
  reference without the credential, how to rotate before the old key is revoked, and what to do
  after the demo gateway loses its data.

## Changed

- **`feed-gatewayctl register` refuses an identity that is already registered**, pointing at
  `rotate`, instead of quietly adding a credential to the existing publisher. It also takes
  `--host <url>`, the developer's own base URL, recorded as administrative metadata and shown by
  `list`: the gateway never fetches it, no phone is told to contact it, and claiming a host grants
  nothing.

- **Gateway storage schema v4** adds `publisher.host` as one `ALTER TABLE ADD COLUMN` with an empty
  default. The live table list is unchanged — still the six public-feed tables a boundary test pins
  — and a database written by an earlier gateway opens, migrates and keeps every row.

- **Deployment.** `deploy/feed/compose.yaml` carries the admin variable group and publishes 8092 on
  host loopback; `deploy/ingress/feed/Caddyfile` routes one `/admin` block the operator may delete;
  `deploy/seeker-gateway.yaml` opens the internal port, routes `/admin*` at the edge, and declares
  `BROADCAST_ADMIN_PASSWORD_HASH` **empty**, so turning the page on is one encrypted secret and no
  credential is committed.

## Notes

- **This does not make the demo's storage durable.** On the current App Platform deployment the
  gateway's SQLite file can be discarded when a container is replaced, taking registrations and
  credential hashes with it. The admin page is what makes recovering from that a login and a few
  forms rather than a database console — the password is deployment configuration, not a row — but
  lost publisher secrets cannot be recovered from hashes, and nothing here preserves or restores
  data automatically.

## Fixed (later the same day)

- **SEE-145: the hosted feed gateway stops losing its database on every deploy.** App Platform has
  no disk to attach, so the gateway's SQLite file lived on the container's own filesystem and went
  with it every time one was replaced — taking every registration, every credential hash and every
  relay binding. It had been documented as an accepted limitation and recovered from by
  re-registering publishers by hand; it is now removed rather than described.

  `internal/storage/postgres` is a second implementation of the same `storage.GatewayStore`
  contract, and which one a deployment gets is the whole of the difference:
  `BROADCAST_DATABASE_PATH` for a file, `BROADCAST_DATABASE_URL` for Postgres. Setting both is
  refused at startup, because they are two authorities for the same state and a deployment that
  named both has already lost track of which one holds it. The image ships **no** path default any
  more, so the choice is always the deployment's — it was never startable without configuration
  anyway, `BROADCAST_PUBLIC_URL` having no default for the same reason.

  Nothing above the store changed. Validation, RPC, cursor and outbox-draining rules never knew
  which database they had, and a boundary test that used to say "business code does not import
  SQLite" now says it of either implementation — which is why a second database was a new package
  rather than an edit to an existing one.

  What the port preserves deliberately: every instant stays the same millisecond integer rather
  than becoming a `timestamptz`, because a proposal's expiry, a notice's backoff, a binding's
  window and the three relay cutoffs are comparisons the two stores must answer identically, and a
  type change would have altered what they mean on the way past. A paged walk orders and compares
  under the `C` collation, because Postgres would otherwise order text by the database's locale and
  a walk whose `ORDER BY` disagreed with its own cursor skips documents.

  What it rebuilds explicitly: SQLite serialized writes with one connection and an immediate
  transaction lock, so that two publications could not decide against the same stale revision. Every
  write here takes one transaction-scoped advisory lock first — the same rule, now holding *across*
  processes rather than only within one, so `feed-gatewayctl` can register a publisher while the
  gateway runs instead of failing fast.

  The tables are in a `gateway` schema rather than `public`, with row-level security enabled and no
  policy. A managed Postgres may serve its public schema to anyone holding the project's publishable
  key — a key that is meant to be published — and this database holds credential hashes and the
  current push target of every enrolled phone. The schema is the defence; the policy-less RLS is
  what still holds if somebody exposes the schema later. Both are pinned by a test.

  `feed-gatewayctl` takes either: a Postgres URL is recognized by its scheme, anything else is a
  file. Its store tests need a real Postgres (`BROADCAST_TEST_DATABASE_URL`) and skip without one,
  because what they check is that this dialect answers the same questions the file does, and the
  only thing that knows is the database.

  Self-hosting is unchanged and SQLite remains the recommended shape for it: the four Compose
  presets, their explicit volumes, the backup procedure and the whole existing test suite are
  untouched.
