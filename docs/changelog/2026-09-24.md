# 2026-09-24

## Fixed

- **SEE-148: a shortened MCP pairing link was opened as if it were complete.** A fresh
  `vault_create_pairing_link` HTTPS URL renders the pairing page, and its button, QR, and copy
  value all carry the same `seekervault://pair` URI. The reported page, `…/pair#eyJ2Ij...WiJ9`, is
  a real fragment with the middle replaced by a literal ellipsis (the payload starts `{"v":` and a
  minimal one ends `Z"}`). The page rejects that, and a cut-off fragment, with "This pairing link
  is damaged or incomplete." The tool text now includes a Connect your phone link whose target is
  the entire `https_url`, plus the address and `pairing_uri` each on one fenced line. The server
  instructions tell the agent not to omit, wrap, or escape either value. The fragment protocol and
  the SEE-140 page rules are unchanged. A chat client that still abbreviates the URL on its own is
  outside this server. No physical phone check was run.

## Android

Review findings on the execution-provider interface (SEE-145).

- **A stored row keeps a downgrade honest, so the version number stays at 3.** SEE-145's addition to
  `ProposalStore` is purely additive — the execution provider and the versioned action are written
  *beside* the legacy operation and plugin names, never instead of them — but the stored number had
  been raised to 4, and a version-3 build's `decode` refuses anything outside `1..3` before it reads
  a single field. Every row this build had rewritten would have vanished on the way back, taking the
  owner's review and the record of the one attempt with it, and a refreshed proposal would have
  looked unexecuted and become actionable again. The number stays at 3. Writing keys an older reader
  ignores is what "additive" means; renumbering is not.

- **A legacy capability name authorizes only the capability it was published for.**
  `jupiter.prediction` never meant "Jupiter, and separately whatever this document asks for" — it
  meant Jupiter's prediction order. A document pairing it with the `swap` action, or `jupiter.swap`
  with a prediction, was resolving to Jupiter anyway, because the name was collapsed to a provider
  and the action it was paired with was dropped; the check that remained asked only whether Jupiter
  serves swaps, which it does. The build before SEE-145 refused the same document as another
  plugin's. The pair is now what gets checked, wherever a legacy name is read — off the wire, out of
  a stored row, and at the gate between a review and the wallet — and naming the provider outright
  does not rescue it, because a stated provider settles *which* provider and never *whether*. It is
  reported as its own refusal, `name_mismatch`, rather than as a missing provider: nothing is
  missing, the document disagrees with itself.

## Added

- **SEE-146: a standalone SKR staking MCP server, and the approval path that reviews it.** A second,
  independently deployable direct server — `skr-staking-server/` — connects to the phone as its own
  connection and offers an agent five tools: `get_staking_status`, which reads, and `request_stake`,
  `request_unstake`, `request_cancel_unstake` and `request_withdraw`, which create approval requests
  and stop there. None of them signs, executes or approves anything, and the wallet is never a
  parameter: it comes from the connection's own binding.

  It reuses the existing Direct Server SDK for pairing, the request lifecycle, preparation, results
  and confirmation; everything SKR-specific lives in its own `src/skr/` module. The general MCP
  server adopts no staking logic, and the feed gateway is untouched.

  Walkthroughs: [SKR staking](../wiki/skr-staking.md), [the tools](../integrations/skr-staking.md),
  [running the server](../development/skr-staking-server.md),
  [what was verified and the owner-run test](../testing/see-146.md).

- **A fifth action kind in the protocol.** `StakingAction { wallet, network, operation, amount }` is
  field 5 of the `Action` oneof — one message rather than four, because the four operations are four
  states of one position. It carries no program, mint, pool, vault or stake account **on purpose**: a
  server that could name the program it wants called is a server that could have an owner review one
  program and sign for another. Nothing on the wire moved, and every existing fixture still decodes.

  Cancelling and withdrawing carry no amount, and an amount on either is refused rather than ignored
  — by the server and, independently, by the phone. The program acts on the whole pending unstake for
  both, so a number there would describe a choice nobody is being offered.

- **The phone reads the staking program for itself.**
  `android/app/src/main/java/.../skr/` carries the program ID and the SKR mint, derives the
  configuration, the vault, the guardian's pool and the owner's stake account from their seeds, reads
  the accounts through the app's own endpoint, and decodes the prepared transaction with the app's own
  parser. It checks the operation, the deployment, the stake account's ownership, the amount or the
  shares, the signer roles, the destination, the supporting instructions and the cooldown — and every
  fixed account position the instruction has, because nobody has a reason to change one.

  The position is read **before** the preparation is asked for, so the reading is never newer than the
  bytes it judges.

- **Four staking actions in the Inbox, named as four things.** Unstake and withdraw get different
  titles, different sentences, different amount labels and different Approve buttons, because one
  starts a wait and moves nothing and the other is the step that finally moves the SKR. A pending
  cooldown that a further unstake would restart is warned about in the error colour, and a cooldown
  that has already finished is refused by name — the program answers `WithdrawRequired`, so the review
  says so rather than letting a transaction fail after it was approved.

- **A `staking` policy action.** One rule for the owner to write, because a rule is about whether this
  app may touch their staking position at all. What the rules are told is not the same for all four:
  a stake commits tokens and is outgoing, an unstake and a cancellation move nothing, and a withdrawal
  brings SKR back. Counting all four as outgoing transfers would charge a spending limit for something
  that did not happen.

## Notes

- The staking program is deployed on **mainnet-beta and nowhere else** — checked, not assumed. The
  server compares genesis hashes at startup and refuses to come up against another cluster, because a
  devnet endpoint reads every account as absent, which is indistinguishable from an owner who has
  nothing staked.
- The cooldown, the minimum stake and a withdrawal's amount are all read from the chain every time.
  48 hours is what the configuration says today, not a constant anybody compiled in.
- `solana-mobile/react-native-samples` carries no licence file, so none of its source is vendored:
  discriminators are computed as Anchor computes them, layouts are written out field by field, seeds
  are derived, and each derivation is asserted against the on-chain IDL and against real accounts.
- No staking dashboard, background monitoring, withdrawal reminders, shared staking feed, automatic
  approval or staking contract of this project's own. Sandbox behaviour is unchanged: nothing in the
  staking path can sign or broadcast, and the tests hold it to that.

## SEE-146 review fixes

Three findings from the review of [#54](https://github.com/BrRenat/SeekerAgentConnect/pull/54),
each now held by a test that fails without its fix.

- **A submitted staking transaction can now stop being submitted.** `skr-staking-server` handed the
  SDK a `StakingProvider` and nothing else, so no `ConfirmationTracker` was ever built:
  `direct.requests.confirmations` was undefined, an agent polling a `SUBMITTED` request read the
  same unchanged request forever, and the owner's own check on the phone was answered
  `CHAIN_UNAVAILABLE` because there was nothing to ask. It now supplies a `ConfirmationProvider`
  over the endpoint it already reads everything else from. For an unstake this is not cosmetic: an
  unstake nobody can confirm is a 48-hour cooldown the owner cannot tell has begun.

  `confirmedTransaction` is the one read here that goes straight to JSON-RPC rather than through
  `Connection`, because it asks for base64: the whole use of that call is comparing what ran
  against what the owner approved, and comparing a re-encoding of a parse would only prove the
  encoder agrees with itself.

- **`get_staking_status` refuses a wallet it cannot act on.** Creating a request already asserted
  the network; a read did not. A phone that had published a devnet binding got this mainnet-only
  server's answer for that address back, labelled `devnet` — a position read off one cluster and
  presented as another's, indistinguishable from an ordinary answer. The network is now checked
  before the position is read, and this package's chain errors reach the agent as
  `INVALID_PARAMETERS` or `CHAIN_UNAVAILABLE` rather than escaping as an unhandled failure.

- **A malformed `SKR_STAKING_ALLOWED_HOSTS` stops startup.** The parse ran inside the returned
  configuration object, after the one `problems.length` check, so its problem went into a list
  nobody read again. A URL or a wildcard where a host name belongs was silently dropped and the
  server came up refusing the very agent it had been configured to let in, with nothing at startup
  to say why.

- **The SKR staking image starts.** The runtime stage copied the Direct Server SDK's built output
  but not its `node_modules`, so under pnpm's isolated layout `@bufbuild/protobuf` could not be
  resolved and the container exited on its first import. Published as
  `brenat/seeker-agent-connect:skr-staking-mcp-0.1.1`.

- **Hosted SKR staking server.** `deploy/seeker-skr-staking-mcp.yaml` is the App Platform spec for
  it, shaped like `seeker-mcp.yaml`: port 8080, h2c behind the platform's HTTP/2, a TCP health
  check, the public URL and allowed host from `${APP_URL}`/`${APP_DOMAIN}`, and the agent token and
  RPC URL as encrypted secrets.

## SEE-149: the pairing link on the SKR staking server

- **The SKR staking server has the HTTPS pairing flow the general MCP server has.** An agent
  connected only to `skr-staking-server`'s `/mcp` can call `skr_create_pairing_link` and hand the
  owner a complete `https://<SKR_STAKING_PUBLIC_URL origin>/pair#<fragment>` link. The server serves
  that page itself, beside `/healthz`, `/mcp` and the phone API, and the page says it is the staking
  server and a separate connection — so a hosted deployment no longer has to be paired by opening a
  container console and reading a QR code out of a terminal. `skr-staking-server pair` prints the
  same link beside the QR code and the URI.

  The tool has its own name on purpose. An agent may be connected to the general server too, and
  `vault_create_pairing_link` there pairs a different database and a different connection; two links
  called the same thing are two links that can be handed over in the wrong order.

- **The page, the fragment codec and the agent-facing wording moved into the SDK.** They are now
  `server-sdk/src/pairing/` — `landing.ts`, `link.ts`, `link-text.ts` and `page/` — and both servers
  use them through the SDK's public API. The staking server imports nothing from `mcp-server`. What
  each host still supplies is the sentence naming itself, the path to its own `uqr` build, and its
  own MCP registration, because the SDK imports no MCP and installs no QR library. Sharing rather
  than copying is the point: the token-in-the-fragment rule, the CSP, the origin check and the
  refusal of a shortened fragment are security-carrying code, and two copies drift apart.

- **SEE-140 and SEE-148's protections are unchanged and now tested on both servers.** No automatic
  launch; nothing pairs, revokes or issues on page load, copy or QR; the token stays in the fragment
  and appears in no request, log or storage; a code for another origin is refused; and a truncated
  fragment or one with a literal ellipsis in it is rejected as damaged rather than half-read. Pairing
  the staking server leaves the general server's pairing alone, and the reverse.

- **Tests.** The tool's output, the served page with its CSP enabled, the page rendering a
  tool-generated link (button, QR and copy value all the same URI), the refusals, and the CLI's three
  outputs — `skr-staking-server/src/pairing/`, plus the shared handler and codec in
  `server-sdk/src/pairing/`. `check-deployments` and both package audits still pass.

  One pre-existing fix travels with this: `skr-staking-server pair` with no `SKR_STAKING_PUBLIC_URL`
  used to ask for a code with no origin at all, which pairing refuses; it now names the loopback
  origin a phone on `adb reverse` would call, as the general server's command already did.
