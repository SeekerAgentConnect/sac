# 2026-09-17

## Added

- **Docker images and a Compose stack for self-hosting (SEE-46 / SAW-034).** [`gateway/compose.yaml`](../../gateway/compose.yaml) runs the sidecar behind a gateway, building both from the checkout: no unpublished package or image is needed. [`mcp-server/Dockerfile`](../../servers/mcp-server/Dockerfile) and [`test-agent/Dockerfile`](../../tools/test-agent/Dockerfile) are multi-stage, pin Node and pnpm, install with `--frozen-lockfile`, install again with `--prod` for the runtime stage, run as fixed unprivileged accounts, drop every Linux capability, and set `no-new-privileges`. Durable requests live on a volume at `/data`, the only path the runtime account can write.
- [`docs/guides/self-hosting.md`](../guides/self-hosting.md): the full setup, what is reachable and what is not, reaching the stack by hostname, the test agent, persistence, and troubleshooting. [`gateway/.env.example`](../../gateway/.env.example) carries the deployment's settings, separate from the repository root's development `.env.example`.
- **A TLS gateway and a public/private endpoint split (SEE-47 / SAW-035).** [`gateway/compose.public.yaml`](../../gateway/compose.public.yaml) and [`gateway/Caddyfile.public`](../../gateway/Caddyfile.public) put the stack on the internet with a certificate Caddy obtains and renews for a domain the operator owns: `docker compose -f compose.yaml -f compose.public.yaml up -d --build`. `/mcp` and the phone's pairing, request, and update services are public; `/healthz` and the Stage 1 `LiveCommandService` diagnostic are not, and every other path and any unknown `Host` is refused at the gateway. Each route caps a request body at 64 KiB, the admin API is off, and credentials stay out of the access log. [`gateway/Caddyfile`](../../gateway/Caddyfile) keeps its place as the local-development configuration, plain HTTP on a loopback address.
- **An OAuth profile for a hosted MCP client (SEE-48 / SAW-036).** With `MCP_OAUTH_ISSUER` set, `/mcp` also accepts an OAuth 2.1 access token issued by the operator's own authorization server, so a hosted client — Claude's custom connectors are the one this was written for — can connect on a person's authorization instead of a shared token: `docker compose -f compose.yaml -f compose.public.yaml -f compose.oauth.yaml up -d --build`. The sidecar is the resource server the MCP specification describes and no more: it publishes protected-resource metadata (RFC 9728) at both well-known paths, validates the signature, issuer, audience, expiry and scopes of every token, and issues none. [`gateway/compose.oauth.yaml`](../../gateway/compose.oauth.yaml) is the optional overlay, and [`docs/integrations/claude.md`](../integrations/claude.md) is the operator's setup, including what an authorization server must support and what every refusal means.
- **The finished test-agent CLI, and Hermes against the packaged stack (SEE-49 / SAW-037).** `wait <id>` reads a request until it settles or a deadline passes, and `--wait` does the same after `ack`, `sign`, or `transfer` create one — with the `request_id` on stderr before any waiting starts, and one JSON document on stdout at the end. `status` and `wait` now print `outcome`: `succeeded`, `failed`, or `unsettled`, the same three answers as the exit codes. `swap` exists and says that swaps are a later stage which no sidecar serves, rather than failing as an unknown word. [`examples/hermes.config.hosted.yaml`](../../examples/hermes.config.hosted.yaml) is the Hermes entry for a deployment reached over its own domain, and [`docs/integrations/hermes.md`](../integrations/hermes.md#9-hermes-against-the-packaged-stack) covers Hermes against the Stage 7 stack, locally and hosted.
- **A self-hosting and operations guide somebody else can follow (SEE-50 / SAW-038).** [`docs/guides/self-hosting.md`](../guides/self-hosting.md) is now numbered from a clean checkout to a first request waiting on the phone, separately for your own machine and for a Linux VPS on the internet, and it covers everything after the first start: logs and what never reaches them, rotating each credential, revoking and re-pairing the phone, updating, what migrations do, and one backup and restore procedure — with a section on what recovery can and cannot do. What the stack needs from other people is named rather than waved away: base images and the npm registry at build time, a domain and a certificate authority to go public, somebody's Solana RPC endpoint for transfers, an authorization server for a hosted client, and Firebase only if push is wanted.
- **A Docker image and a Blueprint for Render.** `deploy/render/` (removed on 2026-09-18) packs the sidecar and a Caddy gateway into one container for a [Render](https://render.com) web service: Render terminates HTTPS and forwards HTTP to Caddy, which forwards `/mcp`, OAuth discovery, and the phone's services — under the deployment's own hostname only — to the loopback-bound sidecar; `/healthz` answers Render's probes, and the Stage 1 diagnostic and every other path get `404`. A small Node supervisor validates the configuration, derives `MCP_ALLOWED_HOSTS` and, when `SIDECAR_PUBLIC_URL` is unset, the public URL from Render's own `RENDER_EXTERNAL_URL`, and stops the service if either process exits. `render.yaml` builds it from the repository with a `/data` disk and generated tokens; The image is built for `linux/amd64` from an Apple silicon Mac too — its dependency and build stages run on the building machine's platform, so pnpm never runs under emulation — and pushed to Docker Hub by hand for an "Existing Image" deployment; `.github/workflows/build-render.yml` does the same to GitHub Container Registry, on manual dispatch only. `render-pair` is the pairing CLI for Render's Shell tab, run as the service's own account so the disk's files stay its own. Nothing in the sidecar, the Compose stack, or a stage boundary changed.

## Changed

- **A transfer keeps the authorization the wallet handed back (SEE-84).** A wallet reauthorizes this app at the start of every session and may replace this phone's token. Message signing already kept the replacement; sending a transaction reported only its outcome and dropped it, so the next operation could offer a token the wallet had already replaced. `WalletAdapter.signAndSendTransaction` now answers with a [`SendingAnswer`](../../apps/android/app/src/main/java/io/github/brrenat/seekervault/wallet/WalletAdapter.kt) — the outcome and the authorization — and the replacement is kept for a sent, a declined, and an unknown transfer alike. A phone that can't write it down still reports exactly what the wallet did and asks the wallet nothing again.
- **Nothing is signed for an account the wallet no longer authorizes (SEE-84).** Inside the one session, and before any signature or transaction is put to the wallet, the wallet's own reauthorization is checked against the account the owner reviewed. An account it no longer lists, or one it lists with chains that contradict the reviewed network, stops the request: the phone forgets the session and the owner connects the wallet again and reviews afresh. A wallet that lists no chains for the account has said nothing, which is how connecting has always read it.
- **One wallet session, one client (SEE-84).** [`MwaWalletAdapter`](../../apps/android/app/src/main/java/io/github/brrenat/seekervault/wallet/MwaWalletAdapter.kt) made a new Mobile Wallet Adapter client for every operation, which threw away the wallet endpoint the client had learned while authorizing. It now keeps one client for the session and drops it on disconnect, on an authorization the wallet refused, and on a network change. Nothing is held open between calls. Restoring that targeting across a process restart would need an upstream API — the client's endpoint is private with no public setter, and this app does not reach into one by reflection — so the limitation is written down in [`wallet-lifecycle.md`](../testing/wallet-lifecycle.md#wallet-targeting) rather than worked around.
- **The wallet's selection and its authorization are one sealed record (SEE-84).** They were two files, each atomic on its own but not as a pair. [`WalletStore`](../../apps/android/app/src/main/java/io/github/brrenat/seekervault/wallet/storage/WalletStore.kt) now keeps one versioned AES-256-GCM record at `noBackupFilesDir/wallet/wallet-session`, migrates the older pair on first read and deletes it, and refuses half of one. The repository reads it whole and never signs with a token whose account and network aren't the selection in hand.
- **A failure before the transaction reached the wallet is a failure (SEE-84).** The phone knows whether it ever got as far as asking, so a session that ended before the request was made settles as a failure instead of leaving an outcome nobody will ever close. From the instant the request is made, the rule is unchanged: an outcome nobody knows is UNKNOWN, never a rejection, and nothing is ever sent again by itself.

## Notes

- The gateway joins the sidecar's network namespace, so the sidecar keeps the loopback-only bind it has had since Stage 1 while still being reachable. The sidecar's port is unreachable from the host and from every other container, not merely unmapped, and only the gateway's port is published — bound to `127.0.0.1` by default. No stage boundary moved and no sidecar source changed.
- The test agent is in the `agent` Compose profile, so `docker compose up` never starts it. Starting the stack creates no wallet request, spends nothing, and launches no LLM. Its default container command, `tools`, only reads.
- Node is PID 1 in the sidecar image, so `main.ts` receives `SIGTERM` itself and closes the listener, the streams, and SQLite; Compose allows 30 seconds.
- The two gateway configurations are separate files reached by separate commands, so loopback HTTP cannot become the public default by omission. The overlay derives `MCP_ALLOWED_HOSTS` and `SIDECAR_PUBLIC_URL` from `GATEWAY_DOMAIN`, the two settings a public deployment must not get wrong, and refuses to start without the domain or the certificate authority's contact address.
- The gateway adds no authentication and removes none: it never inserts or strips an `Authorization` header, and it passes `Host` through, so the sidecar's own boundaries and its DNS-rebinding check are unchanged. Nothing in the repository suggests overriding a certificate warning.
- The phone's live update stream is not carried by a TLS-terminating gateway: it is gRPC over HTTP/2 terminating at the sidecar's own TLS listener. Behind the gateway no update endpoint is configured, so pairing advertises none and the phone keeps its manual refresh — nothing is promised that the endpoint could not deliver.
- SAW-035 changed no sidecar or test-agent source, and moved no stage boundary.
- OAuth is optional and off by default. An operator running Hermes or an agent of their own keeps `MCP_TOKEN` and needs none of it, and a deployment without `MCP_OAUTH_ISSUER` advertises no authorization at all — the discovery document answers 404.
- Nothing here became an authorization server: there is no authorization endpoint, no token endpoint, no client registration, no consent screen, and no client secret anywhere in the repository. The authorization server is a product the operator already runs or signs up for, and the only thing read from it is public keys.
- A token is accepted only if it was issued for this deployment — the audience check the specification exists to insist on — and only with an asymmetric signature. It is never passed on to anything, and it opens `/mcp` and nothing else: the phone's API keeps its own credentials, so a hosted client never gains a phone approval credential.
- While OAuth is on there is no second way in: `MCP_TOKEN` opens `/mcp` only under a loopback `Host`, which is the stack's own private endpoint inside the container network namespace, and the public gateway closes any connection claiming a host it does not serve.
- An authorized client may ask. Every request still waits for the owner's hand on their own wallet, and the tools an access token reaches are exactly the tools `MCP_TOKEN` reaches.
- Revoking a grant stops the next token rather than the current one, because a signed token is not re-checked on every call; short access-token lifetimes are the answer, and removing `MCP_OAUTH_ISSUER` refuses every access token at once.
- **A behaviour change in the CLI:** `hello` and `ack` are development diagnostics, and they now run only with `MCP_DEMO_TOOLS=true` in the environment — as `.env.example` sets it — or with `--demo`. Both return an acknowledgement, and an acknowledgement is neither a wallet signature nor a payment confirmation; a client that lives in a deployment should not be able to reach for one by accident. An older `.env` without the line gets exit 2 and a message naming both ways to proceed. The wallet commands, `sign` and `transfer`, are unaffected.
- Waiting changes nothing about a request. A deadline that passes means the owner has not answered yet: exit 10, `timed_out: true`, and the request exactly as it was. Nothing withdraws a request, retries one, or creates a second, and `UNKNOWN` stays unsettled rather than failed — a script that reads either as a failure is a script that pays twice.
- The `swap` command implements no swap. It reports that `vault_swap` is not served, queues nothing, and is held to `transfer`'s rules — `--wallet` and `--network` required — so the command that reports a swap is unserved never becomes a looser one the day it is served.
- The test-agent container now follows the stack's `MCP_DEMO_TOOLS`, which a deployment leaves off.
- The guide no longer says there is no account to make. There is none with **us**, and that is the accurate claim; a public deployment still needs a registrar and a certificate authority, and transfers still need somebody's RPC endpoint.
- **Restoring an older backup moves the sidecar's record backwards, and that is all it does.** A request answered after the backup is PENDING again; nothing is re-executed, no wallet is opened, no transaction is rebuilt, and nothing is resent. The owner's phone re-delivers the answer it still holds, and a transfer that was already sent is settled by reading the chain, never by building a replacement — so a restore can lose the record of a payment, and cannot cause a second one.
- No wallet key is in this stack, so no backup of it can lose or recover funds. The phone's own data — the owner's answers, their Activity records, their rules, the wallet they selected — is on the phone and nowhere else, and uninstalling the app removes it for good.
- The Stage 7 stage boundary moved for OAuth alone (`AGENTS.md`): token validation lives in `mcp-server/src/oauth.ts`, three files know it exists, and a stage-boundary check fails if that changes.

## Added

- **A client-plugin boundary in the existing core (SEE-86 / Stage 7.1).** [`android/.../plugins/`](../../apps/android/app/src/main/java/io/github/brrenat/seekervault/plugins) is one place a bundled client plugin can be registered, so the two Jupiter plugins (SEE-93, SEE-94) can be written without touching a transport, a policy, the wallet, or storage. A plugin declares a stable ID, the contract version it was written against, the operations it serves and the environments it serves them in, and supplies exactly three behaviours: parameter collection, preparation, and inspection. [`docs/wiki/client-plugins.md`](../wiki/client-plugins.md) is the architecture document, including the extraction work SEE-102 would still have to do and how a host app would get an entry point — neither of which this change implements.
- **What a plugin is handed is exhaustive, and it is not wallet authority.** An `ActionSubject` carries the connection ID, the operation, the environment, the structured request, and the wallet the owner selected — a public address and a network. No credential, no wallet authorization token, no transport handle, and nothing that can approve or send. The owner's manual approval, the one-at-a-time wallet interaction, the policy evaluation and the local execution record all stay in core.
- **Typed inspection facts, with coverage derived rather than stated.** A plugin reports what it read as an `InspectedAction`: a payer, an amount in base units, a mint, a recipient, the programs called, and how many of the transaction's instructions it actually read. Whether the bytes were read whole comes from those two counts, so a plugin cannot claim complete coverage of bytes it didn't finish. The chain is core's — the network the owner's wallet is selected for — and a plugin's own idea of which network its bytes are on is never consulted.
- **An unserved operation establishes nothing.** No plugin, nothing prepared, or bytes that couldn't be read all produce unread facts: value moves, nothing is verified, and the verdict can never be `ALLOWED`. A missing plugin is a gap in the review and never a byte that turned out to be fine.

## Changed

Anything else resolves against the bundled list. That list is empty at SEE-86, so a swap resolves to "no plugin" and produces the same unread facts the previous build produced: behaviour is unchanged, and SEE-93 changes one list.

## Notes

- Operations are named at the protocol's own level. Core says `swap`; a plugin claims `swap`. That Jupiter is what makes a swap work is the plugin's business, which is what keeps a provider's name out of `connections/`, `sync/`, `live/`, `push/`, `policy/`, `transactions/` and `activity/`.
- Nothing is downloaded and there is no dynamic load path, so there is none to secure. `PluginRegistry.bundled()` is the build-time selection, and a manifest that names a plugin (SEE-88) can only be matched against what the build already carries. Two plugins registered under one ID fail where the list is written, because an ID is what a manifest names and a name that means two things means nothing.
- Three refusals are kept apart rather than collapsed, because they are three different things to tell someone: this build carries no plugin for the operation, it carries one written against another version of the boundary, or it carries one that doesn't serve this environment. None of them is a verdict about the operation.
- **No limit was lifted and no stage boundary moved.** The app still holds no key, builds no transaction of its own, reaches no chain, and opens no wallet without the owner's hand on it. No storage format, proto, or screen changed, so the app starts on the same persisted data and no migration discards anything; the approved v4 presentation is untouched.
- **Nothing owner-visible changed**, so there is nothing new to check on a device. No plugin exists yet: `jupiter.swap` is SEE-93 and `jupiter.prediction` is SEE-94. Server manifests and per-connection modes are SEE-88, shared proposals SEE-89, the Sandbox/Production choice SEE-97, and the host-app entry points SEE-104.

## Changed

- **MCP is now an optional adapter over the request core (SEE-87 / Stage 7.1).** The Node sidecar used to *be* its MCP endpoint: `MCP_TOKEN` was required to start, `/mcp` was always mounted, and the agent tools reached the request store, the transaction preparer and the confirmation tracker directly. `MCP_ENABLED` is the switch and defaults to on, so an existing deployment keeps every setting and every behaviour it has — the same tool names, the same contracts, the same errors, the same result delivery. [`docs/wiki/mcp-adapter.md`](../wiki/mcp-adapter.md) is the architecture page, including the distinction Stage 7.1 needs: this sidecar is the owner's **private** server, and the Go publisher templates (SEE-95, SEE-96) are a developer's **broadcast** servers that speak no MCP at all.
- **One internal boundary, and it decides nothing.** [`server-sdk/src/requests/agent-api.ts`](../../packages/server-sdk/src/requests/agent-api.ts) names the whole of what an adapter may ask the core for: store a request, read one, withdraw one, answer a retry, read the owner's wallet binding, and — only when `SOLANA_RPC_URL` is configured — check an asset before storing a transfer and read what became of a submitted transaction. Idempotency, parameter validation, the lifecycle's transitions, the pending limit and result handling stay in `RequestStore`, `requests/lifecycle.ts` and `requests/action.ts`, and the `RequestFailure` an adapter sees is the one the core raised. It authenticates nobody — a credential belongs to the adapter that accepts it, so `/mcp`'s token and OAuth checks stay in `mcp-endpoint.ts` — and it holds no connection, cache or store of its own.
- **Startup, shutdown and configuration stopped knowing what MCP is.** `server.ts` builds the core, calls one `mcpAdapter` function, and from then on treats the result as an optional route; every MCP-only setting is read in that one function. `close()` closes what exists. Nothing about pairing, the request store, the phone API, production updates or push depends on whether the adapter ran.

## Added

- **A mode with no agent endpoint at all.** With `MCP_ENABLED=false`, `/mcp` answers 404 and so do both `/.well-known/oauth-protected-resource` paths — not served rather than locked, because a challenge would suggest that some credential would open one. No MCP setting is required. A leftover `MCP_TOKEN`, `MCP_ALLOWED_HOSTS` or `MCP_DEMO_TOOLS` is ignored and **named in the startup log**: turning the adapter off should not force an operator to delete a token they may want back, but nothing is allowed to do nothing quietly. `MCP_OAUTH_*` is refused as a configuration error, because the profile publishes metadata telling a client where to authorize for an endpoint the deployment would not serve. A broken switch value (`MCP_ENABLED=off`) is a configuration error and leaves the adapter **on**, so a typo can never silently remove the endpoint.
- **`MCP_ENABLED` in the shipped deployment assets**, extending Stage 7 rather than forking it: [`gateway/compose.yaml`](../../gateway/compose.yaml) gained the setting and no new file, so there is one stack and not two. `MCP_TOKEN` is no longer a compose-level hard requirement, because whether it is required depends on the switch and the sidecar's own configuration check is the one place that knows the rule — it now names both ways out. `gateway/.env.example` and the root `.env.example` document the setting, and [`docs/guides/self-hosting.md`](../guides/self-hosting.md#running-with-no-agent-endpoint-at-all) covers the mode.

## Added

- **Server manifests, per-connection modes, and plugin compatibility checks (SEE-88 / Stage 7.1).** A connection's kind is now part of its record, and it comes from the server's own validated statement rather than from how it was added. [`proto/seekervault/server/v1/manifest.proto`](../../packages/protocol/proto/seekervault/server/v1/manifest.proto) is the document — the server's lasting ID, the phone–server contract version it speaks, a settings revision, the mode (`direct` or `gateway_feed`), one reference (a URL, or a gateway origin and a channel), the client plugins its operations need with a contract range each, the environments it serves, and a bounded name — in its own package, because the Go gateway (SEE-90) and the publisher templates (SEE-95, SEE-96) publish one too and serve no `RequestService`. [`docs/wiki/server-manifests.md`](../wiki/server-manifests.md) is the architecture page.
- **`PairingService.GetServerManifest`**, authenticated with the phone credential and scoped to the caller's connection like `GetConnectionCapabilities`. The sidecar's manifest is always the same shape, because it is always the same kind of server: `direct`, protocol 1, the URL the phone paired with, `production`, and no required plugins — an acknowledgement, a message signature and a transfer are actions the app carries out itself. Its settings revision is stored rather than constant ([migration 6](../development/mcp-server.md#migrations) on the `server` singleton): startup fingerprints the content and the revision moves by one exactly when that content changes, so a restart with the same settings republishes the same revision, and it never moves down.
- **`android/.../servers/`**, data and pure functions: the validated model, `manifestFrom` with one `ManifestProblem` per rule, `FeedReferences` for `seekervault://feed` references, and `serverSupport`. A feed reference carries no secret — a broadcast has nothing to authenticate — so one can be printed in a README, and the publisher's own address is deliberately absent from it.
- **Six states instead of a boolean**, because they are six different things to tell someone: a required plugin this build doesn't carry, one it carries at a version the server doesn't work with, a protocol version this app doesn't speak, an environment the server doesn't serve, a manifest that was refused, and supported. Legacy-direct and not-yet-asked are their own states too, and both are executable.
- **Cross-runtime manifest fixtures** in [`proto/fixtures/seekervault/server/v1/`](../../packages/protocol/proto/fixtures/seekervault/server/v1/ServerManifest): a direct server, a publisher with two requirements and a non-Latin name, a manifest claiming another publisher's channel, and a revision at the unsigned 64-bit maximum. The sidecar's tests check the bytes, and the Android tests check what the phone *makes* of each one, so both runtimes agree about which manifests are refused as well as about the wire format.

## Changed

- **A manifest confirms; it can never move a connection.** The identity, the origin and the mode it names must be the ones the connection already has, so nothing in a manifest redirects a credential, switches a transport, or claims another publisher's audience — a publisher may name only `server/<its own ID>`. A mode is never guessed, and a missing one is refused rather than read as the more permissive case, so **a paired direct connection can never become a feed**.
- **The phone caches by validated identity and revision.** The same revision keeps what it holds, a higher one replaces it, a lower one is refused, and content that changed while the revision stood still is a contradiction the phone keeps neither half of. A server it couldn't reach leaves the record exactly as it was: not hearing an answer is not an answer.
- **Support is derived on every read and never stored.** A verdict on disk would outlive the build that reached it: installing a version of the app that carries a plugin would leave yesterday's "missing" sitting in a file. `ConnectionsViewModel` and `InboxViewModel` compute it from the process's one `PluginRegistry`.
- **A server this build doesn't support is viewable and not executable.** Its requests are shown in full and can be rejected; the affirmative answer is not offered, nothing is prepared, no wallet is opened, and there is no tick to overrule it — what is missing is on this phone. Nothing falls back to signing a raw message or a transaction the app couldn't account for.
- **`Connection` gained a stored mode and a server record**, held together by one invariant: a feed always has a validated manifest, and a manifest a connection holds always agrees with its mode. `ConnectionStore` is at version 2 and still reads a version 1 file — as a direct connection whose server has not been asked yet, which is what it is.
- **`Connection.usable` carries the mode.** It already meant "the phone can still call this connection's sidecar" and is the condition on refresh, synchronization, push registration, wallet publication and every approval path, so requiring the direct mode there excluded feeds from all of them at once rather than in thirty places that could each be forgotten. A feed holds no credential and never did, and the connection screens say that instead of reporting one as missing.
- **The manifest's `oneof` is the last field group in the message.** Where a oneof's bytes land is not settled by the protobuf spec — `buf convert` writes it after the fields around it, protobuf-es writes it in field-number order — and last is the one position every runtime agrees on, which is what lets the fixtures compare bytes at all.

## Notes

- **Nothing about the existing private workflow changed.** Pairing, the credential and what it may reach, stored request identity, the lifecycle, `PrepareRequest`/`SubmitResult`, production updates, FCM registration, the wallet rules and the owner's policies are untouched, and a sidecar from before this stage answers `unimplemented` — the documented legacy-direct path, not a failure.
- **A manifest can ask for nothing.** There is no field in it for a permission, a policy, a wallet endpoint, or anything loadable, and `StageBoundaryTest` reads the protocol file and fails if the field set changes.
- **This build resolves no feed**, and says so rather than pretending: `FeedGateway` is the seam a feed's manifest comes through, the gateway that answers it is SEE-90, and `addFeed` reports `NoGateway`. There is no owner-facing screen for adding one yet, because there is nothing for it to resolve against; what the data path does is already held by tests against a fake gateway, including that no call reaches the publisher and no credential is created.
- **No screen was redesigned.** The states are said in the approved design's own components: the connection's status line, and one line in place of the approval.

## Added

- **Shared proposals, with device-local parameters, decisions and results (SEE-89 / Stage 7.1).** A publisher broadcasts one operation and everyone subscribed receives the same bytes. [`proto/seekervault/proposal/v1/proposal.proto`](../../packages/protocol/proto/seekervault/proposal/v1/proposal.proto) is that document — the publisher's identity and its own channel, a stable proposal ID, a revision that never goes backwards, the operation at the protocol's own level with the plugin it was written for, created and updated times, an absolute required expiry, an explicit open-or-cancelled status, the publisher's unverified note, and at most 32 bounded named terms — in its own package, because it is **not** the private `ActionRequest` with more subscribers. [`docs/wiki/shared-proposals.md`](../wiki/shared-proposals.md) is the architecture page.
- **`android/.../proposals/`**, data and pure functions: the validated model keyed by publisher, channel and proposal; `proposalFrom` with one `ProposalProblem` per rule; `ProposalRecord`, which keeps the publisher's half and this device's apart; the derived `proposalAvailability` and `proposalStanding`; and `bindingProblem`, the whole gate between a review and the wallet.
- **`ProposalRepository` and `ProposalStore`**: one JSON file per proposal under the feed it was read on, holding the publisher's document and this device's decisions together — the dismissal and its revision, the review and the exact revision reviewed, the binding, and what the wallet did. Every rule the model holds itself to is applied again to what comes off the disk.
- **`ActivityKind.Operation` with a `ReviewedOperation`**: the binding written down — the operation and plugin as codes, the proposal revision, the wallet and cluster, the preparation version, and the parameters this owner chose. The outcomes are the transfer path's own, its signature is a transaction's ID, and it gets an explorer link for its own cluster.
- **Cross-runtime proposal fixtures** in [`proto/fixtures/seekervault/proposal/v1/`](../../packages/protocol/proto/fixtures/seekervault/proposal/v1/Proposal): an open swap proposal with a non-Latin note, a withdrawn prediction, one claiming another publisher's channel, and a revision at the unsigned 64-bit maximum. Three runtimes have to agree about those bytes — the Go publisher that writes them, the phone that acts on them, and the sidecar — so `mcp-server/src/proposals.test.ts` checks them too, even though this sidecar publishes no proposal and never will.

## Changed

- **The personal request was not made shared to get here.** A private request is still addressed to one phone and still returns its result to the server that asked; a proposal is addressed to nobody in particular, and its state is only ever the publisher's own. Nothing in the durable workflow, its storage, or its lifecycle moved.
- **Delivery is not trustworthy about repetition, so the apply path is.** One idempotent path takes every snapshot read, stream event and duplicate push: the same revision with the same terms writes nothing at all, so a replay cannot touch a dismissal, a review or an execution; a lower revision is refused; a higher one replaces the publisher's half and leaves this device's decisions exactly where they were, which is what makes an older review *detectably* stale rather than silently applied to new terms; and the same revision with **different** terms is a contradiction the phone keeps the validated terms of and stops executing from until a higher revision says something new.
- **A dismissal is final for the proposal's identity**, not for its revision. A publisher that could re-open one by changing a number would have a way to keep putting the same proposal in front of someone who said no.
- **What is executed is never "the proposal".** The terms as they stood, the parameters this owner chose, the wallet they had selected, the plugin this build resolved and its contract version, and one set of prepared bytes are pinned together in one `ExecutionBinding` before any wallet opens. `bindingProblem` is the whole gate, and it asks for the standing rather than deciding again, so what the owner sees and what the gate allows cannot drift apart.
- **A publisher's `plugin_id` is checked, never followed.** A document cannot select code: the phone resolves the operation against its own compiled registry and refuses a proposal that names a different plugin than the one that resolved.
- **One execution per proposal identity, ever.** The record is written before the wallet is opened, under the lock that reads it, so a second tap finds it and stops — and it is not relaxed for a failure, a decline, or a new revision. A proposal that has already put an operation to this owner's wallet must not become spendable again because the publisher republished it.
- **An execution the app closed on is unresolved, and never a failure.** The wallet may well have sent the transaction. The wallet is not asked again either way, and nothing retries signing or submission automatically.
- **Availability and standing are derived on every read.** A stored "expired" would be a fact about when it was written, and wrong the moment the clock moved — the same reason support is never stored (SEE-88).
- **A feed's proposals go when the feed does**, in the same place its answers and its rules already do, and a removal that happened while the app was closed is cleaned up on the next load. The owner's Activity records outlive both.

## Notes

- **Nothing on this side is published.** For a `gateway_feed` connection there is no `PublishWallet`, no `PrepareRequest`, no `SubmitResult` and no sync upload — all of them already require `Connection.usable`, which requires the direct mode (SEE-88), so a feed is excluded from every one of them at once. A subscription tells the gateway which channel this phone is interested in, and that is the whole of what goes out.
- **A proposal cannot describe a subscriber.** There is no field in it for an address, a chosen quantity, or anything prepared for someone to sign, and `StageBoundaryTest` reads the protocol file and fails if the field set changes or if a forbidden word appears in it.

- **This build receives no proposal and executes none**, and says so rather than pretending: `ProposalFeed` is the seam, the gateway is SEE-90 and the live stream SEE-91, the plugins that read a proposal's terms and prepare its bytes are SEE-93 and SEE-94, and `refresh` reports `NoFeed`. There is no proposals screen, because there is nothing for it to list. The local path — apply, review, bind, execute, record — is held whole by tests against a fake feed and a test plugin.

## Changed

- **A credential is the whole of the grant.** It says which server the caller publishes as, and every document is checked against that rather than against what the document claims — so a publisher can name only its own channel, and a withdrawal names no channel at all. Two publishers cannot touch each other's settings or proposals, and the test that says so tries it four ways.
- **The gateway will not relay a redirection.** A published manifest must be a feed naming this gateway's configured origin; a `direct` manifest carries a URL, and holding one would let a publisher hand every subscribed phone an address of its choosing. The phone would refuse it too — the same rule, one hop later — so neither side depends on the other getting it right.
- **The revision is the idempotency key**, because it is already the publisher's promise about its content. The same revision with the same content answers `unchanged` and writes nothing; the same revision with different content is a conflict that says which revision is held; a lower one is stale; a creation time that moved is refused; and nothing is published over a withdrawal, because a phone keeps its record of a proposal it acted on for ever (SEE-89).
- **A document is rebuilt from the fields that were validated**, never stored as it arrived, so an unknown protobuf field is dropped rather than relayed to every phone on the channel. Over JSON the codec is strict: a field the contract does not have is refused, which is how an attempt to publish a wallet, an amount or a signature is answered.
- **Reads are version-aware in the contract rather than in a header.** `known_settings_revision` and `known_snapshot_sequence` answer `unchanged`, and every read answers `Cache-Control: no-store`: a proxy deciding how long a feed stays current would be a second opinion about what a publisher is proposing.
- **A walk has a documented consistency boundary and is not a transaction.** Pages are ordered by proposal ID and every page of one walk reports the sequence it began at, so a completed walk holds everything that existed then and still exists now, some possibly at a newer revision, plus anything published during it that sorts later. It converges because each document carries its own revision — which is also what lets SEE-91 buffer a stream during a walk and apply it after.
- **Retention is the proposal's own expiry plus a window**, withdrawn proposals included, so a phone that was switched off learns that a proposal was taken back rather than simply failing to find it. Nothing on a phone is deleted by it.

## Notes

- **The gateway is called and calls nobody.** No publisher is ever contacted — the point of the mode rather than a detail of it, since a publisher that could be reached could be told which phones are interested in it — and no phone, chain or provider either. A boundary test fails if shipped code acquires an HTTP client, and the image ships no trust store.
- **It keeps nothing about a reader.** No session, no subscription record, no count: a test reads the database after several reads and requires every row count to be unchanged. What it learns from a read is which channel someone asked about.
- **Delivery is at-least-once, and says so.** A crash between committing and fanning out leaves a notice to send, not a document nobody hears about; two pending notices for one document collapse into the later one, as the private workflow's push invalidations already do under one collapse key (SAW-056); and a notice is cleared only at the revision it was sent at, so a publication that lands mid-flight is sent afterwards. The phone's idempotent apply path is what makes a repeat harmless (SEE-89).
- **Nothing is fanned out to yet.** Centrifugo and Redis are SEE-91, and `dispatch.Dispatcher` is the seam; until then the fan-out is a log line, and the machinery that makes a crash harmless is exercised either way.
- **No phone calls the gateway in this build.** The Android client for `FeedGateway` and `ProposalFeed` is SEE-91's, which is where a real stream and real unary reads over TLS are proven. What closes the loop here is the fixtures, from both ends.
- **Nothing in the app or the sidecar changed behaviour.** The phone gained one test and the generated client for a service it does not call yet; the sidecar gained generated code for a contract it will never speak.

## Added

- **Streaming delivery, and the phone that listens to it (SEE-91).** The gateway fans out through **Centrifugo v6.9.6** with **Redis 8** behind it, and the phone listens over Centrifugo's unidirectional gRPC transport. [`broadcast/internal/stream`](../../broadcast/internal/stream) publishes each committed document to the broker and mints the ticket a listener connects with; [`broadcast/centrifugo.yaml`](../../broadcast/centrifugo.yaml) is the broker configured so that a listener can only listen; and `android/.../feeds/` is the phone's side — the transport behind one adapter, the decisions as pure functions, and one foreground listener per gateway. - **`FeedService.GetStreamTicket`, because a listener cannot subscribe itself.** The transport is one-way: after a stream opens the phone sends nothing, so it cannot subscribe to a channel, ask for history, or refresh its credential. The channels come from the connection's token, so the gateway grants them — the request is the channels a phone holds feed references for, and the answer is a short-lived ticket, the channels actually granted, and a lifetime. A channel this gateway does not host is left out of the grant rather than refused, because a ticket is about several channels and refusing one would take the stream away from all of them.
- **`seekervault.gateway.v1.FeedEvent`: the envelope is ours.** A publication carries the channel sequence and the document — manifest or proposal — rebuilt by the gateway from the fields it validated. The phone parses one type and runs what is inside through the same validators a read goes through, so the stream is a faster way to learn something and never a more trusted one; an event of a kind it does not know sends it to the snapshot rather than being read as an empty document. Three new cross-runtime fixtures (`FeedEvent/settings`, `proposal`, `withdrawn`) are taken from the gateway's own outbox and read back by the phone's validators.
- **A third generation template, and a vendored schema.** [`third_party/centrifugo`](../../packages/protocol/third_party/centrifugo) holds a byte-for-byte copy of the release's `unistream.proto` with its digest in `SHA256SUMS`; `pnpm generate` refuses to run if the file no longer matches, and `buf.gen.centrifugo.yaml` generates Kotlin from it into a directory of its own, keeping the broker's own package name. Neither the sidecar nor the gateway is compiled against a client protocol neither of them speaks, and exactly one file in the app may import it.
- **The stack gained two services and one public path.** `broadcast/compose.yaml` runs the broker and a deliberately unpersisted Redis on an internal network with no route out of the deployment, and Caddy forwards exactly one gRPC procedure — `/centrifugal.centrifugo.unistream.CentrifugoUniStream/Consume` — as h2c. It is on the gateway's own origin, which is the only address a phone ever learns.

## Notes

- **What the transport cannot do decided the design, and it was measured rather than assumed.** A connect request naming channels in `subs` gets a connection with no subscriptions at all; a token-granted channel bypasses the anonymous-subscribe permission, so every such permission stays off; `channel_regex` does not constrain a token-granted channel, so it is not configured; there are no application-level pings whatever `ping_interval` says, so liveness is HTTP/2's; and a graceful shutdown arrives as `3001` with `reconnect: false`, so the client reads the documented code range and not that field. Every one of those is in [`docs/testing/stage-7-1.md`](../testing/stage-7-1.md) with what was run.
- **Recovery is asked for once and answered honestly.** `recovered: true` is the only proof of continuity. A changed epoch, an offset older than the broker's history, a channel that is not recoverable or one the stream opened without all send the phone to the authoritative snapshot — because the broker's history is a bounded cache and the documents are the gateway's. A successful recovery echoes the *requested* offset, so the new cursor is the last document actually applied; a phone reading its position from that field would go backwards on every reconnect.
- **No buffer joins the snapshot to the stream, and none is needed.** Both apply through SEE-89's revision-ordered idempotent path, which refuses a document that is not newer than what is held, so a page from the middle of a walk and an event that arrives during it converge whichever order they land in. The sequence is what makes the *next* read cheap, not what makes this one correct.
- **The listener is foreground-only and shares nothing with the direct path's.** One stream per gateway, opened on `onStart`, closed on `onStop`, and reopened — debounced — when the feed set changes, because the transport cannot add a subscription to an open stream. No WorkManager was added: a shared feed has nothing to deliver to a phone nobody is holding, and what a phone needs after a while away is a snapshot.
- **Two limitations are written down rather than hidden.** The broker's **JSON** history API cannot render these binary payloads (it answers 500; `"limit": 0` still answers the channel's position, which is the supported way to ask whether it moved). And the broker's queue bound protects the *broker*: our client keeps reading the stream however slowly the application consumes it, so a slow phone never becomes a slow socket — what bounds a phone that falls behind is the gateway's publish rate limit per publisher. Each listener still costs a connection on a node; Redis makes nodes interchangeable, not free.
- **No screen lists a feed yet.** The listener applies what arrives through the repositories, and the plugins that read a proposal's terms are SEE-93 and SEE-94.

## Added

- **The Go CopyTrading publisher template (SEE-95 / Stage 7.1).** Every earlier ticket in this stage named the thing that would write the documents; [`publisher/`](../../publisher) is the first of them. A trader — or a strategy system on their behalf — posts one signal to the template's own API, it publishes that signal once to the shared gateway, and every subscribed phone reads the same document and chooses its own amount on its own device. "CopyTrading" means user-approved trader signals: no wallet monitoring, no copy detection, no unattended execution, no exchange account. [`docs/wiki/copytrading-template.md`](../wiki/copytrading-template.md) is the architecture page, including a complete worked example of where publication ends and each owner's execution begins; [`docs/integrations/signal-api.md`](../integrations/signal-api.md) is the API for an external strategy system; [`docs/development/demos.md`](../development/demos.md) is how to run it.
- **A second Go module, not a command inside the gateway.** The gateway's operator and a publisher are different people, and a template is meant to be copied out of this repository — one that compiled against `broadcast/internal/store` could not be. So `publisher/` shares the protocol in [`proto/`](../../packages/protocol/proto) and nothing else, and where that could drift [`contract_test.go`](../../publisher/internal/signals/contract_test.go) reads the **gateway's own source** for the document bounds, the revision ceiling and the channel prefix, and skips only when that source is absent — which is what a copied-out template looks like.
- **One module, two templates.** What is not about swaps — the configuration, the store, the outbox, the API and the CLI — is the module's core, and the swap signal is one `signals.Kind` that `cmd/copytrading` registers: which operation is published, which bundled plugin serves it, and what its terms must say. SEE-96's prediction template is a second kind over the same core, and no setting can turn one into the other.
- **No feed client is generated for a publisher.** [`buf.gen.publisher.yaml`](../../buf.gen.publisher.yaml) takes `publish.proto`, `problem.proto`, `proposal.proto` and `manifest.proto` and nothing else, so a template cannot read the feed it publishes to, subscribe to one, or learn anything about who is subscribed — not because a rule forbids it but because no code for it exists in the module. It is the same argument that keeps `publish.proto` out of the phone's generation, and a boundary test checks both halves: what is absent, and what is present.
- **The API is the one path in, and the CLI is a client of it.** Nine JSON endpoints over HTTP — create, update, cancel, retry, read, list, the manifest, the status and a health probe — with one token in constant time on everything but the probe. [`cmd/publishctl`](../../publisher/cmd/publishctl) imports no store, no publisher and no configuration; every command is one HTTP call that any program could make, which is what keeps validation, the identity, the revision and the publication in one place.
- **A signal is validated by the phone's own rules before anything is broadcast.** `input_mint` and `output_mint` must be exact base58 32-byte mints — a ticker is refused, because "BTC" names a dozen things on Solana and nothing off it — direction is the ordered pair with no side field, decimals are 0 to 18, the slippage ceiling is basis points of a whole, the optional bounds are whole numbers in base units, and a label is counted in UTF-16 units because that is what `String.length` counts on the phone. Numbers are published canonically, so `"09"` and `"9"` are one signal. A term the kind does not know is **refused**, which is stricter than the phone on purpose: a phone ignores an extra term because a publisher may say more than a plugin reads, but a template that minted one would be broadcasting a word nothing will ever read.
- **The document is its own outbox.** Every row carries the revision the signal is at and the revision the gateway has confirmed; anything where the first is above the second is work to do. There is no second table to keep in step, so there is no state in which a signal exists and its publication does not — and because the revision and the content are settled in the store *before* the first call, every retry sends identical bytes, which the gateway answers `UNCHANGED`. A template killed mid-publish republishes the same document rather than inventing a second one.
- **`Idempotency-Key` is required on a create**, because a bot that retries has no other way to be safe. The same key with the same statement answers 200 with the signal the first call created; the same key with a different statement is 409, since two statements cannot be one signal; a different key with identical content is deliberately a second signal. What the key is compared against is the *validated* statement, so whitespace, key order and how a number was spelled do not make a retry look new.
- **A gateway that is down is not a failed signal.** The API stores it and answers **202** with `"publication":"pending"` and the next attempt's time; the drainer keeps trying, doubling from a second to a minute. A refusal that retrying cannot change answers **502** with the gateway's own problem code and is then left alone — a restart loop must not become a publication loop — and `POST /v1/signals/<id>/retry` is how an operator says the cause is fixed. Every problem the gateway can answer with is classified in one place, with the reason written beside it.
- **Sandbox and production are separate deployments, and the database says which.** The environment has no default, it is the single value in the published manifest, and it is stamped into the file: opening a production database with a sandbox configuration is refused at startup, as is opening another publisher's. The way these get mixed up is not a mistyped argument, it is a copied compose file pointed at a volume that already exists.
- **Its own deployment, in its own directory.** A `FROM scratch` image with a static binary and — unlike the gateway's — a CA bundle from the start, because the gateway is somebody else's HTTPS endpoint and a publisher that could not verify it would be publishing to whatever answered. A base `compose.yaml` on loopback with a `Caddyfile`, a `compose.public.yaml` overlay with a warning rather than a recommendation (what it puts on the internet is a **write** API whose token is the whole grant to publish), an `.env.example`, and a `ctl` profile `docker compose up` never starts.
- **`pnpm check:publisher`**, and a fifth CI job. The script also builds the gateway into a temporary directory, so the opt-in test that runs the **real** gateway as a separate process is not silently skipped; a machine that cannot build it gets every other test and a warning saying which one it lost.

## Added

- **The Jupiter Prediction plugin (SEE-94).** `jupiter.prediction` reads which market a publisher pointed at, asks the provider what that market currently *is*, asks the owner which side and how much, and prepares a real order through Jupiter's own keyless API — then the phone resolves the transaction's accounts, reads the order back out of the bytes, and the wallet signs once. [`docs/wiki/jupiter-prediction.md`](../wiki/jupiter-prediction.md) is the architecture page.
- **A publisher names a market and is believed about nothing else.** The payload is the market's identifier, optionally its event and source, and the token a stake is deposited in ([`protocol.md`](../protocol.md#a-prediction-markets-terms-see-94)). Whether the market is open, what the two sides cost, what its rules say and when it settles are all read from the provider at the moment the owner looks — and the market is read **before** an order is requested, which is how a stale signal becomes "this market is no longer open" rather than an order that fails. The side and the stake are the owner's, are in no document, and reach neither the publisher nor the gateway.
- **The phone reads the chain, for one thing, because the provider gives no choice.** A prediction order arrives **only** as a versioned transaction whose accounts come from address lookup tables — six plausible spellings of a legacy-transaction parameter were tried against the live API and all are ignored — so the escape SEE-93 uses is not available. In a real captured order, 35 of the aggregator's 55 accounts and 4 of the prediction program's 12 sat behind those tables. The owner chose to resolve them: `solana/` is a shared, provider-neutral component with **one read method**, it discovers the tables from each transaction rather than hardcoding any, and it validates ownership, format, indices and the rebuilt account list in the runtime's own order.
- **And what that costs is written down rather than glossed.** The review is then only as accurate as the configured endpoint: this is not offline verification and is not trustless ([`security.md`](../security.md#resolving-a-lookup-table)). The endpoint is the application's or its host's — never a publisher's, because an endpoint chosen by the thing being reviewed is not a second opinion — is **empty by default** so a checkout reaches no cluster, and a table that cannot be fetched or validated **blocks signing with its own reason**. There is no parameter-only review and no blind signature anywhere in that path.
- **Resolving proves which accounts the runtime will use, and nothing else**, so every check that makes a swap approvable still runs afterwards. What the order review establishes, out of the instructions: the owner pays and the order is theirs; it buys rather than sells; it buys **the side the owner picked**, read from the instruction's own byte; the contracts, the per-contract ceiling, the cost and the slippage are the ones quoted; the stake leaves the owner's own account for the provider's own token and the contracts land in the order's own account; the funding swap — read by **SEE-93's reader, unchanged** — takes no more than the stake and puts it in the very account the order spends from; and every other instruction is one of the small set an order may contain.
- **The provider co-signs, so the rule is not "nothing else signs".** An order arrives with two signature slots and the protocol's own already filled. The rule the review holds is "exactly one signature is missing, it is the owner's, and the owner is the fee payer" — and both ways of breaking it are refused.
- **It stops at submission plus links.** No fill monitoring, no positions screen, no settlement, no payout claim, no profit or loss. Once an order is submitted the owner gets the transaction on the block explorer and **the market on Jupiter** — and deliberately no position link, because the platform has no per-position address and the site answers `200` even for a market that does not exist. Inventing one would have been the only dishonest thing on offer. Under both links the screen says plainly what the app does not know.
- **One real order and its real lookup tables are committed as a fixture.** `fixtures/jupiter/orders.json` carries an order from the live API together with the contents of the tables it names, read through the same `getMultipleAccounts` call the app uses, so `PredictionFixturesTest` resolves it offline and reads every field back against the provider's own JSON. Without the tables the fixture would not exercise the thing it exists for.

## Changed

- **`PolicyAction.Prediction` (SEE-94).** The owner's rules now have a word for buying one side of a market, because what leaves is a stake and what comes back is a claim on an outcome: somebody willing to exchange one token for another has not thereby said they are willing to bet. Without it every prediction would have warned for ever, which is the kind of warning that teaches people to tick without reading.
- **The instruction readers no longer assume where an account came from.** `transactions.readInstruction` and `jupiter.swapStep` take a program, a list of accounts and the data, so the same code reads a self-contained message and a resolved one — which is what lets an order's funding swap be read by exactly the code that reads a swap, rather than by a second copy of it.
- **The decoder can be asked for a message it cannot resolve alone.** `decodeTransaction(bytes, resolvable = true)` returns a versioned message together with the tables it names; the default is unchanged, so every reviewer that reads bytes and nothing else — transfers, swaps — still refuses one outright. It also reports **which** signature slots are empty rather than only whether any are, which is what makes the co-signing rule checkable.
- **An operation's record keeps the provider's own identifiers.** `ReviewedOperation.references` holds the order and position accounts and the market, read out of the bytes, and reaches the record through the same channel the policy snapshot uses. **No URL is ever stored**: every link is built at the moment it is shown, from compiled code, because a link read back off disk is a link something else could have written.
- **`inspect` is still not a suspending function**, and that was a decision. A prediction order has to read the chain before it can be reviewed, which would have been the obvious reason to make it one; instead the reading happens in `prepare`, where a plugin may already reach a network, and `inspect` returns what that reading found, keyed by the exact bytes. The boundary keeps its plainest promise: an inspection reads bytes, never a network.
- **A market whose `result` is JSON null is unresolved**, which took a fix: `optString` on a JSON null answers the four characters `null`, so such a market read as one that had settled on an outcome called "null" — and therefore as one no order could be placed on. The live API really does send explicit nulls there, and the test body now does too.

## Notes

- **Three ways out were possible and the owner picked one.** Sign a versioned transaction on a parameter-only review; refuse the format and ship a plugin that never prepares; or read the tables. The third keeps the app's own standard — the phone establishes what it signs — at the cost of a dependency that is now documented rather than hidden.
- **The market hash cannot be derived from the market identifier.** md5, sha1, sha256 and blake2s were each checked against a real pair and none matches, so the market is *cross-checked* between the provider's answer and the bytes rather than proved from the ID. - **A possibly dispatched order is never repeated.** An order placed twice is a position twice the size, so an answer the phone never received is recorded as unresolved, never as a failure, and nothing retries.

## Added

- **The Jupiter Swap plugin, and the path from a signal to a signature (SEE-93).** `jupiter.swap` is the first client plugin this app carries, and the first thing written against the boundary SEE-86 landed: it reads a publisher's spot-swap signal, asks the owner how much of their own money to spend, gets a route and an unsigned transaction from [Jupiter itself](../integrations/jupiter.md), and reads those bytes back independently before anything reaches a wallet. [`docs/wiki/jupiter-swap.md`](../wiki/jupiter-swap.md) is the architecture page. It reaches one host of its own and imports nothing that could sign, store or approve — a new `StageBoundaryTest` check reads its imports against an exact list and fails if the provider's host appears anywhere else in the app.
- **A signal names mints, never tickers.** The supported payload is `input_mint`, `output_mint`, their decimals, optional unverified symbols, a slippage ceiling and optional amount bounds ([`protocol.md`](../protocol.md#a-swap-signals-terms-see-93)). There is deliberately no way to propose "buy Bitcoin": "BTC" names a dozen things on Solana and nothing at all off it, so a publisher that will not name a mint has not said what it is proposing. Direction is the ordered pair, with no separate side field — one that could disagree with the pair eventually would.
- **A legacy transaction, and one hop, so the phone can read what it signs.** A versioned Solana message loads most of its accounts from an address lookup table, which cannot be resolved without reading the chain; Jupiter will state what its tables hold, and a builder's account of its own bytes has never been evidence about them here. So the plugin asks for `asLegacyTransaction` and `onlyDirectRoutes`, refuses an answer that needs a table anyway, and **verifies the single hop in the bytes** rather than merely having asked for it. What that costs — some pairs have no direct route at some sizes — is written down, and so is the standing risk: if `asLegacyTransaction` ever goes away, the plugin stops preparing rather than starts signing what it cannot read.
- **What the review covers, and what it does not, stated rather than implied** ([`security.md`](../security.md#inspecting-a-swap)). Out of the instructions: nothing is signed yet, the owner's wallet pays and nothing else signs, one routing instruction which the owner authorizes, the input leaving the owner's own token account for the publisher's mint in exactly the amount the owner entered, the output arriving in the owner's own account for the publisher's other mint, the floor the instruction will enforce equal to the offer's stated threshold to the base unit, no platform fee in either the account or the basis points, and every other instruction one of the five a swap has a reason for. **Not** the route plan, which names the pools the aggregator hops through — and that is not a gap, because the route plan cannot change any of the above: the program checks them itself and fails the whole transaction if the output falls under the floor. The phone verifies the bound; the chain enforces it.
- **The path a person walks.** `operations/` is the review and the execution: a feed connection's details offer its **Signals** where a direct connection offers Pending requests, and one of them opens a review of the shape a transfer's already has — the publisher's words as theirs, then the facts read out of the bytes, then what the owner's own rules make of those facts, never instead of each other. The package names no provider, so SEE-94's plugin will be shown by the same screens. Approve appears only for bytes the phone accounted for whole, which is input validation and not a rule anybody can overrule.
- **Two owners, one signal, their own amounts.** The amount and the slippage are collected in base units and whole basis points, within the publisher's bounds, and they stay on the phone: a feed connection has no outbox, no result upload and no per-subscriber state anywhere. `OperationPrivacyTest` runs the whole path against two real HTTP servers and reads every byte the phone sent each of them back — the gateway gets a channel and a sequence, the provider gets two mints, an amount and (for the build alone) the owner's public address, and nothing goes anywhere after the wallet.
- **Four real transactions, committed.** `fixtures/jupiter/swaps.json` holds real answers from the live API — SOL in, SOL out, an output account that does not exist yet, and the other routing variant — captured by [`scripts/capture-jupiter.mjs`](../../scripts/capture-jupiter.mjs), which has its own reader in another language and records what *it* made of each instruction. The phone's reader is asserted to agree, instruction for instruction. A transaction the tests built themselves would have been readable by construction, which is exactly the claim that needed evidence.

## Notes

- **The relay never fails a notice, and that is a decision rather than an omission.** A hint that could defer the outbox would mean the broker re-publishing documents it had already delivered for as long as somebody else's service was down. So every failure is logged by classification and swallowed, the outbox keeps meaning "the document was fanned out", and what covers a lost hint is the phone's own paths: the foreground stream, and the read it runs when it comes back.
- **A publisher cannot name a topic, and the reason is structural.** A topic is derived from the channel in a notice, and a notice is written by the gateway inside the transaction that stored the document, from the server ID the credential resolved to. There is no field anywhere one could be put in, a publication claiming another channel is refused at the door, and revoking a credential stops the hints because it stops the publications.
- **Nobody keeps a list of who subscribed.** Firebase owns topic membership; the gateway names a topic when asked and is never told whether anyone joined; and the phone keeps no list on disk — its subscriptions are derived from the connections the owner has, every time. That leaves exactly one gap, and the honest cure rather than a registry: a feed removed while the app was not running leaves a subscription behind, and a hint arriving on a topic no feed wants is unsubscribed from, so it removes itself the first time it costs anything.
- **The work input is empty, which is what makes a dropped hint free.** A hint enqueues one unique job with no input at all, and the job reads every feed the phone holds that is not already live on a stream. So two hints are one read, a hint Firebase replaced under its collapse key loses nothing, and a hint that never arrived is caught by the next one or by the owner's next glance. The quota — one hint per topic per ten seconds, burst five — drops rather than queues, and what it drops is a wake-up, never a document.
- **The proposal alert opens the feed it is on.** There is no screen that lists a proposal yet (SEE-93 and SEE-94 bring the plugins that read one's terms), so the tap route opens that feed's connection details, which is the deepest current review state this build has. The proposal's own ID travels with the route and is validated before it is used, so the screen that lists one can open it directly without the notification changing. Nothing is prepared, signed or sent by a notification or by a hint.
- **A topic message is not a schedule and not a guarantee.** Firebase decides when a topic message arrives, Android decides when a background job runs, and a force-stopped app receives nothing until the owner opens it again — the same limitation SAW-059 recorded for the private path, now written down for this one too.

## Review fixes

Three findings from the automated review of the Stage 7 branch, each fixed on top of the tickets above.

- **A discovered `jwks_uri` is now held to the same rule as a configured one (SAW-036).** `MCP_OAUTH_JWKS_URL` had to be https, or http on loopback; a URL an authorization server advertised in its own metadata did not, so a server that published a plaintext key set would have had this sidecar fetch signing keys over a network that could replace them — and a substituted key mints a token with the right issuer and audience. - **Restoring a backup sets the database's owner (SAW-038).** The sidecar runs as uid 10001 and must be able to write the file; a copy made as root would have left it unwritable, and SQLite needs to write even to read a database with a journal. The restore now chowns explicitly, and the guide says how to check the result.
