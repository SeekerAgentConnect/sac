# 2026-09-23

## Changed

- **SEE-145: one common Solana execution-provider interface, with Jupiter as the first bundled
  adapter.** `jupiter.swap` and `jupiter.prediction` stop being two plugins that happen to be
  Jupiter's and become one execution provider — `jupiter` — serving two provider-neutral, versioned
  actions: `swap` at schema 1 and `prediction.buy` at schema 1.

  What the owner wants to do is now a separate, explicit thing from who prepares it. A provider is
  **named**, never inferred: there is no routing between providers, no automatic fallback, and
  nothing anywhere that treats a market at one venue as the market at another. `ActionPlugin`
  became `ExecutionProvider`, `PluginDescriptor` became `ProviderCapabilities`, `PluginRegistry`
  became `ProviderRegistry`, and an operation became an `ActionId` with a schema version beside it.

  Capabilities say what a venue actually promises: which actions, at which schema versions, on
  which Solana clusters, in which environments, in which assets, within which limits. Resolving
  answers `Supported` or one of seven reasons — no such provider, a boundary version this build
  cannot call, an action it does not serve, a schema it does not read, a cluster it does not serve,
  an environment it does not keep, an asset it will not take — and every one of them happens before
  anything is prepared and long before anything is signed.

  Walkthroughs: [execution providers](../wiki/execution-providers.md),
  [client plugins](../wiki/client-plugins.md), [Jupiter swap](../wiki/jupiter-swap.md),
  [Jupiter prediction](../wiki/jupiter-prediction.md), [environments](../wiki/environments.md).

- **An action's payload is read once, by core, before any provider is consulted.** The `swap` and
  `prediction.buy` schemas moved out of the Jupiter package and into
  `plugins/actions/`, because they belong to the action rather than to whoever executes it: a
  publisher is a stranger, every provider of an action has to refuse the same malformed document in
  the same way, and two providers reading the same terms their own way is two chances to disagree
  about what the owner is looking at.

  What went the other way is everything genuinely the venue's. Jupiter's two stake tokens and its
  five-dollar minimum order used to be rules inside the prediction payload reader, which quietly
  made them part of what the action meant; they are now declared as its capability, and a publisher
  naming a token this venue will not take is refused when the signal is read.

- **A review is bound to the provider, the action, the schema version and the instrument**, beside
  the bytes, the revision, the owner's choice, the wallet, the cluster and the environment it was
  already bound to. Each is refused by name — `OtherProvider`, `OtherAction`, `OtherSchema`,
  `OtherInstrument`, `UnreadableTerms` — and the provider is looked up again at the moment of
  acting, so an app updated between the review and the wallet does not sign for a venue it no
  longer carries.

- **A review is one revision's terms from end to end.** When a publisher raises the revision under
  an open review, the parsed terms, the input form, which provider serves them and where the owner
  may continue outside the app are all re-read together with the record, and what the owner chose
  about the terms that were replaced is not carried onto terms they never saw. Preparing and
  approving both check the revision they were opened under, so the latest revision can never be
  prepared against the previous one's limits or pair.

- **A provider's answer reaches the review that asked for it, and no other.** A proposal ID belongs
  to its publisher, so two feeds can hold the same one and mean two different documents; the same
  proposal reopened, or moved to a new revision, is likewise a different thing to be reading. Every
  review carries its own number, `resolve` is superseded when the owner moves on, and a read that
  was already in flight is discarded rather than applied — so a closed-market answer for one feed
  cannot hide another feed's preparation, and one publisher's deposit decimals cannot change what
  an amount entered against another's means.

- **An environment is still not a network, and now neither is derived from the other.** Which
  Solana clusters a provider serves is `ActionCapability.networks`; which of sandbox and production
  it keeps is `ProviderCapabilities.environments`; and they are separate refusals, because a
  provider with no devnet is not a provider with no sandbox and telling an owner the wrong one
  would send them to change the wrong setting.

## Added

- **A test-only alternate provider**, registered beside Jupiter and driven end to end through the
  real review, rules, binding, wallet and record path without one line of core dispatch knowing it
  exists (`AlternateProviderTest`). It lives in `src/test`, so it is compiled into no APK: there is
  no flag to get wrong and nothing to strip, and `BundledProvidersTest` holds the shipped list to
  Jupiter alone.

- **Reasons the owner can act on.** A proposal nothing serves used to be a button that did nothing;
  it now says which of the seven refusals it is, in the same place a provider's own failure appears.

## Notes

- **Nothing on the wire changed, and no published manifest was invalidated.** A provider reaches
  the phone through the `plugin_id` compatibility claim that was already there, and the
  provider-neutral versioned action through the `capability_id` and `capability_version` that
  SEE-108 already defined. Both spellings of an action are accepted — a publisher saying
  `prediction` and one saying `prediction.buy` are asking for the same order — and what the phone
  re-emits is the legacy spelling, so a client written before this change reads what it always
  read. An explicit `execution_provider` field is the natural next step and is deliberately not
  part of this change.

- **`jupiter.swap` is looked up, never parsed.** It is not read as "the provider `jupiter` doing
  the action `swap`": a name that happens to contain a dot is not a structure, and one explicit
  table is the whole compatibility surface. A provider registered later needs no row in it — it
  declares the bundled names it answers to, and the registry matches them.

- **Two numbers are called "contract".** The interface inside the APK is now at 2, because
  SEE-145 changed every part of it. The number a server manifest names for `jupiter.swap` is still
  1, because the agreement between a server and a client did not change and restructuring the code
  behind a name is not the server's business.

- **Stored records survive in both directions.** `ProposalStore` stays at version 3 and writes the
  action and the provider beside the legacy operation and plugin names, never instead of them, so a
  row this build writes is still readable by one that only knows version 3, and rows written before
  are read through the same compatibility table — pending items, completed records and the
  one-attempt rule included. An activity record keeps the bundled name the owner already knows, so
  history reads the same across the upgrade.

- **The optional status query is declared and polled by nothing.** Jupiter answers that it does not
  support one, because it has no read that would let this app turn "submitted" into "filled"
  without guessing. There is still no fill monitoring, no positions screen, no settlement and no
  profit or loss here.
