## Added

- **Joined Stage 5.3 acceptance and Seeker runbook (SEE-79 / SAW-059):** `pnpm test:push` now combines a configured real-sidecar acceptance path with Android's production two-sidecar HTTP/2 synchronization path. It covers authenticated target ownership, rotation, stale compare-clear, permanent invalid-target cleanup, revocation isolation, fixed post-commit payloads, idempotent agent retries, delayed/dropped/duplicate hint timing, process-reloaded Stage 5.2 recovery, denied presentation, notification identity, and tap-to-current-state without an automatic wallet call.
  - The Firebase setup guide now points to one revision-tagged physical-device runbook covering active, background, process-absent, screen-off/Doze, TTL/drop/duplicate, token lifecycle, revoked connections, denied permission, two sidecars, stale/current taps, reboot, Force stop, and a Firebase-off comparison.
  - No physical Seeker or real Firebase deployment was available on 2026-09-14. Every delivery and OS-behavior row is recorded as **NOT RUN**; injected senders, Robolectric, WorkManager tests, and APK builds are automated evidence only.
- **Private request notifications and read-only tap routing (SEE-80 / SAW-058):** a Firebase-configured APK creates one high-importance request-review channel with secret lock-screen visibility and asks for Android notification permission only after a usable connection loads. Denial suppresses alerts only; all Stage 5.2 foreground, manual, unary, and periodic recovery remains unchanged.
  - After authoritative push Sync, newly discovered pending keys receive generic alerts and keys that left PENDING have their alerts canceled. Local removal or revocation also cancels every posted alert for that connection immediately, and unusable connections cannot receive a new alert. Notifications disclose no request content and use distinct immutable explicit intents carrying only validated connection/request IDs.
  - Tapping fetches current state from the named paired sidecar before review controls appear. Expired, canceled, answered-elsewhere, removed, revoked, and unreachable routes are stated honestly; an answer already stored on this phone opens its existing record. A tap never chooses an answer, approves, signs, or opens a wallet; the shared Sync may retry only an answer the owner already stored. Firebase-off builds create no channel, prompt, or notification.
- **Bounded FCM handoff and shared recovery (SEE-78 / SAW-057):** the messaging service now has an explicit short path: exact invalidation validation followed by unique WorkManager enqueue. It performs no sidecar fetch or cache reconciliation inside the Firebase callback budget, and the empty-input worker owns longer network work.
  - FCM collapse and WorkManager `KEEP` coalesce duplicate hints. At execution time, push and periodic recovery omit every usable connection with a Live foreground stream and send only the remaining recovery set through the existing four-sidecar-bounded, per-connection synchronization coordinator. Stream events, Refresh, periodic work, and push work therefore share one monotonic state writer.
  - Dropped pings and Firebase-off builds still converge through foreground reconciliation/Subscribe, manual Refresh, unary Sync, and the persisted Stage 5.2 periodic job. No notification permission/UI, channel, tap route, wallet operation, or new authority is added.
- **Minimal FCM invalidation and authoritative fetch (SEE-77 / SAW-056):** each committed durable request event can enqueue a coalesced Firebase data message containing only `kind=request_invalidation` and `version=1`. The FID remains a routing field; no connection or request ID, credential, policy, agent content, transaction authorization, approval, or signature enters the app-visible payload or logs.
  - New pending requests use high priority; later changes use normal. Every hint has a five-minute TTL and the shared `seeker-vault-request-state-v1` collapse key. Invalid FIDs are compare-cleared without racing rotation; transient failures leave durable state and the target unchanged.
  - Android accepts only the exact data map and enqueues one unique, connected-network, empty-input WorkManager fetch across usable connections through the existing authenticated bounded Sync repository. Push remains optional and best-effort. This child adds no notification permission/UI, channel, tap route, approval, signing, or wallet action.
- **Connection-scoped FCM target lifecycle (SEE-76 / SAW-055):** a configured Android app explicitly registers with current Firebase Messaging only while it has a usable paired connection. Initial registration and later refresh callbacks are serialized and published independently to every paired sidecar with that connection's own credential; the phone stores no target.
  - `PairingService.SetFcmToken` authenticates first, accepts only the caller's connection ID, bounds the opaque target, atomically rotates one server-side value, and compare-clears only the value being invalidated. Pairing replacement, phone revocation, and operator revocation delete it in the same SQLite transaction.
  - A transient publication failure gets three bounded exponential retries for only the failed sidecar; successful sidecars are not repeated. Credentials and FCM targets are redacted from diagnostics and logs. Firebase-off is a no-op and Stage 5.2 remains authoritative. This adds no FCM send caller, message payload handling, notification permission/UI, tap routing, sync trigger, or wallet authority.
- **Optional Firebase/FCM deployment boundary (SEE-75 / SAW-054):** Android now pins Firebase Messaging through the current BoM and applies the Google Services plugin only when an operator supplies an ignored `android/app/google-services.json`. The ordinary checkout remains unconfigured and builds the same Stage 5.2 app paths.
  - The sidecar owns one named Firebase Admin sender only when `FCM_PROJECT_ID` is explicitly set. It resolves credentials through Application Default Credentials, logs no project or credential data, and deletes the Admin app on shutdown. With the setting empty, no Firebase app is constructed.
  - This child adds no token registration or storage, FCM dispatch, app-defined messaging handler, runtime notification-permission request/channel, notification UI, deep link, or push-triggered work. The setup guide documents the Firebase library's standard merged manifest entries, project/credential deployment, off and unavailable behavior, and pricing/quotas as checked on 2026-09-14 without promising permanent zero-cost infrastructure.
- **Shared Android synchronization and persistent update state (SEE-69 / SAW-050):** Android now has one application-scoped, headless `SynchronizationRepository` for manual Refresh and the later foreground and WorkManager owners. It discovers existing-connection capability, uses gRPC unary Sync when configured, retains legacy Refresh for old/unconfigured sidecars, and keeps one observable connection-scoped state without putting credentials in it.
  - One versioned atomic document per connection stores only replaceable server state: the validated update endpoint, request/status bytes and revisions, bounded removal markers, cursor/instance, nonterminal-Activity rotation position, and last successful Sync. Complete pages and buffered events commit together; interrupted/corrupt/future state recovers with a full snapshot while phone-owned answers, approvals, signatures, policies, and Activity remain authoritative.
  - Per-connection calls coalesce, different servers proceed independently, revisions reject stale/duplicate/conflicting/regressing data, and a stream barrier is never coalesced behind a weaker manual snapshot. Deletion/revocation cancels in-flight work and invalidates late responses and older generations before deleting the cache.
  - Sync retries only results the owner already recorded through the existing idempotent delivery path and may advance an existing Activity row through the existing server-confirmation interpretation. It creates no answer or Activity row and cannot prepare, approve, open a wallet, sign, send, simulate, or re-execute. No lifecycle stream owner, worker schedule, FCM, or wallet automation is included.
- **Foreground lifecycle, live streams, and reactive screens (SEE-70 / SAW-051):** the application now owns at most one authenticated bidirectional update stream per usable paired sidecar while foreground. Rotation and navigation keep it; background, removal, and revocation close it; foreground return reconciles before resuming.
  - Replay and full-snapshot recovery feed the shared persistent synchronization path, making pending requests, counts, request state, Activity, and connection status reactive. Transient failures use isolated, capped jittered backoff, while authentication, incompatibility, revocation, and intentional background remain distinct states.
  - The real production Kotlin transport keeps its HTTP/2 send side open for subscribe and heartbeats, closes after three unanswered negotiated intervals, and cancels the RPC on lifecycle shutdown. This adds no worker, FCM, wallet automation, preparation, signing, sending, or PR-stage work.
- **Periodic WorkManager background synchronization (SEE-71 / SAW-052):** Android now retains one unique, network-constrained 15-minute periodic job while any usable connection exists. `KEEP` preserves its clock across app starts and foreground transitions; losing the last usable connection cancels it.
  - The headless `CoroutineWorker` reloads connection metadata and Keystore-encrypted credentials, then invokes the existing shared unary repository. It caps headless concurrency at four sidecars, bounds each connection, retries transient unreachability with exponential backoff, treats revocation as permanent for that connection, and skips a run when every usable foreground stream is already live.
  - WorkManager input contains no token or request. A worker may reconcile a known transaction and retry only an already-recorded result through existing paths; it cannot prepare, approve, open a wallet, sign, send, or replay. There is no foreground service, alarm, Firebase dependency, push path, or exact scheduling promise.
- **Joined live/background acceptance and Seeker runbook (SEE-72 / SAW-053):** `pnpm test:updates` now exercises the production HTTP/2 update path across real sidecar processes, the MCP SDK client, and Android's production transport, repository, persistent cache, and foreground owner. It covers foreground delivery, two-sidecar isolation, restart/expiry, lifecycle cleanup, worker-only unary recovery, bounded retry, and idempotent delivery of an existing owner result; secure-listener tests cover automatic read-only confirmation without Check status.
  - Loopback h2c uses OkHttp HTTP/2 prior knowledge on the advertised development update origin, while HTTPS keeps platform trust, host verification, and ALPN. A deliberate HTTP/1 downgrade fails the joined test.
  - The new MacBook-to-Seeker runbook covers HTTP/2 setup, two adb reverse mappings, foreground/lifecycle/fault checks, WorkManager and connection inspection, and honest device reporting. No physical Seeker was attached for this change, so background, screen-off, process-death, reboot, and force-stop checks remain NOT RUN. Stage 5.2 has no immediate background wake-up; push-triggered reconciliation remains [SEE-73](https://linear.app/seekeragentwallet/issue/SEE-73).
