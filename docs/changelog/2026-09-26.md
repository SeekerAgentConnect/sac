# 2026-09-26

## Added

- **SEE-163: the demo admin panels pair a phone by camera.** Both the Prediction admin and the
  CopyTrading trader page showed the feed reference only as text an operator had to copy into SAC
  by hand. Each now draws the reference as a QR code beside the input, and the CopyTrading Devices
  page draws every live invitation the same way, so a phone pairs — and an approved device
  redeems — by pointing SAC's camera at the screen. The codes are inline SVG drawn server-side:
  the pages' CSP still loads no images and no scripts, nothing new is encoded beyond what the
  inputs beside the codes already show, and a failed drawing leaves the text path untouched. The
  two demos each gained `internal/admin/qr.go` over the zero-dependency `go-qrcode` encoder, with
  tests that read the drawn rectangles back into the encoder's own matrix.

- **The app says when a restricted feed's publisher decides.** A decision only reached the phone
  when the owner opened the feed or refreshed it, and then only as a changed status line. While the
  app is open, every request still waiting is now checked every 20 seconds and on returning to the
  foreground — signed with the device key, never the wallet, and without reporting an unreachable
  publisher the owner did not ask about. When a request this phone already held turns approved
  (the feed connects), rejected or revoked, a snackbar says so by the feed's name. Loading stored
  access at startup and sending a new request are not announced.

- **SEE-162: the gateway's admin page can make a feed restricted.** SEE-156 made who may read a feed
  the gateway operator's registration, but only `feed-gatewayctl` could set it; the admin page showed
  the policy and said to use the command, which on App Platform meant the container console. **Add
  server** now asks who may read the feed — public, or restricted with the origin its phones
  authenticate at — and every feed publisher's page has a **Who may read** form that does what
  `feed-gatewayctl access` does, through the same store call and with the same rules: a restricted
  feed needs an HTTPS origin with no path, a public one refuses any, and a relay-only server cannot be
  restricted. A change retires every stream name issued under the old policy, so it asks for the
  server ID typed back and then says the publisher should publish its manifest again; asking for the
  policy already held changes nothing. Three admin tests cover registration, the refusals and the
  switch in both directions. Details: [docs/wiki/feed-gateway.md](../wiki/feed-gateway.md#the-operators-admin-page).

- **SEE-161: a History row opens its record, not the review.** Tapping an item under Inbox →
  History used to open the live review sheet: today's rules, a fresh quote and the review's own
  controls, for something already decided. It now opens a read-only, full-height page with no
  bottom navigation, built only from what this phone stored when it happened. The page shows the
  title and source, the final status, your response, any delivery problem, the execution result,
  the original request or signal as received, transactions, a timeline, identifiers and a footnote,
  in that order, and leaves out any section with nothing to show. Approved never reads as
  succeeded: a transaction still waiting on the chain says so, and a private transfer is re-checked
  while the page is open and updates in place. The only actions are Back, copy, the explorer link
  and **Send again** for an answer the server hasn't acknowledged. Back returns to History with the
  same tab, source filter and scroll offset, even across the process being recreated. A
  notification about an item that has closed since opens the same page. History rows gain a status
  icon and a chevron, and **Its inbox** on a connection now opens the Inbox narrowed to it, with
  the filter card. Design brief: `docs/design/history-details/`; details:
  `docs/wiki/history-details.md`.

  Not included: a private request that expired or was cancelled before it was answered still has
  no stored record, so it has no History row to open. And the record has no provider link, so
  SEE-157's **Open order** is no longer reachable from History. The brief allows no action beyond
  Back, copy, the explorer link and Send again.

- **SEE-157: a prediction's provider opens in the provider's app, and a placed order can be opened
  from History.** "This market on Jupiter" used to hand a `https://jup.ag/…` address to whatever
  opens links, which on a phone with Jupiter installed still usually meant a browser. Every
  destination is now asked for as an *app* first and falls back to the web only when no app takes
  it, so an owner with the provider installed lands in it and an owner without it lands in a
  browser, as before. A phone that opens neither is not an error: the screen says everything it
  said, and nothing about the operation depended on the link.

  Jupiter's deep link is a `jup.ag` address, and that is the honest answer rather than a
  compromise: `jup.ag/.well-known/assetlinks.json` delegates its addresses to Jupiter's own Android
  app, so Android opens them in the app that verified them. Jupiter publishes no private scheme and
  none was invented. The payload carries a deep link and a web address separately anyway, because
  the next venue's may genuinely differ.

  **The market link now lands on the market.** `https://jup.ag/prediction/<marketId>` was a guess —
  the real page is addressed by the event's slug, which the publisher template reads from the
  venue's listing and a phone cannot ask for — and the site answers `200` for anything, so the
  guess could not even be caught by fetching it. A publisher may now name the page
  (`provider_deep_link`, `provider_web_url`), and the phone's execution provider uses it **only
  when it is the provider's own property**: `https`, on its own host or a subdomain, matched on the
  host and never on the end of the string. Anything else is ignored and the composed address
  stands. So a publisher can improve where an owner lands and cannot change who they land on.

  **After an order is placed, its History entry offers "Open order".** It opens the owner's
  prediction portfolio on Jupiter, which is where a placed order actually is; there is still no
  per-order page, and an address with an order account in it would be a page nobody serves. It is
  shown only when the record holds an order account, so it never appears with nothing behind it,
  and it survives a restart because the record keeps *which* order — a public account — and the
  destination is built from compiled code at the moment it is shown. **No URL is stored**, exactly
  as before.

  Nothing about a provider is in the generic prediction screens: they carry two addresses and know
  what neither of them is. A provider that names no destination is unchanged, and an existing
  signal with no link terms behaves exactly as it did.

- **SEE-156: a feed can be restricted to the devices its publisher approved.** Every feed before
  this was a broadcast: the reference was the whole of the grant, and anyone holding it could read.
  The shipped CopyTrading signals demo is now a **restricted** feed instead, and Prediction stays a
  working public one — both on the same `publisher-support` library, and public feeds behave exactly
  as they did.

  A feed's policy is the **gateway operator's registration**, not anything a link or a publisher can
  claim. `feed-gatewayctl access --server <uuid> --access restricted --auth-origin <origin>` records
  it, and the gateway stamps it into the manifest it serves, so a feed switched to restricted is
  never served as public and a publisher cannot open its own feed by leaving the field out. A
  restricted publisher refuses to publish until the gateway confirms the policy, which is what makes
  an old gateway a failure rather than a silent downgrade.

  The owner adds the onboarding reference and proves the wallet **once**, by signing ASCII text that
  says in its own second paragraph that it is not a transaction and moves no funds. The phone
  rebuilds that text from fields and compares it with the publisher's copy before the wallet is
  opened at all, so a publisher cannot get a signature over words this app did not write. The proof
  binds a per-feed P-256 key the phone generates in the Keystore and never exports; every later step
  — asking where the request stands, taking the invitation — is signed with that key, and the wallet
  is not opened again.

  The request appears on the trader UI's new **Devices / Feed access** page, inside the existing
  password-gated admin. An operator approves, rejects, revokes, reissues, or revokes every device of
  a wallet. Approval issues a single-use invitation, valid five minutes, bound to that wallet, feed
  and installation; redeeming it mints a session and the publisher registers a grant with the
  gateway using its own server credential.

  The gateway enforces the grant on every path — each read, each page of a walk, the stream ticket,
  the topic answer and the presence answer — and a revocation moves the channel's access epoch and
  emits a control event, so a listener already attached goes silent and does not come back with its
  old ticket. Grants are finite and renewed; when the publisher cannot reach the gateway, a revoked
  device keeps reading for at most what was left of its grant, and nothing renews a grant that was
  revoked. A restricted feed has no public topic, because one anybody could join would announce
  every signal to devices nobody approved: each approved device registers its own delivery target
  under its session instead.

  What the gateway is told is deliberately thin: an opaque publisher-scoped subscriber reference, a
  device reference, a digest of the session and an expiry. Not the wallet address, and not the
  signature. What the owner is told is deliberately plain: pending, rejected, connected, revoked or
  expired, each with what they can do about it, and — because it is true — that signals already on
  the phone stay.

  Why it is shaped this way is [`docs/wiki/restricted-feeds.md`](../wiki/restricted-feeds.md);
  running a feed of your own is [`docs/integrations/restricted-feeds.md`](../integrations/restricted-feeds.md);
  running the shipped demo is [`docs/guides/restricted-feed-demo.md`](../guides/restricted-feed-demo.md).
  What was verified and what was not is [`docs/testing/see-156.md`](../testing/see-156.md) — the Go
  sides are covered by tests that were executed and passed, and the Android half is written but was
  not compiled or run on this host, which had no Android toolchain.

## Fixed

- **Service messages show as the top banner, not as a snackbar at the bottom.** Connection messages
  (added, paired, renamed, removed, access problems and the publisher's access decisions), policy
  editor messages and the activity screen's "link would not open" each drew their own snackbar at
  the bottom of the screen that raised them, in a style the rest of the app does not use. They now
  go through `LocalInAppNotices` to the same top banner that announces requests (lime) and
  disconnections (orange), as a new `Info` kind on the theme's neutral surface: queued one at a time
  behind any other banner, six seconds, swipe or tap to dismiss.

- **Switching wallets no longer keeps a restricted feed readable.** Access to a restricted feed is
  proven with one wallet, but the phone kept presenting that wallet's session whatever wallet was
  selected, so the feed stayed connected and kept delivering signals after a switch. A session is
  now presented only while the wallet it was proven with is selected: the feed reads as not paired
  with **Send access request** for the new wallet, the open stream is reopened without it, and a
  gateway refusal of a feed whose session was not presented no longer marks that session expired.
  Switching back before asking again restores access; asking with the new wallet replaces it, as
  before. The wallet selection is now loaded before stored access, including for background reads.

- **A restricted feed whose wallet signature was dismissed no longer reads as connected.** Adding a
  restricted feed stores the feed and then asks the wallet to sign the access request; closing the
  wallet instead left the feed stored with no request, and its row and detail sheet fell through to
  the gateway's transport state ("Live"), though no signal could arrive. Such a feed now reads as not
  connected — the home row is disconnected with "Not paired · request access", the detail sheet says
  no request was sent and counts it as a problem — and the sheet's second action becomes **Send
  access request**, which opens the wallet once. The same action is offered after the publisher
  rejects a request, which the rejected status already told the owner to do.

- **SEE-159: approving a prediction opened Android's wallet chooser instead of the wallet that was
  connected.** With Jupiter, Backpack and Seeker Wallet all on the phone, every approval showed
  "Open with…" and asked which one to open. Choosing "Just once" meant being asked again on the next
  approval; the only way to stop being asked was "Always", which sets a default for the whole phone —
  a decision about every app, taken for a choice that belongs to this one. The same thing happened to
  the first approval after the app was restarted, and to the connection itself, which is why the home
  card could read "phantom" when the owner believed they had connected Seeker Wallet: that was the
  account label of the app the chooser had actually opened, not stale metadata about the one they
  meant to pick.

  The wallet app the owner connects is now kept beside their account and every wallet request is aimed
  at it, so a prediction approval, a message signing, a transfer, and the first of any of them after a
  restart all open that wallet and nothing else. Where the aim comes from is only ever what somebody
  else established: the association URI the wallet itself reports while it authorizes, and the app's
  package and name as Android reports them. Nothing invents a wallet's identity, no wallet becomes the
  phone's default, and no server has any say in it.

  A phone with one wallet app connects it outright, with nothing to pick and no list to see. A phone
  with several asks once, on the Wallet screen under **Wallet app**, and then never again. Connecting
  another wallet replaces the whole aim, and disconnecting clears it, so nothing is left pointing at a
  wallet the owner has left. Upgrading keeps the wallet that is already connected: the stored record
  from the previous build is still whole, it simply doesn't say which app answered, and the next
  request finds out.

  Two outcomes are deliberate rather than convenient. **A wallet app that has been uninstalled stops
  an approval instead of moving it**: the owner is told no wallet app answered and connects a wallet
  again, because falling back to whichever other wallet Android found would put an approval given for
  one wallet in front of another. And the account the wallet signs with is still checked against the
  one the owner reviewed, so a wallet that reauthorizes a different account signs nothing — that rule
  is unchanged, and the aim does not weaken it.

  The wallet's own name is what the Wallet screen and the home card now call the wallet, with the
  account's label beside the address rather than standing in for it.

  The cause was in Mobile Wallet Adapter itself. A wallet reports where its associations belong, but
  the library's client keeps that in a private field with no way to set one, so it could learn a wallet
  within one process and never be told one — and the first request in any process went out naming no
  wallet at all. The app now builds the association itself, over the library's public scenario, intent
  creator and adapter operations, which is what lets a remembered wallet be named on it. Nothing is
  reached by reflection, the library still runs the handshake and the protocol, and the pinned version
  is unchanged.

  Twenty-nine focused regressions cover where a request is aimed for every combination of what is
  stored and what is installed, the stored record and its reading back by a phone that has restarted,
  an upgrade from the previous format, the choice on the Wallet screen, changing and disconnecting the
  wallet, and the uninstalled-wallet and wrong-account refusals. No protocol changed and no sidecar
  behaviour changed; the stored wallet record gains the aim and reads the previous format.
  Details: [docs/wiki/wallet-targeting.md](../wiki/wallet-targeting.md).

  **Not yet verified on hardware.** Acceptance is a real Seeker with Seeker Wallet and at least one
  other Mobile Wallet Adapter wallet installed, covering the initial connection, repeated approvals, a
  restart, changing the wallet, an expired authorization and a cancellation. No automated test starts a
  real wallet app or exercises Android's own resolution of the intent.

- **Rules list every kind of action (SEE-160).** The rules sheet offered only acknowledge, sign a
  message and transfer, so once **Only these actions may be asked for** was on, every swap and
  prediction signal warned "This kind of request is not on your list" with no way to allow it. The
  sheet now lists every `PolicyAction`: SKR staking, swap and prediction order included. The model,
  the stored rules and the evaluator already knew these kinds, so no storage format changed.
  `docs/policy.md` and `docs/guides/policies.md` list them too.

- **Prediction review sheet fixes.** Choosing a side and a stake no longer replaces the market's
  title in the sheet's headline; the choice stays on the "your part" card. The primary button reads
  **Approve and trade** (sandbox: **Simulate the trade**) instead of "stake". Everywhere a prediction
  asks for the owner's part it now says **side and amount** rather than "side and stake": the card
  and its **Choose side and amount** button, the stacked sheet (**Your side and amount**, field
  **Amount**), the quote texts, the notification and Jupiter's findings. SKR staking is unchanged. The sheet's facts now carry
  **This market on Jupiter · Open ↗**, the same link history showed only after an order (SEE-157),
  opened in Jupiter's app when installed. The design system gains `FactRowValueStyle.Link` and
  `ReviewSheet(onOpenLink)` for it.

- **The side-and-stake sheet rides above the keyboard.** Typing the stake opened the keyboard over
  the amount field. `SeekerSheet(aboveKeyboard = true)` pads the sheet by the keyboard's inset and,
  while it is open, has the keyboard resize the window rather than pan it (panning as well left a
  keyboard-sized gap). Only the owner-input sheet turns it on; every other screen keeps panning.
  The amount is focused when the sheet opens, so the keyboard comes up with it.

- **History items open without a decision footer.** A prediction opened from the Requests
  History tab — placed, dismissed, withdrawn, expired or unsupported — no longer shows
  **Approve and trade** / **Dismiss**; the sheet draws the footer only while the signal is open. A
  swap proposal's **Dismiss** follows the same rule.

- **"No answer from the wallet" reads "Wallet declined".** The Requests history rows and the answer
  label for a request or signal whose wallet hand-off came back without an answer said
  "Unknown: no answer from the wallet" (or "Not signed: …"); they now say **Wallet declined**. The
  detail text under the review still says the phone never learned what the wallet did.

- **Requests: swipe between Pending and History.** The two tabs are pages of a horizontal pager,
  so a swipe left or right switches them and a tap on a tab slides to it; the tab bar and the pages
  follow one selected tab. The first row now sits 16dp below the tab bar, the same as the rows' side
  margins.

- **A publisher forgot nothing about the challenges it issued.** A challenge that has expired can no
  longer be answered, so the row was spent history, and nothing deleted it: a publisher running for
  a year would have held one for every attempt anyone ever made at it. Each sync pass now forgets
  them, and a sweep that fails is logged rather than allowed to stop the pass.

- **The demo gave its eligibility rule to the access service and not to the syncer**, which is where
  a renewal re-asks it. Both defaulted to the same manual approval, so nothing behaved differently —
  but it is the wiring an integrator copies, and copied as it was it would have renewed access the
  copier's own rule had stopped allowing.
