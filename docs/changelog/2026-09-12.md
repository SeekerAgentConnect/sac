# 2026-09-12

## Added

- **Mobile Wallet Adapter and the wallet binding (SEE-23 / SAW-015):**
  - **The app connects the wallet the owner already has.** A **Wallet** row on Connections opens a screen that offers Mainnet, Devnet, and Testnet, connects through Mobile Wallet Adapter, and shows the address, network, account name, and when it was connected. **Disconnect wallet** ends it. The app creates no wallet, holds no key, and signs nothing.
  - **One boundary to the wallet.** `wallet/WalletAdapter.kt` has `connect` and `disconnect` and six outcomes: connected, no wallet, declined, an authorization the wallet refused, an unsupported network, and a failure. `MwaWalletAdapter` is the only file that imports the wallet client, and it runs the wallet from `MainActivity`'s `ActivityResultSender`. There is no dedicated wallet activity and no foreground service.
  - **The address is published; the authorization isn't.** The phone stores the selection in `filesDir/wallet/` and the wallet's authorization token, encrypted under the Keystore key, in `noBackupFilesDir/wallet/`. Only the public address and the network go to a sidecar, through the new `RequestService.PublishWallet`.
  - **Agents read it with `vault_get_address`,** which is read-only and always served. With no wallet connected it fails with the new `WALLET_NOT_CONNECTED`: no address is invented. `pnpm agent address` calls it.
  - **Creating a wallet action checks the binding.** `RequestStore.create` refuses one with `WALLET_NOT_CONNECTED` or `WALLET_MISMATCH` instead of the flat Stage 2 refusal.
  - **Changing or disconnecting the wallet cancels what no longer fits.** The sidecar cancels the connection's PENDING wallet requests and returns their references; the phone takes them off its inbox. Acknowledgements are untouched.
  - **Contract:** `WalletBinding` and `REQUEST_ERROR_WALLET_NOT_CONNECTED` in `request.proto`, and `PublishWallet` with its request and response in `service.proto`, with cross-runtime fixtures for a binding, a publication, and a cleared one.
  - **Schema migration 3** adds `wallet_address`, `wallet_network`, and `wallet_bound_at_ms` to `connections`. An upgraded database starts with no binding; connect the wallet in the app afterwards.
  - **New docs:** `docs/guides/wallet-setup.md` and `docs/testing/stage-3.md`, whose owner-run checks on the Seeker are recorded as NOT RUN.

- **Manual message signing (SEE-24 / SAW-016):**
  - **`vault_sign_message` asks the owner's wallet to sign a message,** as `message` (text, whose UTF-8 encoding is signed) or `message_base64` (bytes). It answers at once with the request as PENDING: no wallet is contacted until the owner approves it on their phone. `pnpm agent sign "<text>"` calls it.
  - **`vault_get_capabilities` says what a sidecar actually serves:** `approval: "manual"`, `signing: "wallet"`, the operations it implements, whether a wallet is connected, and the limits. It is read-only, always served, and never fails. `pnpm agent capabilities` calls it.
  - **The owner reviews the exact bytes.** Request details shows the complete message with its invisible characters marked — `␊` for a line break, `<U+200B>` for a zero-width space — the number of bytes the wallet will sign, the wallet and network that would sign, and a line saying a signature is not a payment. **Approve and sign** is the only path to the wallet, and it needs a connected wallet.
  - **The approval binds to what was reviewed.** The phone sends the SHA-256 of the exact message with its approval, and the sidecar refuses any other hash. A wallet or network that changed during the review stops the approval instead of signing something unseen.
  - **The wallet signs through the same boundary.** `WalletAdapter.signMessage` is new, and `MwaWalletAdapter` uses `signMessagesDetached` on the chain the owner connected on, checking that the wallet signed with the account that was asked. A signature over other bytes than the ones sent is discarded.
  - **The sidecar verifies, and still signs nothing.** `requests/signature.ts` checks the Ed25519 signature against the request's wallet and its own copy of the message before accepting it; anything else is `INVALID_PARAMETERS`. The stage-boundary test now also keeps signing APIs out of the sidecar's sources.
  - **The result carries the signed bytes.** A COMPLETED request has `wallet`, `signature` (base58), and `signed_message_base64`, so an agent verifies the signature itself. `pnpm agent get` does exactly that, with its own verifier, and prints `signature_verified`.
  - **A lost signing is a failure, not a doubt.** Nothing is broadcast, so an approval the wallet never answered is reported as FAILED when the app next opens.
  - **New doc:** `docs/guides/message-signing.md`, and `docs/testing/stage-3.md` gains the SAW-016 coverage, owner steps 16 to 23, and a verification record.

- **The wallet lifecycle and reliable result delivery (SEE-25 / SAW-017):**
  - **One trip to the wallet, one reported outcome.** The wallet is asked once per request, only between the owner's approval and the signing outcome. Everything that sends a result afterwards — a refresh, **Send again**, a retry after a lost response — goes to the sidecar and never to a wallet.
  - **A rotation changes nothing.** The request, the approval, and the signing survive the screen being recreated while the wallet has the message. The Mobile Wallet Adapter sender now waits briefly for the next screen's rather than failing a call the owner just started, and only the activity that registered a sender clears it.
  - **An answer this phone never received is unresolved, never a success.** A new `SigningOutcome.Unresolved` covers the app dying in the wallet and a wallet that never answers: the screen says this phone never learned what the wallet did, and the sidecar is told the request failed. `InboxViewModel.onAppVisible`, from `MainActivity.onStart`, settles them on every return to the foreground, leaving the signings still in flight alone, and the wallet is never asked again.
  - **A wallet that never answers times out** after ten minutes, so a lost result can't hold a request open for the rest of the session.
  - **Nothing is dropped between sends.** `deliver` now serializes per request: a signature stored while an earlier send was still in the air waits for it and then goes out, instead of waiting for the next refresh. A refresh, which has other work to get through, still leaves a send in flight to itself.
  - **Repeated `SubmitResult` returns the same terminal result,** for an approval and for a signature, before and after a sidecar restart. A reply naming another connection's request is refused; a reply for one connection can never settle another's.
  - **New doc:** `docs/testing/wallet-lifecycle.md`, with what the automated tests cover, fourteen owner-run checks on the Seeker recorded as NOT RUN, and the verification record. `docs/guides/troubleshooting.md` gains a section on signing a message.
  - **`ResultStore` is at version 3,** for the new outcome. Files written by versions 1 and 2 are still read.

- **The wallet setup guide and the Stage 3 device checks (SEE-26 / SAW-018):**
  - **One guide for the whole round trip.** `docs/guides/wallet-setup.md` now opens Seed Vault Wallet, connects the app, checks the address and the network from both sides, signs the example message and reads the signature back, and disconnects. It states plainly that no step here ever asks for a seed phrase, a recovery phrase, or a private key, and that anything which does isn't part of this project.
  - **Hermes can sign.** `docs/integrations/hermes.md` gains a signing section: read the capabilities, read the wallet, create the request, answer on the Seeker, read the result, and verify the signature against `signed_message_base64` with a verifier of your own. It says where the shown results come from, and that the wallet tools have never been driven by Hermes.
  - **The wallet under test is recorded, not assumed.** The guide has a table for Seed Vault Wallet's version, the device, the network path it actually accepted, and what it shows while signing — all NOT RUN until a Seeker runs them.
  - **A development wallet is not the acceptance check.** `FakeWalletAdapter` may exercise error handling, and does. Stage 3 is accepted only when the owner's own Seeker signs by hand (R8); a mock, an emulator, or a successful APK build is recorded as NOT RUN.
  - **Nothing here spends, swaps, holds an agent key, or asks for a biometric of its own** — checked rather than promised. The sidecar's boundary test pins every registered MCP tool to the seven that exist and fails on a chain RPC, a broadcast API, or any private key, secret key, or keypair in a shipped source; `StageBoundaryTest` fails on a transaction API, a biometric or device-credential API, or a biometric library on the classpath.
  - **The device script is written.** `docs/testing/stage-3.md` adds the Hermes round trip as steps 24 to 33, including both rejection paths, and a verification record that keeps the automated results apart from the physical-Seeker ones.

## Changed

- **Stage 3 has started.** `README.md` and `AGENTS.md` name it as the current stage. The stage boundary now allows the Mobile Wallet Adapter client and storage in `wallet/storage/`, on purpose, and rules out wallet-key APIs everywhere. Seed Vault's own SDK stays off the classpath until the signing task.
- **Connections always shows the Wallet row,** even with no connections yet, so a wallet can be connected before pairing.
- **`android/gradle/libs.versions.toml` pins `mobile-wallet-adapter-clientlib-ktx` 2.2.0,** and `docs/development/toolchain.md` records it.
- **Hermes's example config allows `vault_get_address`.** `docs/integrations/hermes.md` marks its recorded tool listing as the run from before the tool existed.
- **The phone API's role matrix gains `RequestService.PublishWallet`,** which only the paired phone's credential opens, for its own connection.
- **Stored answers are version 2 (SAW-016):** an answer can now be an approval, and carries what the wallet did. Files written by the previous version are still read.
- **Hermes's example config allows `vault_sign_message` and `vault_get_capabilities`.**

## Notes

- **Stage 3 is not accepted yet.** Every automated check passes and the guide is reproducible, but the owner's own wallet has signed nothing: steps 1 to 33 of `docs/testing/stage-3.md` and the fourteen lifecycle checks are NOT RUN. No mock, emulator, or APK build changes that.
- **SAW-018 changed no behaviour.** It adds documentation, two stage-boundary tests, and the verification record; the app and the sidecar work exactly as they did after SAW-017.
- **Nothing spends yet.** A message signature moves no funds and sends nothing on chain. Transfers and swaps arrive in Stages 4 and 6, and every one of them will still need the owner's approval on the phone.
- **SAW-016 changed no `.proto` file.** The contract already defined `SignMessageAction`, `Approval`, and `MessageSignature` from SAW-009, and the signed bytes are always the request's own, so nothing new had to travel on the wire.
- **Real signing on the Seeker with Seed Vault Wallet is NOT RUN.** No device was attached; steps 16 to 23 of the owner's checks cover it, including what the wallet shows while signing.
- **Which networks the installed wallet serves is the wallet's business.** The app offers all three and reports what the wallet answers, rather than assuming Seed Vault Wallet exposes a devnet switch. Step 9 of the owner's checks records what it actually does on the Seeker.
