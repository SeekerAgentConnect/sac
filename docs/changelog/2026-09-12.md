# 2026-09-12

## Added

- **Transfer integration tests and the local activity history (SEE-32 / SAW-023):**
  - **`pnpm test:transfer` drives the whole path end to end.** The sidecar runs as its own process with its own database, the CLI (`pnpm agent`) as another, the Connect phone client stands in for the phone, and a throwaway Ed25519 key pair stands in for the wallet. The chain is `startFakeRpc`, which serves the test's own `FakeChain` as ordinary Solana JSON-RPC on loopback. Seven scenarios: a SOL transfer, an SPL transfer to someone with no token account, a transaction the chain rejected, the owner's rejection, the same result twice, a restart with a transaction in flight, and an endpoint that stops answering.
  - **Nothing in the default checks reaches a cluster or spends anything.** One check does talk to a real network, and it is off unless `SEEKER_VAULT_NETWORK_CHECKS=1`: it reads devnet, needs no funded wallet, and proves the one guard no fixture can — that the sidecar reads a real cluster's genesis hash and refuses a transfer whose network doesn't match it.
  - **`pnpm agent transfer` no longer guesses any part of a payment.** `--wallet` and `--network` are required and neither falls back to `vault_get_address`; the amount must be a whole number of base units above zero, so `1.5`, `0`, `2_500_000`, and `1e6` are refused with exit code 2 before a session is opened.
  - **`pnpm agent status <id>`** reports what became of a request with an exit code a script can branch on: **0** once it ended as asked, **10** while no outcome is established — `PENDING`, `PROCESSING`, `SUBMITTED`, and `UNKNOWN` alike — and **11** once it ended any other way. It prints the state, what the server last read from the chain, and, for a transfer that was sent, `explorer_url` on its own cluster. `UNKNOWN` counts as unsettled on purpose: a script that treats it as a failure is a script that pays twice.
  - **The agent's request view gains `network`.** A signature belongs to one cluster and to no other, so the cluster an action names travels with it. A `sign_message` request has none, because nothing about it reaches a cluster.
  - **Activity: the owner's own record of what this phone did.** Reached from Connections, newest first. Each record holds who asked, the terms that were reviewed — wallet, recipient, amount in base units, asset — the network, how it ended, the signature, and which endpoint's word a confirmation rests on. One record per request, whatever happened to it on the way.
  - **It outlives the answer the server was owed.** An answer is dropped a week after it settles and when its connection is removed; a record of a payment is not. Removing the agent that asked for a transfer does not erase the transfer. The owner clears the history themselves, and that is the only way a record goes.
  - **A message signature is never shown as a payment.** A signed message carries a 64-byte signature too. Which kind a record holds comes from the kind of request, never from the signature, so there is no explorer link on one and the screen says in words that it moved nothing and is on no network.
  - **The explorer is a link, never a fetch.** **View on Solana Explorer** hands the address to whatever app opens links, on the record's own cluster. `StageBoundaryTest` proves the app makes no request to it: the address appears in one file, that file holds no HTTP client, and the app's HTTP clients exist only in the two sidecar transports and the one client they share.
  - **An approval the sidecar never accepted is recorded as nothing at all.** No wallet was opened for one and nothing moved, so there is nothing to have a record of.
  - **A history that can't be read says so.** It keeps showing what it last read and warns, instead of reading as an empty history — an unreadable record and no record must never look the same.
  - **New docs:** `docs/testing/stage-4.md`, with the scenario table, the opt-in devnet check, what the automated checks deliberately can't show, and ten owner-run device checks recorded as NOT RUN. `docs/guides/transfers.md` gains **The Activity record**, and `test-agent/README.md` the new `transfer` requirements and `status`.

- **On-chain confirmation and uncertain outcomes (SEE-31 / SAW-022):**
  - **`SUBMITTED` and `CONFIRMED` are now different things in practice, not only on paper.** A transfer the wallet sent stays `SUBMITTED` until the chain settles it. The sidecar reads the signature's status (`getSignatureStatuses`), fetches the transaction under it (`getTransaction`), and stores what it found — the commitment level, the slot, the chain's own error, when it looked, and how often — in a new `Outcome.confirmation`.
  - **A confirmed result is checked against the approved bytes.** Before anything is called `CONFIRMED`, the transaction the chain holds under that signature is compared, over its message, with the exact `PreparedTransaction` the approval named. A signature naming some other transaction settles nothing: the request stays `SUBMITTED`, `matches_approval` is false, and the detail says plainly that nothing here can account for the approved transaction.
  - **Nothing runs on its own.** There is still no background worker. A check happens when the agent reads the request with `vault_get_request` — throttled to one chain call every two seconds per request — or when the owner taps **Check status**, which is the new `RequestService.CheckStatus`. That check opens no wallet, sends nothing again, and either settles the request or leaves it exactly as it was.
  - **Silence is never taken for evidence.** An endpoint that timed out, refused, or has no status yet changes nothing at all. Only the approved transaction's own blockhash window closing, *together with* a search of the ledger itself that still finds nothing, is read as "it can never land" — and that is the only route to `FAILED` without a chain error.
  - **The trust is named.** A confirmed or failed transfer rests on one endpoint's word. Its **host** — never the URL, which can carry an API key — is stored in the confirmation, returned to the agent as `checked_with`, offered in `vault_get_capabilities` as `confirmed_with`, and shown on the phone as "Checked with …".
  - **Nothing replaces a transaction.** Not on a chain failure, not on an expired blockhash, not on a signature the sidecar can't account for. An `UNKNOWN` transfer — the phone lost the wallet before it reported anything — has no signature to look up at all; checking says so and leaves it `UNKNOWN`. Another attempt is a new request the owner approves by hand.
  - **On the phone:** a sent transfer's status now says whether the network confirmed it, rejected it with the network's own reason, or hasn't settled it yet, with **Check status** offered while the chain could still decide. A failed check says so and changes nothing about the transaction.
  - **Documentation:** [confirmation](../protocol.md#confirmation), [sending a transfer](../guides/troubleshooting.md#sending-a-transfer) including an `UNKNOWN` outcome, [`docs/guides/transfers.md`](../guides/transfers.md), and [`docs/security.md`](../security.md#confirming-a-transfer-saw-022).
- **Approving a transfer through the wallet (SEE-30 / SAW-021):**
  - **A transfer reaches the wallet only through the owner's explicit approval of the preparation this phone inspected.** The review screen now offers **Approve and send**, and offers it only for a transaction the phone read whole and found to match the request (SAW-020). Anything else gets no button at all rather than one that refuses, and can still be rejected.
  - **The approval binds to four things:** the request, the preparation's version and content hash, the wallet, and the network. A version read again while the owner was looking, a wallet other than the one on screen, or an inspection that didn't come back `Verified` stops it before anything is stored.
  - **The sidecar is the commit point.** The approval is written to this phone — with the exact bytes — and sent, and the wallet is opened only once the sidecar accepts it and the request is `PROCESSING`. An approval it refuses as `STALE_PREPARATION`, or that never reaches it, is deleted: nothing was approved anywhere, the request stays `PENDING`, and the phone reads it again for a fresh review.
  - **The wallet is handed the stored bytes, not bytes fetched again.** A sidecar that rebuilt the transaction between the review and the approval cannot substitute one, and a rotation or a restart cannot change what is signed. `MwaWalletAdapter` calls `signAndSendTransactions`: the wallet signs and submits, and the app still builds nothing, signs nothing of its own, and has no chain endpoint.
  - **An outcome nobody knows is reported as UNKNOWN.** A wallet that says it signed but didn't submit, a session that ended without an answer, or an app killed while the wallet had the transaction all become `unknown_outcome`, never an execution failure and never a retry. A message keeps the old meaning — nothing broadcast, so `FAILED` — because nothing about a message reaches a network.
  - **One wallet interaction at a time,** across every screen, and one per approval: double taps, a refresh crossing the send, and **Send again** all reach a sidecar and never a wallet.
  - **Policy says "Not evaluated."** Per-connection rules are Stage 5, and the screen says so rather than calling anything ALLOWED.
  - **Storage:** answers are version 4, holding the version, content hash, and unsigned bytes an approved transfer is bound to, so a crash between the approval and the wallet's answer can't change what was approved.
  - **Documentation:** [approval binding](../architecture.md#approval-binding), the transfer half of [`docs/testing/wallet-lifecycle.md`](../testing/wallet-lifecycle.md) with ten new device checks, the owner's side in [`docs/guides/transfers.md`](../guides/transfers.md), and [`docs/security.md`](../security.md#approving-a-transfer-saw-021).
- **Inspecting transfer bytes on the phone (SEE-29 / SAW-020):**
  - **The review screen derives a transfer from the transaction, not from the server.** Opening a PENDING transfer fetches a fresh preparation and decodes it on the phone: the amount in base units, the recipient, the token's mint, the fee payer, every required signer, what each instruction does, the blockhash, and any compute-budget price. All of it is then checked against the stored request, which never changes, and against the wallet the owner selected.
  - **No chain is read, and none is needed.** A token account's address derives from its owner and its mint, so the phone computes it and compares; `TransferChecked` carries decimals the token program enforces; and a token is shown as its mint address and base units, never a name. There is no ticker to fake.
  - **Anything unread is reported as unread.** An instruction the app can't read leaves the transaction not fully covered, not approvable, and the screen says how much of it was read. An instruction from a program that *can* move value — `Approve`, `SetAuthority` — makes the preparation invalid outright: a program a transfer may use is not permission for every instruction it offers.
  - **Anything unaccounted for is refused.** Bytes left over at the end, a length spelled two ways, an instruction index outside the account list, an address lookup table, a signature already present, or a content hash that isn't the bytes' own all end the review.
  - **The server's numbers are labelled as the server's.** A network fee can't be read out of a transaction, so it sits under its own heading, apart from the facts; the agent's note stays where it was, marked unverified.
  - **`RequestService.PrepareRequest` is wired up on the phone,** with a new `ConnectionGateway.prepareRequest`. Preparations are held in memory only: one is good only while its blockhash is, so a stale one is never read back from disk and shown as current.
  - **Shared fixtures tie the two halves together:** 20 transactions built by the sidecar's real builder and decoded by the phone, covering sound transfers, tampered ones (a changed recipient, amount, or mint, an extra transfer, an extra signer, the wrong fee payer), a delegate riding along, an unknown program, and bytes that can't be read at all. See [`docs/testing/transaction-fixtures.md`](../testing/transaction-fixtures.md).
  - **Documentation:** what inspection guarantees and what it doesn't, in [`docs/security.md`](../security.md#inspecting-a-transfer).
- **Transfer requests and fresh transaction preparation (SEE-28 / SAW-019):**
  - **`vault_transfer` queues a transfer of SOL or a classic SPL token.** It takes `wallet`, `network`, `recipient`, `amount` in base units, and an optional `token_mint`, and answers at once with the stored request as `PENDING`. Nothing is built, signed, or sent when it is called. `pnpm agent transfer <to> <amount> [--mint <address>]` drives it from the agent's side.
  - **`RequestService.PrepareRequest` builds the transaction.** For a PENDING transfer it reads the chain — the mint's decimals, the owner's and the recipient's associated token accounts, a fresh blockhash — and compiles one unsigned version 0 transaction with no address lookup tables, the owner's wallet as the fee payer and only signer, and every signature slot empty. SOL uses one System `Transfer`; a token uses `TransferChecked`, preceded by `CreateIdempotent` when the recipient has no token account yet.
  - **Each preparation is a new version, and supersedes the last.** The response carries the bytes, their SHA-256, the version, `last_valid_block_height`, the estimated expiry, the network fee, and the rent for any account it creates. An approval of an earlier version, or one that arrives with less than 15 seconds of the blockhash window left, is refused with `STALE_PREPARATION`.
  - **The sidecar reads the chain, and can do nothing else with it.** `sidecar/src/solana/` is the only place that reaches a cluster, and every method there is a read: genesis hash, account info, latest blockhash, block height, fee for a message, and rent exemption. There is no send, no simulate, and no signer.
  - **It refuses what it can't honestly prepare, by name:** a Token-2022 mint, an NFT, an uninitialized mint, a missing or frozen token account, a balance below the amount, a recipient given as a token account or an executable program, and an endpoint whose genesis hash isn't the request's network.
  - **`SOLANA_RPC_URL` and `SOLANA_RPC_TIMEOUT_MS`** configure the endpoint. Without a URL the sidecar serves no `vault_transfer`, leaves `transfer` out of `vault_get_capabilities`, and answers a transfer's `PrepareRequest` with the new `CHAIN_UNAVAILABLE`. The URL may carry an API key, so it never reaches a log or an error message.
  - **Contract:** `PreparedTransaction.fee_lamports` and `.rent_lamports`, and `REQUEST_ERROR_CHAIN_UNAVAILABLE`, in `request.proto`, with the cross-runtime fixtures updated in both runtimes.
  - **Documentation:** `docs/guides/transfers.md` for the owner, transfers and preparation in `docs/protocol.md`, and the tool, the configuration, and the new tests in `docs/development/sidecar.md`.
- **Mobile Wallet Adapter and the wallet binding (SEE-23 / SAW-015):**
  - **The app connects the wallet the owner already has.** A **Wallet** row on Connections opens a screen that offers Mainnet, Devnet, and Testnet, connects through Mobile Wallet Adapter, and shows the address, network, account name, and when it was connected. **Disconnect wallet** ends it. The app creates no wallet, holds no key, and signs nothing.
  - **One boundary to the wallet.** `wallet/WalletAdapter.kt` has `connect` and `disconnect` and six outcomes: connected, no wallet, declined, an authorization the wallet refused, an unsupported network, and a failure. `MwaWalletAdapter` is the only file that imports the wallet client, and it runs the wallet from `MainActivity`'s `ActivityResultSender`. There is no dedicated wallet activity and no foreground service.
  - **The address is published; the authorization isn't.** The phone stores the selection in `filesDir/wallet/` and the wallet's authorization token, encrypted under the Keystore key, in `noBackupFilesDir/wallet/`. Only the public address and the network go to a sidecar, through the new `RequestService.PublishWallet`.
  - **Agents read it with `vault_get_address`,** which is read-only and always served. With no wallet connected it fails with the new `WALLET_NOT_CONNECTED`: no address is invented. `pnpm agent address` calls it.
  - **Creating a wallet action checks the binding.** `RequestStore.create` refuses one with `WALLET_NOT_CONNECTED` or `WALLET_MISMATCH` instead of the flat Stage 2 refusal.
  - **Changing or disconnecting the wallet cancels what no longer fits.** The sidecar cancels the connection's PENDING wallet requests and returns their references; the phone takes them off its inbox. Acknowledgements are untouched.
  - **Contract:** `WalletBinding` and `REQUEST_ERROR_WALLET_NOT_CONNECTED` in `request.proto`, and `PublishWallet` with its request and response in `service.proto`, with cross-runtime fixtures for a binding, a publication, and a cleared one.
  - **Schema migration 3** adds `wallet_address`, `wallet_network`, and `wallet_bound_at_ms` to `connections`. An upgraded database starts with no binding; connect the wallet in the app afterwards.
  - **New docs:** `docs/guides/wallet-setup.md` and `docs/testing/stage-3.md`, whose owner-run checks on the Seeker are recorded as NOT RUN.

- **Manual message signing (SEE-24 / SAW-016):**
  - **`vault_sign_message` asks the owner's wallet to sign a message,** as `message` (text, whose UTF-8 encoding is signed) or `message_base64` (bytes). It answers at once with the request as PENDING: no wallet is contacted until the owner approves it on their phone. `pnpm agent sign "<text>"` calls it.
  - **`vault_get_capabilities` says what a sidecar actually serves:** `approval: "manual"`, `signing: "wallet"`, the operations it implements, whether a wallet is connected, and the limits. It is read-only, always served, and never fails. `pnpm agent capabilities` calls it.
  - **The owner reviews the exact bytes.** Request details shows the complete message with its invisible characters marked — `␊` for a line break, `<U+200B>` for a zero-width space — the number of bytes the wallet will sign, the wallet and network that would sign, and a line saying a signature is not a payment. **Approve and sign** is the only path to the wallet, and it needs a connected wallet.
  - **The approval binds to what was reviewed.** The phone sends the SHA-256 of the exact message with its approval, and the sidecar refuses any other hash. A wallet or network that changed during the review stops the approval instead of signing something unseen.
  - **The wallet signs through the same boundary.** `WalletAdapter.signMessage` is new, and `MwaWalletAdapter` uses `signMessagesDetached` on the chain the owner connected on, checking that the wallet signed with the account that was asked. A signature over other bytes than the ones sent is discarded.
  - **The sidecar verifies, and still signs nothing.** `requests/signature.ts` checks the Ed25519 signature against the request's wallet and its own copy of the message before accepting it; anything else is `INVALID_PARAMETERS`. The stage-boundary test now also keeps signing APIs out of the sidecar's sources.
  - **The result carries the signed bytes.** A COMPLETED request has `wallet`, `signature` (base58), and `signed_message_base64`, so an agent verifies the signature itself. `pnpm agent get` does exactly that, with its own verifier, and prints `signature_verified`.
  - **A lost signing is a failure, not a doubt.** Nothing is broadcast, so an approval the wallet never answered is reported as FAILED when the app next opens.
  - **New doc:** `docs/guides/message-signing.md`, and `docs/testing/stage-3.md` gains the SAW-016 coverage, owner steps 16 to 23, and a verification record.

- **The wallet lifecycle and reliable result delivery (SEE-25 / SAW-017):**
  - **One trip to the wallet, one reported outcome.** The wallet is asked once per request, only between the owner's approval and the signing outcome. Everything that sends a result afterwards — a refresh, **Send again**, a retry after a lost response — goes to the sidecar and never to a wallet.
  - **A rotation changes nothing.** The request, the approval, and the signing survive the screen being recreated while the wallet has the message. The Mobile Wallet Adapter sender now waits briefly for the next screen's rather than failing a call the owner just started, and only the activity that registered a sender clears it.
  - **An answer this phone never received is unresolved, never a success.** A new `SigningOutcome.Unresolved` covers the app dying in the wallet and a wallet that never answers: the screen says this phone never learned what the wallet did, and the sidecar is told the request failed. `InboxViewModel.onAppVisible`, from `MainActivity.onStart`, settles them on every return to the foreground, leaving the signings still in flight alone, and the wallet is never asked again.
  - **A wallet that never answers times out** after ten minutes, so a lost result can't hold a request open for the rest of the session.
  - **Nothing is dropped between sends.** `deliver` now serializes per request: a signature stored while an earlier send was still in the air waits for it and then goes out, instead of waiting for the next refresh. A refresh, which has other work to get through, still leaves a send in flight to itself.
  - **Repeated `SubmitResult` returns the same terminal result,** for an approval and for a signature, before and after a sidecar restart. A reply naming another connection's request is refused; a reply for one connection can never settle another's.
  - **New doc:** `docs/testing/wallet-lifecycle.md`, with what the automated tests cover, fourteen owner-run checks on the Seeker recorded as NOT RUN, and the verification record. `docs/guides/troubleshooting.md` gains a section on signing a message.
  - **`ResultStore` is at version 3,** for the new outcome. Files written by versions 1 and 2 are still read.

- **The wallet setup guide and the Stage 3 device checks (SEE-26 / SAW-018):**
  - **One guide for the whole round trip.** `docs/guides/wallet-setup.md` now opens Seed Vault Wallet, connects the app, checks the address and the network from both sides, signs the example message and reads the signature back, and disconnects. It states plainly that no step here ever asks for a seed phrase, a recovery phrase, or a private key, and that anything which does isn't part of this project.
  - **Hermes can sign.** `docs/integrations/hermes.md` gains a signing section: read the capabilities, read the wallet, create the request, answer on the Seeker, read the result, and verify the signature against `signed_message_base64` with a verifier of your own. It says where the shown results come from, and that the wallet tools have never been driven by Hermes.
  - **The wallet under test is recorded, not assumed.** The guide has a table for Seed Vault Wallet's version, the device, the network path it actually accepted, and what it shows while signing — all NOT RUN until a Seeker runs them.
  - **A development wallet is not the acceptance check.** `FakeWalletAdapter` may exercise error handling, and does. Stage 3 is accepted only when the owner's own Seeker signs by hand (R8); a mock, an emulator, or a successful APK build is recorded as NOT RUN.
  - **Nothing here spends, swaps, holds an agent key, or asks for a biometric of its own** — checked rather than promised. The sidecar's boundary test pins every registered MCP tool to the seven that exist and fails on a chain RPC, a broadcast API, or any private key, secret key, or keypair in a shipped source; `StageBoundaryTest` fails on a transaction API, a biometric or device-credential API, or a biometric library on the classpath.
  - **The device script is written.** `docs/testing/stage-3.md` adds the Hermes round trip as steps 24 to 33, including both rejection paths, and a verification record that keeps the automated results apart from the physical-Seeker ones.

## Changed

- **The phone reads transactions, and still signs and sends nothing.** The Android stage boundary lifts the limit for decoding alone: reading stays in `transactions/`, holds no key, and reaches no network. Approving a transfer through the wallet is SAW-021, so the review screen says plainly that approving isn't built yet rather than offering a button that would do nothing.
- **The transfer parser is the app's own, deliberately.** The Mobile Wallet Adapter client already puts `web3-solana` and BouncyCastle on the classpath, so this was never about dependency count: a general-purpose decoder reads what it can, and what a review needs is something that refuses everything it cannot fully account for. `StageBoundaryTest` fails if a source file starts importing an SDK decoder instead.
- **Stage 4 has started.** `README.md` and `AGENTS.md` name it as the current stage. The sidecar's stage boundary now allows `@solana/web3.js` and a chain client, on purpose, and in return names every tool the sidecar serves and every JSON-RPC method it calls. The Android boundary is unchanged: the phone still builds and sends nothing.
- **`@solana/web3.js` 1.99.0 is a sidecar dependency,** used only for address maths and message compilation. The SPL Token instructions and layouts are encoded in `sidecar/src/solana/token.ts` instead, so the bytes the phone will parse in SAW-020 are written and frozen by tests here. `bufferutil` and `utf-8-validate`, `ws`'s optional native builds, stay off.
- **Stage 3 has started.** `README.md` and `AGENTS.md` name it as the current stage. The stage boundary now allows the Mobile Wallet Adapter client and storage in `wallet/storage/`, on purpose, and rules out wallet-key APIs everywhere. Seed Vault's own SDK stays off the classpath until the signing task.
- **Connections always shows the Wallet row,** even with no connections yet, so a wallet can be connected before pairing.
- **`android/gradle/libs.versions.toml` pins `mobile-wallet-adapter-clientlib-ktx` 2.2.0,** and `docs/development/toolchain.md` records it.
- **Hermes's example config allows `vault_get_address`.** `docs/integrations/hermes.md` marks its recorded tool listing as the run from before the tool existed.
- **The phone API's role matrix gains `RequestService.PublishWallet`,** which only the paired phone's credential opens, for its own connection.
- **Stored answers are version 2 (SAW-016):** an answer can now be an approval, and carries what the wallet did. Files written by the previous version are still read.
- **Hermes's example config allows `vault_sign_message` and `vault_get_capabilities`.**

## Notes

- **No automated check has ever sent a transaction to any cluster.** Every transfer test in this repository runs against a fake chain on loopback, and none of them needs a funded wallet. The opt-in devnet check reads and spends nothing.
- **SAW-023's device checks are NOT RUN.** No device was attached; checks 31 to 40 in `docs/testing/stage-4.md` cover the history on a real Seeker, including the explorer opening on the right cluster.
- **The history stores base units, and not a token's decimals.** A mint's decimals are read fresh when a transfer is reviewed. Keeping a count from months ago could show a wrong amount later, so the record keeps the number the transaction actually carried; SOL, whose decimals are fixed, is also shown the readable way.
- **Nothing can be approved or sent yet.** SAW-020 reads a transfer and judges it. The owner still cannot approve one, and no wallet is opened for a transfer: that is SAW-021.
- **Inspection proves what a transaction does, not what it is worth.** The phone has no prices, and a mint address is not a reputation. Whether the token, the amount, and the recipient are the ones the owner meant stays the owner's judgement.
- **Nothing spends yet.** SAW-019 is the sidecar's side: a stored request, and unsigned bytes for review. The phone's own inspection of those bytes (SAW-020), approval through the wallet (SAW-021), and on-chain confirmation (SAW-022) are not written, so no transfer can yet be approved or sent.
- **No real cluster is touched by any check.** Every transfer test runs against a fake chain on loopback, and the default checks spend nothing on any network.
- **A failed preparation changes nothing.** The request stays PENDING and can be prepared again; only `CHAIN_UNAVAILABLE` is worth retrying unchanged.
- **Stage 3 is not accepted yet.** Every automated check passes and the guide is reproducible, but the owner's own wallet has signed nothing: steps 1 to 33 of `docs/testing/stage-3.md` and the fourteen lifecycle checks are NOT RUN. No mock, emulator, or APK build changes that.
- **SAW-018 changed no behaviour.** It adds documentation, two stage-boundary tests, and the verification record; the app and the sidecar work exactly as they did after SAW-017.
- **Nothing spends yet.** A message signature moves no funds and sends nothing on chain. Transfers and swaps arrive in Stages 4 and 6, and every one of them will still need the owner's approval on the phone.
- **SAW-016 changed no `.proto` file.** The contract already defined `SignMessageAction`, `Approval`, and `MessageSignature` from SAW-009, and the signed bytes are always the request's own, so nothing new had to travel on the wire.
- **Real signing on the Seeker with Seed Vault Wallet is NOT RUN.** No device was attached; steps 16 to 23 of the owner's checks cover it, including what the wallet shows while signing.
- **Which networks the installed wallet serves is the wallet's business.** The app offers all three and reports what the wallet answers, rather than assuming Seed Vault Wallet exposes a devnet switch. Step 9 of the owner's checks records what it actually does on the Seeker.
