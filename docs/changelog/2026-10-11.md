# 2026-10-11

## Added

- **Client configuration from the trusted gateway (SEE-185).** The APK carries one gateway origin
  (`-Pseekervault.gatewayUrl`, release `SEEKERVAULT_GATEWAY_URL`, `BuildConfig.GATEWAY_URL`). The
  gateway's operator sets the Solana RPC endpoint for mainnet, devnet and testnet and the SAC swap
  service fee once for every app that trusts it. The app fetches both from the new
  `FeedService.GetClientConfig`, caches them, and applies a change at once without a rebuild. The
  gateway stores the configuration in a single-row `client_config` table (SQLite schema 9, Postgres
  schema 5 with RLS). The revision moves by one with every real change, and saving an identical
  configuration changes nothing. It is set on the admin page (**Client configuration**) or with
  `feed-gatewayctl client-config show | set-rpc | set-fee`. Both validate it whole: https endpoints
  (loopback http only), no user info or fragment, fee 0–100 bps never clamped, base58 owner, mints
  and accounts. Everything in it is public, so a provider that needs a secret key goes behind the
  operator's own proxy. [docs/wiki/client-config.md](../wiki/client-config.md).
- **Every signal names its network (SEE-185).** `request.v2` contract version 2 adds the required
  `ActionCapability.network`. The gateway accepts only contract 2 for new publications. A missing or
  unknown network is `GATEWAY_PROBLEM_BAD_NETWORK`. A network the publisher's held manifest does not
  declare, or a publisher with no manifest yet, is the new `GATEWAY_PROBLEM_OTHER_NETWORK`
  (`failed_precondition`), checked in the publication's own transaction. Documents that declare a
  network are left out of the protocol-1 `ListProposals`/`GetProposal` views. On the phone a
  contract-1 document, or one with an unknown network, stays readable and is never executed.
  Nothing infers a network for it.
- **A feed operation's wallet is chosen per operation (SEE-185).** The review shows the signal's
  **Network** and the **Wallet** that will sign. The choice is remembered per feed and network. When
  there is no remembered choice, the only authorized profile on that network is used, and otherwise
  none. The phone never substitutes a profile from another network. A restricted feed's
  **Access wallet** is a separate identity, used only to prove access, and public feeds are added
  with no wallet. [docs/guides/wallet-setup.md](../guides/wallet-setup.md#feed-operations).
- **Preview without sending (SEE-185).** Beside a feed signal's approval, when the provider serves a
  preview, the owner can run the same preparation, inspection, rules and binding gate without
  opening the wallet. The preview is recorded beside the signal, and the signal stays open.
  Executing needs a fresh preparation. [docs/wiki/environments.md](../wiki/environments.md).
- **A transaction proven never sent goes back to PENDING (server SDK).** The phone's new
  `SubmitResultRequest.not_sent` moves an UNKNOWN transfer, swap or staking request back to
  PENDING, the lifecycle's one backward step. The sidecar first checks for itself, through its
  `ConfirmationProvider`, that the endpoint serves the request's network and that the chain is past
  the approved version's `last_valid_block_height`; until then it answers `CHAIN_UNAVAILABLE`
  (`unavailable`) and moves nothing. With no endpoint it answers `unimplemented`. The reopened
  request clears the dead attempt's approval, signature and confirmation, needs a fresh preparation
  (the approved version is spent, `STALE_PREPARATION`), and expires at once if its deadline has
  passed. Repeated results are now judged within the current attempt. The `vault_transfer` and
  SKR staking instructions say an UNKNOWN request can return to PENDING.
  [docs/protocol.md](../protocol.md#reopening).

## Changed

- **SAC swap fee (SEE-173) comes from the gateway.** Feed swaps carry the gateway's terms for the
  signal's network, which are zero unless the operator sets a fee. Direct operations always carry
  none. The terms are pinned with the preparation and checked again before the wallet opens and
  inside the wallet lock. If they changed, the review says "The service fee configured for this app
  changed…" and the owner prepares again. Jupiter's on-chain account verification and the fee
  disclosure are unchanged. A failed fetch is never read as a zero fee. With no usable
  configuration (unreachable gateway and nothing cached within 24 hours, or an invalid answer), the
  operation is not prepared.
- **Solana RPC endpoints come only from the gateway (SEE-185, replacing SEE-184's sources).** There
  is no build default, owner setting or general fallback. Per-network genesis proof, wrong-cluster
  refusal, side-by-side networks and the debug-only local validator are kept. Confirmation, history
  and position reads use the cached endpoints of any age.
- **One trusted gateway (SEE-185).** Feed links, Discover cards and manifests that name another
  gateway are refused. A feed already stored from another gateway is readable and not executable.
  The relay and Discover use the same gateway.
- **Publishers (SEE-185).** The business API requires `network` on create and update (`bad_network`
  400, `other_network` 400, `network_fixed` 409), and `publishctl create|update` needs `--network`.
  Store schema 6 adds the signal's network. A signal stored before SEE-185 gets no network: it is
  refused locally (`no_network`) instead of being published open, and it can still be withdrawn.
  The `PublishProposal` fallback is removed. The CopyTrading trader form offers the manifest's
  networks, with mainnet selected. Prediction names mainnet on every signal and re-publishes older
  signals as a new generation. `PREDICTION_STATE=any` is allowed and logs a warning.
- **Direct manifests (server SDK, MCP server)** no longer emit environments. The manifest's
  fingerprint changes once, so its settings revision moves once on upgrade.
- **The signal review puts the decision first.** "Who carries this out" (provider, disclosures,
  official links) now sits below the Approve / Preview / Dismiss buttons instead of above the
  network, wallet and "Your part" sections.
- **Trade signal tiles say what the publisher says.** A swap signal's Home tile is labelled
  "Signal" and titled by the publisher's note (first line, up to 90 characters) instead of "Swap".
  Its review no longer shows "What the publisher proposed": the publisher's raw terms and expiry
  sit folded at the bottom of the sheet, and "Who carries this out" is folded the same way. The
  swap amount field is labelled "Amount".
- **The signal review's header** no longer shows the protocol action ("swap") over "From
  <connection>" (see the header entry below). An open signal no longer shows a "Waiting for you"
  banner, and the publisher's note is shown as the sheet's title-size text instead of under "What
  the publisher says".
- **A swap signal's "Your part" works like a prediction's.** The review shows a "Your part · amount
  and wallet" card ("2.5 USDC · Main wallet") whose **Choose amount and wallet** / **Edit** opens a
  sheet stacked over the review with the signing wallet (**Choose** / **Change** opens the wallet
  picker over it), the amount and the slippage. **Use these** writes the choice and prepares at
  once. The separate Network / Wallet card and the inline amount and slippage fields are gone; **Get
  a fresh quote and prepare again** remains once something was prepared or failed.
- **A prediction's wallet is chosen with its side and stake.** The prediction review no longer has
  a **Choose wallet** / **Connect a wallet** button: the side and stake sheet starts with the
  signing wallet (**Choose** / **Change** opens the picker over it), **Use these** needs one, and
  the Your part card reads "5 USDC on Yes · Main wallet".
- **The prediction review has no Quote card and no wallet row.** The quote's figures (contracts,
  cost, payout, fee, market status) and the payer read out of the transaction are rows under
  Technical details; the chosen wallet is on the Your part card.
- **A feed's server row no longer says "Choose a wallet".** Paired servers showed it for any feed
  that declares networks and has no bound wallet, although since SEE-185 a feed's operations each
  choose their wallet for the signal's network. Only a direct server that declares a network still
  asks for one; a restricted feed's missing access wallet is said by its access line.
- **A swap signal is reviewed in the prediction's review sheet.** An open swap opens the design's
  `sheet-swap`: "Swap", the pair as the headline ("USDC → SOL"), the router and the most the price may
  move, the Your part card, the verdict, the stale-quote and preparation-error cards, and the pinned
  footer (**Approve and swap**, **Preview without sending**, **Dismiss**, or "Getting a quote…"
  while one is fetched). The supporting detail sits in the same four collapsed sections as a
  prediction's, with the swap's terms labelled under Technical details. The stages, verdict, checks
  and sections are one shared mapper (`SignalStage`, `SignalSheetWording`). An executed swap keeps
  the older review with its explorer and receipt.
- **The swap review's header matches the prediction sheet's.** It is titled "Swap" (or "Signal" for
  another action), with the **Signal** chip and the connection's chip under the title, the
  publisher's note, then the network chip the signal declares (devnet flagged).

  `GATEWAY_PROBLEM_OTHER_ENVIRONMENT` (34) are reserved. The gateway no longer validates manifest
  environments or holds them fixed, and it drops them from stored manifests. The phone's

  sets the variable starts and logs that it is ignored.
- The Wallet → **Solana RPC** sheet, `RpcSettingsStore`, `RpcEndpointCard` and the
  `rpc-endpoint-card` design spec.
- The Android build settings `seekervault.solanaRpc*`, `seekervault.relayUrl`,

- `pnpm check:swap-fee-build` and `scripts/check-swap-fee-build.sh`.

## Fixed

- **A direct request's review stays open while the wallet signs.** The approval is stored before
  the wallet is asked, and the wallet hand-off read that stored answer as "done": the review closed
  as the wallet opened. The hand-off now stays until the signing ends, and then returns to the
  review.
- **A transfer whose wallet never answered is settled as "Not sent".** Closing the wallet without
  answering (for example on its "Network mismatch" screen) left the request approved with an
  outcome `UNKNOWN` for good, and the phone even dropped the approved bytes. The phone now keeps them,
  and once the blockhash has expired (three minutes after the hand-off at the earliest) it searches
  the wallet's history on chain, comparing every transaction in the window byte for byte. Found:
  it reads as sent and the server moves `UNKNOWN → SUBMITTED`. Absent: **Not sent · nothing was
  spent**, the phone reports `not_sent`, and the request is back in **Waiting** to approve again
  (see the reopening entry above). A server from before `not_sent` gets `execution_failure`
  instead (`UNKNOWN → FAILED`), so its agent may ask again. A search that can't
  cover the window stays unknown and is retried. Transfers left unknown by an earlier build are
  captured again from their stored approval. The phone also reads how far back an endpoint's
  ledger reaches from a slot after its lowest when the lowest was pruned in between (devnet does
  this), which stopped every proof of absence. [docs/wiki/chain-confirmation.md](../wiki/chain-confirmation.md#a-wallet-that-never-answered).
- **The wallet hand-off returns to the review.** Whatever the wallet did — signed, declined,
  failed, or never answered — and after **Decline**, the hand-off closes and the review stays open
  with the request's status, instead of closing every sheet.
- **The wallet names the app by its site.** Mobile Wallet Adapter's identity URI was the source
  repository, so wallets showed "github.com" as the requesting application. It is now
  `https://seekeragentconnect.github.io`. A wallet may ask to authorize the app once more, because
  its earlier authorization was given to the old identity.
- **A direct sidecar keeps in step with the connection's wallet.** Before this fix, a direct
  sidecar kept the published binding after it stopped declaring that wallet's network
  (`SAC_SUPPORTED_NETWORKS`). The phone reported _Network unsupported_ and refused to sign, but the
  MCP server kept accepting agents' transfers for that wallet. Every review then said "Transaction
  does not match" / "no wallet ready". Now:
  - The phone publishes **no wallet** for that connection, so agents get `WALLET_NOT_CONNECTED`
    and the sidecar cancels the pending requests nobody can approve. When the server declares the
    network again, or the owner chooses a wallet on a declared network, the binding is published
    again (`WalletRepository.bindingOf`).
  - A binding the sidecar couldn't be told is retried whenever connections change, for example on
    a refresh or a manifest re-read. Before, it was retried only when the app returned to the
    foreground (`WalletViewModel`).
  - A request opened before its connection's wallet was ready, or before the owner changed it, is
    prepared again for the current wallet. Before, it kept the stale verdict
    (`InboxViewModel`).

- **A prediction's wallet can be changed after one is chosen (SEE-185 review).** The prediction
  review reached the operation-wallet picker only while no wallet was chosen; once one was chosen or
  remembered, tapping "your part" opened the side and stake instead, so an owner with two Mainnet
  profiles could not switch from A to B. The review now shows **Choose wallet** under its wallet row
  whenever the signal is open (`ReviewSheetState.walletAction`), and choosing another wallet drops
  what was prepared for the old one, so approval needs a fresh quote for the new wallet.
- **Overlapping client-configuration saves no longer lose a half (SEE-185 review).** The admin
  page's endpoint and fee forms and `feed-gatewayctl client-config set-rpc|set-fee` used to read the
  whole configuration, change one half and save the whole as a separate step, so a fee saved between
  the read and the write of an endpoint change (or the other way round) was silently written back.
  They now go through the new `PublisherAdminStore.UpdateClientConfig`, which applies the change to
  what is held and validates and writes the result in one write transaction (SQLite's single writer,
  Postgres's advisory write lock).
- **Signal API docs:** the minimal Python strategy loop in
  [signal-api.md](../integrations/signal-api.md#a-minimal-strategy-loop) now sends the signal's
  required `network`, which it omitted (a `400 bad_network`).
- **Android Home:** a staking request (from the SKR staking server) in the "Waiting for you" rail
  is labelled **Staking** with its own icon. It fell through to the acknowledgement tile and read
  "Acknowledge".

## Migration and deployment

These changes are breaking. In order:

1. **Upgrade the gateway first.** Its migrations add `client_config` and drop environments from
   stored manifests. No new environment variable is needed.
2. **Set the client configuration**, for example:
   `feed-gatewayctl client-config set-rpc --network mainnet --url <https endpoint>` for each network
   the app should read, and `set-fee` if the SAC fee was configured in the build before. Until then,
   the gateway answers revision 0: no endpoints and no fee. Chain reads and Prediction orders then
   fail and say why. [docs/development/swap-fee-config.md](../development/swap-fee-config.md).
3. **Upgrade publishers.** Send `network` on every create and update (`publishctl --network`). Delete
   `PUBLISHER_ENVIRONMENT`. If you ran a sandbox deployment and a production deployment of the same
   template, keep one: preview or execute is now the owner's choice on the phone. Signals from before
   SEE-185 have no network. Withdraw them and publish them again with one (the Prediction template
   does this itself).
4. **Build the app** with `SEEKERVAULT_GATEWAY_URL` (an origin), and remove the retired variables from
   the repository's Actions variables.
5. Feeds a phone added from a gateway other than the build's stay readable and can't be executed.
   Remove them and add them again from the trusted gateway.

## Prediction admin: unpublish, saved search, NBA preset

- **Unpublish a market from the feed.** Each open row of **Published on this feed** has an
  **Unpublish** action (with a confirmation) that calls the new operator endpoint
  `POST /v1/discovery/unpublish` (`{"request_id"}`). It withdraws the proposal and marks the market
  `dismissed`, so discovery cycles stop publishing it on their own (counted as reason `dismissed`).
  Publishing it by name from the search brings it back as a new proposal. Withdrawn and expired
  proposals move into a collapsed **Withdrawn and expired** list.
- **The market search survives a publish.** The admin page saves the last search's filters and
  results in the browser's `localStorage` and restores them after publishing. **Clear markets**
  removes the saved results and keeps the filters.
- **Search presets.** **Sports — NBA** (Polymarket, `sports`, keyword `nba`) runs as one click.
- **Publishing or unpublishing during a discovery cycle waits instead of failing.** A cycle holds
  the reconciler for its whole walk (about 20 s every 5 minutes on the hosted demo). Select and
  unpublish used to answer `409 busy` ("a discovery cycle is already running") at once. They now
  wait up to 30 s for the cycle to finish and answer busy only if it hasn't by then.
- Store schema 7 (`packages/publisher-support/store`) adds `market.dismissed`. Existing files are
  brought forward on open. A file opened by this build is refused by older builds.
  [docs/wiki/prediction-template.md](../wiki/prediction-template.md).

## Prediction demo: liquid yes-or-no questions only, no crypto prices

Three new discovery rules, all on by default. A cycle and the admin search apply all three. A
publish by name applies only the liquidity rule.

- **No market an owner could not get out of.** Both YES and NO must have an offer under $1 and a bid
  above 0, each at most `PREDICTION_MOST_SPREAD_CENTS` apart (1–99, default 5). The bid/ask comes
  from the listing's `pricing`, which Jupiter has always sent and the demo did not read. Prices are
  read only to decide; they are never published. Skipped as `no_liquidity`. A publish by name of
  such a market answers `409 no_liquidity`.
- **Only events with two outcomes.** `PREDICTION_OUTCOMES=two` (default) publishes only events that
  are a single yes-or-no market. Strike ladders, valuation ranges and "by October / by December"
  ladders are skipped as `more_than_two_outcomes`. `any` restores the old behaviour.
- **No crypto price events.** `PREDICTION_CRYPTO_PRICES=exclude` (default) skips crypto events about
  a token's price as `crypto_price`. That covers events tagged `crypto-prices`, `hit-price`,
  `price-milestone`, `price-comparison` or `fdv`, and untagged titles such as "Up or Down",
  "… above ___ on …", "What price will … hit" or "… price on …". Crypto events about launches, laws
  or listings stay.
- A filter is still discovery, not withdrawal. Proposals already published that break a new rule
  stay until the selection replaces them with an eligible event, the source closes them, or the
  operator unpublishes them.

## Pairing links short enough to survive an agent

`vault_create_pairing_link` (and `pnpm pair`) returned `https://<origin>/pair#<fragment>` with a
fragment that was base64url JSON holding the whole `seekervault://pair` URI and the replacement
warning sentence, several hundred characters. Hosted agents relayed it as `/pair#eyJ2Ij...WiJ9`,
and the page rejected the abbreviated fragment as damaged. New links use a compact fragment,
`2.<server id>.<token>.<expiry, Unix seconds>.<0|1 replaces a phone>` (plus `.<path>` when the
server URL has one), about 95 characters. The page completes the server URL from its own origin
and shows its own warning text. The old fragment is still read, so links issued before the upgrade
keep working until they expire. Code: `packages/server-sdk/src/pairing/page/payload.js`,
`landing.ts`; both MCP servers pick it up from the SDK.

## Prediction review says when it is waiting for a quote

While a prediction signal's quote was being fetched, the review's footer kept Approve and Preview

## Feed swaps stop on the phone instead of expiring in the wallet

- **A Jupiter preparation stands for 20 seconds, not a minute.** On mainnet the blockhash in
  Jupiter's swap build stopped being includable about 28 seconds after it arrived, so a swap
  approved at about 35 seconds reached Seeker Wallet already dead, and the wallet answered "Blockhash
  expired" while the app recorded "The wallet gave no answer". `SWAP_PREPARATION_LIFETIME` is now
  20 seconds and a prediction order's `ORDER_LIFETIME` shares it. Approving after the window closes
  now stops on the phone with "prepare again" (`BindingProblem.PreparationExpired`), before the
  wallet is opened. Nothing is rebuilt and nothing extra is signed.
  [docs/wiki/jupiter-swap.md](../wiki/jupiter-swap.md#limits-honestly).
- **No Refresh quote step.** A swap or prediction quote that ran out stays approvable. **Approve**
  (or **Preview without sending**) with less than 15 seconds of the preparation left prepares it
  again in the background, inspects the fresh bytes and assesses the rules again, then opens the
  wallet straight away. If the rules' verdict differs from the one the owner read, it stops with
  "the rules changed" and shows the new one instead. The "This quote has run out" card and its
  strings are gone. [docs/wiki/prediction-review.md](../wiki/prediction-review.md#approving-a-quote-that-ran-out).

## Fixed

- **Prediction orders were refused as "not the ones you were quoted".** Jupiter's order answer now
  states `slippageBps: 134620` while the order instruction carries `0`; contracts, price ceiling and
  cost still match exactly. The review required all four to be equal, so every quote was refused
  and "Get a new quote" could not help. The slippage in the bytes may now be tighter than the answer
  and never looser (`PredictionInspection.kt`).

## Added: a caution before buying a side nobody is buying

- **Prediction buy review warns when the position could not be sold.** A Yes bought on "Solana price
  on October 13? · <80" could not be sold afterwards: Jupiter reported `sellYesPriceUsd: 0`, so the
  phone's Sell position stayed disabled. The review now reads the market's bid for the chosen side
  before the order. With none, it shows "You may not be able to sell this" and requires a tick
  ("I understand I most likely can't sell this position or get my money back before the market
  settles") before the wallet is opened. New `ActionInspection.cautions` carries it from the plugin
  to core, which enforces the tick in `OperationViewModel.go`.
  [docs/wiki/prediction-review.md](../wiki/prediction-review.md#when-nobody-is-buying-the-chosen-side).

## Fixed: transactions the wallet added its own instructions to read as mismatched

- **A sent SKR stake showed "Unresolved · mismatch".** Seeker Wallet appended a compute-unit limit
  and price and two Lighthouse assertions to the approved staking transaction before sending it, and
  the phone and the servers compared the chain's message with the approved one byte for byte. Both
  now accept a message that differs only by compute-budget and Lighthouse instructions, with every
  approved instruction, signer, writability, blockhash and lookup table unchanged
  (`transactions/ApprovedMessage.kt`, `server-sdk` `isApprovedMessage`, used by `mcp-server` and
  `mcp-skr-staking`). Checked against the real stake, kept as
  `fixtures/transactions/wallet-added.json`. [docs/wiki/chain-confirmation.md](../wiki/chain-confirmation.md#what-counts-as-an-answer).
